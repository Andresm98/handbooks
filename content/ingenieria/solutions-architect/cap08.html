La seguridad no es una capa que se añade sobre una arquitectura existente — es una propiedad que debe estar presente desde el primer diagrama. Un SA que trata la seguridad como un requisito tardío construye sistemas que son re-arquitecturados (o abandonados) después de incidentes.

Zero Trust: El Modelo Mental Correcto

Zero Trust no es un producto ni una herramienta — es un principio: "Never trust, always verify." Elimina el concepto de red interna segura. Cualquier request, desde cualquier origen (interno o externo), debe ser autenticado, autorizado, y registrado.


  Modelo Perimetral (Legacy) vs Zero Trust

  PERIMETRAL (INSEGURO):
  Internet → [Firewall] → Red interna "confiable"
                          │  ┌─────────┐  ┌─────────┐
                          └─►│ Svc A   │─►│ Svc B   │ (sin auth entre servicios)
                             └─────────┘  └─────────┘
  Problema: Si un atacante cruza el firewall, tiene acceso a TODO.
  Lateral movement trivial. El 80% de los brechas ocurren internamente.

  ZERO TRUST:
  Internet → [Identity Proxy] → Request con identidad verificada
                                │
              Cada request verifica: ┌─────────────────────────┐
              1. ¿Quién eres?       │ Identity Provider (IdP)  │
              2. ¿Tienes permiso?   │ (Okta, Auth0, KeyCloak)  │
              3. ¿Desde dónde?      └─────────────────────────┘
              4. ¿Es normal?                   │
                                    ┌──────────▼──────────┐
              ┌─────────┐  mTLS     │ Policy Engine       │
              │ Svc A   │──────────►│ (OPA, Casbin)       │
              └─────────┘           └─────────────────────┘
              ┌─────────┐  mTLS
              │ Svc B   │──────────► Igual verificación
              └─────────┘
Perspectiva complementariaZero Trust: El Modelo de Seguridad para Sistemas Distribuidos

El modelo perimetral tradicional ("confiar en todo dentro de la red") fue diseñado para una era donde las aplicaciones vivían en datacenters físicos con un perímetro claro. En sistemas cloud-native y microservicios, ese perímetro no existe.


  MODELO PERIMETRAL TRADICIONAL (obsoleto)
  
  ┌─────── "Red Segura" (firewall perimetral) ────────┐
  │                                                   │
  │  Service A ──────────────────────► Service B      │
  │  (sin autenticación, "confiamos en la red interna")│
  │                                                   │
  │  Problema: Un atacante dentro del perímetro       │
  │  tiene acceso a TODO sin restricciones             │
  └───────────────────────────────────────────────────┘

  ZERO TRUST MODEL (moderno)
  
  Cada request se evalúa independientemente:
  
  Service A ──[mTLS + JWT]──► API Gateway ──[AuthN + AuthZ]──► Service B
                │                    │                    │
                ▼                    ▼                    ▼
         Identidad               Políticas            Auditoría
         verificada              evaluadas            registrada
  
  Principios Zero Trust:
  → "Never trust, always verify" — incluso tráfico interno
  → Least privilege — mínimos permisos necesarios
  → Assume breach — diseñar como si el atacante ya está dentro
  → Verify explicitly — autenticar cada request con contexto completo

Patrones de Autenticación y Autorización

OAuth2 + OIDC: EL ESTÁNDAR REAL

OAuth2 es un framework de autorización (¿qué puedes hacer?). OIDC (OpenID Connect) añade autenticación sobre OAuth2 (¿quién eres?). La mayoría de los sistemas modernos usan ambos. 


  OAuth2 Authorization Code Flow + PKCE (estándar para apps web/móvil)

  Usuario   Browser/App     Auth Server     Resource API
     │           │                │               │
     │──login───►│                │               │
     │           │──auth request─►│               │
     │           │  (+ code_verifier PKCE)         │
     │           │                │               │
     │◄──────────│◄─login form────│               │
     │──creds────►────────────────►               │
     │           │◄─auth code─────│               │
     │           │                │               │
     │           │──token request─►               │
     │           │  (code + code_verifier)         │
     │           │◄─access_token──│               │
     │           │  + id_token    │               │
     │           │  + refresh_token               │
     │           │                │               │
     │           │──API call──────────────────────►│
     │           │  (Bearer: access_token)         │
     │           │◄─response──────────────────────│
     │           │                │               │

  PKCE (Proof Key for Code Exchange): previene interceptación del auth code.
  Obligatorio para public clients (SPAs, mobile apps).

JWT: USO CORRECTO Y ERRORES COMUNES

// JWT Payload — lo que va dentro del token (NO encriptado, solo firmado)
{
  "sub": "user-123",          // Subject: ID del usuario
  "iss": "auth.company.com",  // Issuer: quién emitió el token
  "aud": "api.company.com",   // Audience: para quién es
  "exp": 1734000000,          // Expiration: cuándo expira
  "iat": 1733996400,          // Issued at: cuándo se emitió
  "jti": "uuid-v4",            // JWT ID: para prevenir replay attacks
  "roles": ["admin", "finance"],
  "org_id": "org-456"
}

// ERRORES CRÍTICOS con JWT:
// ❌ Guardar datos sensibles en el payload (está en base64, no cifrado)
// ❌ Expiration muy larga (1 semana+) — imposible revocar
// ❌ No validar 'aud' — un token de servicio A acepta en servicio B
// ❌ Algoritmo 'none' — vulnerabilidad clásica en implementaciones malas
// ❌ Guardar access token en localStorage — XSS lo expone
// ✓  Guardar en httpOnly cookie o en memoria (SPA)
// ✓  Access token: 15 min. Refresh token: 7-30 días en httpOnly cookie

RBAC vs ABAC: CUÁNDO USAR CADA UNO

RBAC — Role-Based Access Control

  • Permisos asignados a roles, roles a usuarios
  • Simple de entender y auditar
  • admin, editor, viewer, billing-admin
  • Suficiente para 80% de los sistemas
  • Problema: role explosion en sistemas complejos
  • Implementación: JWT roles, Casbin, OPA

ABAC — Attribute-Based Access Control

  • Permisos basados en atributos del usuario, recurso, y contexto
  • "Puede ver si es el owner O está en el mismo org"
  • Más expresivo, más complejo
  • Necesario para multi-tenant, permisos granulares
  • Difícil de auditar sin herramientas
  • Implementación: OPA/Rego, AWS Cedar, Zanzibar

mTLS: AUTENTICACIÓN MUTUA ENTRE SERVICIOS

En un sistema Zero Trust, los servicios se autentican entre sí mediante certificados TLS mutuos. Cada servicio tiene su propio certificado de identidad. Implementaciones: Istio service mesh, SPIFFE/SPIRE, Consul Connect.


  mTLS: Handshake Mutuo
  
  Service A                           Service B
      │                                   │
      │──── Client Hello ────────────────►│
      │◄─── Server Certificate ───────────│  (Svc B presenta su cert)
      │──── Client Certificate ──────────►│  (Svc A presenta su cert)
      │◄─── Verify (ambos se autentican) ─│
      │                                   │
      │    Ambos verifican:                │
      │    1. Cert firmado por CA interna  │
      │    2. Identidad del servicio (SPIFFE: spiffe://cluster/ns/svc-b)
      │    3. Cert no revocado (OCSP)      │
      │                                   │
      │═══════ Comunicación cifrada ══════│
  
  Automatizado con Istio: la app no sabe que existe mTLS.
  El sidecar (Envoy) maneja todo transparentemente.

OAuth 2.0 + OIDC: LOS PROTOCOLOS ESTÁNDAR

  OAuth 2.0 Authorization Code Flow (con PKCE — el más seguro para SPAs)
  
  Browser/App          Authorization Server       Resource Server
  ──────────           ────────────────────       ───────────────
  1. Genera code_verifier + code_challenge
  2. Redirect → /authorize?code_challenge=...
  3.                   ← Login page
  4. User credentials →
  5.                   ← Authorization code (corto plazo, ~10 min)
  6. POST /token con code + code_verifier
  7.                   ← access_token (JWT) + refresh_token
  8. GET /api/resource + Bearer token ──────────────►
  9.                                  Valida JWT (firma, exp, claims)
  10.                                              ← Protected resource
  
  Puntos críticos:
  → code_verifier nunca viaja por la red — protege contra intercepción del code
  → access_token de vida corta (15 min típico)
  → refresh_token de vida larga con rotación automática
  → Siempre HTTPS — ninguna excepción
JWT: ESTRUCTURA Y VULNERABILIDADES COMUNES
# ✓ Validación segura de JWT en producción
import jwt
from datetime import datetime, timezone

def validate_token(token: str, public_key: str) -> dict:
    try:
        payload = jwt.decode(
            token,
            public_key,
            algorithms=["RS256"],   # ← NUNCA "none" o "HS256" con secreto débil
            options={
                "verify_exp": True,    # Verificar expiración
                "verify_aud": True,    # Verificar audience (tu servicio)
                "verify_iss": True,    # Verificar issuer (tu auth server)
                "require": ["exp", "iat", "sub", "aud"]
            },
            audience="payments-service",
            issuer="https://auth.miempresa.com"
        )
        # Verificar que el token no está revocado (token blacklist en Redis)
        if is_revoked(payload["jti"]):
            raise jwt.InvalidTokenError("Token revoked")
        
        return payload
        
    except jwt.ExpiredSignatureError:
        raise AuthError("Token expired — use refresh token")
    except jwt.InvalidTokenError as e:
        raise AuthError(f"Invalid token: {e}")

# ❌ Vulnerabilidades comunes:
# jwt.decode(token, key, algorithms=["none"])  — permite tokens sin firma
# jwt.decode(token, key)                       — algoritmo no verificado
# Sin verificar audience — token robado de otro servicio es válido aquí

  Anti-pattern: Secrets en código / variables de entorno en texto plano
  ─────────────────────────────────────────────────────────────────────
  DB_PASSWORD=mysecretpassword123  ← en .env o en el Dockerfile
  → Visible en logs, en historial de git, en imágenes de Docker

  Pattern correcto: Dynamic Secrets con HashiCorp Vault
  ─────────────────────────────────────────────────────────────────────
  
  App (Service Account) ──[Kubernetes Auth]──► Vault
                                                │
                              ┌─────────────────┘
                              │ Genera credenciales dinámicas
                              │ con TTL corto (1 hora)
                              ▼

  → Si el password se filtra, expira en 1 hora

  → Auditoría completa: quién pidió qué credencial y cuándo
  → Revocación inmediata si el servicio es comprometido

Seguridad en Kubernetes: Las 5 Configuraciones Críticas

# 1. Pod Security Context — nunca ejecutar como root
securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  readOnlyRootFilesystem: true  # Filesystem read-only
  allowPrivilegeEscalation: false
  capabilities:
    drop: ["ALL"]              # Drop todas las capabilities

---
# 2. NetworkPolicy — denegar todo por defecto, permitir explícitamente
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: payments-ingress
spec:
  podSelector:
    matchLabels:
      app: payments
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:           # Solo desde API Gateway
        matchLabels:
          app: api-gateway
    ports:
    - port: 8080
  egress:
  - to:
    - podSelector:           # Solo hacia la BD
        matchLabels:
          app: postgres
    ports:
    - port: 5432

---
# 3. RBAC — Least privilege para service accounts
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: payments-role
rules:
- apiGroups: [""]
  resources: ["secrets"]    # Solo puede leer sus secrets
  verbs: ["get"]
  resourceNames: ["payments-secrets"]
Modelos relacionados

La seguridad arquitectónica se implementa de forma diferente según el estilo. En Microservicios, mTLS y service mesh son la base del Zero Trust. En Serverless, IAM roles con least privilege son el mecanismo principal. En Event-Driven, la autenticación del productor/consumidor en Kafka (SASL/SSL) y el cifrado de mensajes son críticos. En Clean/Hexagonal Architecture, los security concerns pertenecen a los adapters externos, no al dominio.

Perspectiva complementariaSeguridad en Kubernetes: Los Vectores Más Comunes
Containers corriendo como root

Un container root que escapa al host tiene acceso de root al nodo. Siempre usar runAsNonRoot: true + readOnlyRootFilesystem: true en SecurityContext.

Secrets en variables de entorno

Las variables de entorno son visibles en kubectl describe pod y en logs de crash. Usar Vault Agent Injector o External Secrets Operator.

Network policies abiertas

Por defecto en K8s, cualquier pod puede comunicarse con cualquier otro pod. Las NetworkPolicies deben ser "deny all" por defecto con allowlist explícito.

Imágenes sin escaneo de vulnerabilidades

Una imagen base con CVEs críticos es una vulnerabilidad desplegada. Integrar Trivy, Grype o Snyk en el pipeline de CI — nunca en CD.

RBAC demasiado permisivo

ClusterAdmin para todos los service accounts es equivalente a "sudo sin contraseña". Definir roles mínimos por servicio con auditoría activa.

API Server expuesto sin restricciones

El API server de K8s no debe ser accesible desde Internet. Usar private endpoint + VPN/Bastion + IP allowlist para acceso administrativo.

Modelos relacionados

La seguridad arquitectónica se integra directamente en Hexagonal Architecture (los adaptadores de entrada son el primer punto de autenticación/autorización), en Microservices (mTLS entre servicios como implementación de Zero Trust), y en Service Mesh (Istio/Linkerd como implementación de políticas de seguridad sin código en los servicios).

Perspectiva complementariaOtra forma de plantear este capítulo

La seguridad no es una capa que se añade encima de la arquitectura — es una propiedad que emerge del diseño desde el inicio. Un SA que trata la seguridad como un checklist de compliance al final del proyecto crea sistemas que son vulnerables por diseño, no por implementación.

La pregunta correcta no es "¿estamos seguros?" sino "¿cuáles son nuestros threat vectors, cuál es la probabilidad de cada uno, y cuál es el costo de mitigación vs el costo del impacto?"
