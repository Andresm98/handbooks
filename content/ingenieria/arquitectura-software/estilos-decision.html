Un estilo arquitectónico no es una moda ni una marca en el CV — es una respuesta a un conjunto específico de problemas. El error más común en la industria es seleccionar un estilo porque "es lo que se usa ahora" en lugar de porque resuelve los problemas específicos del contexto.

El SA senior conoce los estilos como un cirujano conoce sus instrumentos: cada uno tiene un uso correcto, un uso incorrecto, y consecuencias severas si se aplica en el contexto equivocado.

MONOLITO MODULAR: EL ESTILO MÁS SUBESTIMADO

El monolito modular es frecuentemente la respuesta correcta para organizaciones de 10–50 personas que sienten la presión de "ir a microservicios". Ofrece boundaries claros de módulo sin el costo operacional de servicios separados.

EVENT-DRIVEN ARCHITECTURE: CUÁNDO ES LA RESPUESTA

La arquitectura event-driven no es un estilo de moda — es la respuesta correcta cuando el negocio genuinamente opera en términos de eventos y necesita desacoplamiento temporal entre productores y consumidores.

Usar EDA cuando
  • Múltiples sistemas deben reaccionar al mismo evento sin coordinación centralizada
  • Los productores no deben esperar a que los consumidores procesen
  • Necesitas auditabilidad completa de lo que ocurrió y cuándo
  • Los consumidores tienen disponibilidades distintas
  • El volumen de eventos supera la capacidad de procesamiento síncrono
No usar EDA cuando
  • Necesitas respuesta síncrona inmediata (checkout de e-commerce simple)
  • El equipo no tiene experiencia con sistemas de mensajería
  • El debugging de flujos asíncronos es prohibitivo con el equipo actual
  • La consistencia transaccional entre servicios es requerida estrictamente
  • El dominio es simple y no justifica la complejidad añadida
CQRS Y EVENT SOURCING: EL PODER Y EL PRECIO

CQRS y Event Sourcing son frecuentemente adoptados juntos, pero son patrones independientes. Cada uno tiene un costo significativo que debe justificarse.

CQRS — Cuándo vale la pena
  • Read/write ratio extremadamente asimétrico (99:1)
  • Los modelos de lectura y escritura son fundamentalmente diferentes
  • Necesitas proyecciones especializadas para reporting
  • Quieres escalar lectura y escritura independientemente
  • Equipo familiarizado con el patrón — curva de aprendizaje real
Event Sourcing — Precio que pagas
  • El esquema de eventos es inmutable — evolucionar es complejo
  • Las proyecciones deben reconstruirse — puede tomar horas
  • No puedes "corregir" datos — solo puedes compensar con nuevos eventos
  • Queries sobre estado actual requieren proyecciones precalculadas
  • El debugging requiere "replay" del historial de eventos

Microservicios: Lo que Nadie te Dice

La taxonomía de servicios importa más que la descomposición

No basta con dividir. Cada servicio necesita un owner claro, un contrato de API versionado, su propio pipeline CI/CD, y un runbook. Sin esto, los microservicios son monolitos distribuidos — lo peor de ambos mundos.

El distributed monolith

Si tus "microservicios" deben desplegarse juntos, comparten base de datos, o una llamada falla en cascada por todos — tienes un monolito distribuido con toda la complejidad de microservicios y ninguna de sus ventajas.

El costo de la red es real

Una llamada in-process: ~microsegundos. Una llamada HTTP entre servicios: 1-10ms. Un flujo de 10 servicios encadenados síncronamente: 10-100ms de overhead adicional solo por la red.

Observabilidad no es opcional

En un monolito, el stack trace te dice exactamente qué falló. En microservicios, sin distributed tracing configurado desde el día uno, debuggear un fallo cross-service puede tomar horas.

Event-Driven Architecture: Profundidad Real

EDA es el estilo más poderoso y más malentendido. La mayoría de los equipos adoptan "eventos" sin entender los tres modelos fundamentales que existen dentro de EDA.


  Los 3 Modelos de Event-Driven Architecture

  ┌─────────────────────────────────────────────────────────────────────┐
  │  1. EVENT NOTIFICATION                                              │
  │     "Algo ocurrió, quien quiera puede enterarse"                    │
  │     Emisor no sabe quién consume. Bajo acoplamiento.                │
  │     Problema: el estado completo no está en el evento.              │
  │     Uso: notificaciones, cambios de estado simples                  │
  │                                                                     │
  │     OrderService ──[OrderPlaced: {orderId: 123}]──► Notif. Service  │
  │                                                 └──► Inventory Svc  │
  ├─────────────────────────────────────────────────────────────────────┤
  │  2. EVENT-CARRIED STATE TRANSFER                                    │
  │     El evento lleva todo el estado necesario                        │
  │     Consumers son autónomos: no necesitan hacer queries adicionales │
  │     Problema: eventos grandes, versionado complejo                  │
  │     Uso: replicación de datos entre servicios                       │
  │                                                                     │
  │     OrderService ──[OrderPlaced: {orderId, userId, items,           │
  │                      total, address, ...}]──► Analytics Service     │
  │                                                                     │
  ├─────────────────────────────────────────────────────────────────────┤
  │  3. EVENT SOURCING                                                  │
  │     Los eventos SON la fuente de verdad. El estado se deriva.       │
  │     Problema: complejidad operacional muy alta.                     │
  │     Uso: auditoría completa, reconstitución temporal                │
  │                                                                     │
  │     Event Store: [OrderCreated, ItemAdded, Discounted, Confirmed]   │
  │     Estado actual = replay de todos los eventos                     │
  └─────────────────────────────────────────────────────────────────────┘

Serverless: El Modelo Mental Correcto

Serverless no es "sin servidores" — es "sin gestión de servidores". El modelo mental correcto es pensar en funciones como unidades de billing y escalado, no como unidades de lógica de negocio.

Serverless ideal para
  • Procesamiento de imágenes/archivos al subir
  • Webhooks de terceros (Stripe, GitHub, Twilio)
  • ETL pipelines con carga variable
  • Scheduled jobs / cron tasks
  • Backends de prototipos y MVPs
  • APIs con tráfico muy esporádico
Serverless problemático cuando
  • Latencia p99 es crítica (cold start 100-2000ms)
  • Workload continuo de alta frecuencia (más caro que VMs)
  • Transacciones de larga duración (>15 min)
  • Estado complejo entre invocaciones
  • Debugging intensivo necesario en producción
  • Necesitas vendor lock-in mínimo

Anti-patterns Críticos por Estilo

Estilo Anti-pattern Consecuencia real Solución
Microservicios Shared database entre servicios Acoplamiento de datos, imposible escalar independientemente, schema migrations afectan todos Database-per-service. Datos compartidos vía eventos o API calls
Event-Driven Events como comandos disfrazados Acoplamiento implícito. El productor asume comportamiento del consumidor Eventos describen hechos ("OrderPlaced"), no comandos ("ProcessPayment")
CQRS CQRS sin necesidad real Complejidad doble sin beneficio. Dos modelos que mantener Aplicar solo cuando Read y Write models divergen significativamente
Hexagonal Ports sin abstracción real Boilerplate sin beneficio. El framework sigue penetrando el dominio Los ports deben ser interfaces del dominio, no wrappers del framework
Serverless Funciones con demasiada lógica Testing difícil, cold starts largos, debugging imposible Funciones delgadas que orquestan; lógica en librerías testeables
Monolito Modular Módulos con dependencias circulares Imposible extraer a servicios. Mismo problema que el monolito no modular Dependency rules estrictas. Módulo A no puede depender de módulo B si B depende de A
Modelos relacionados

Los estilos arquitectónicos no existen en aislamiento. Microservicios naturalmente adoptan Event-Driven para comunicación async. CQRS con Event Sourcing forma un par clásico. Hexagonal y Clean Architecture son la estructura interna de cualquier servicio, independientemente del estilo macroscópico. El Solutions Architect diseña la combinación correcta para el contexto específico.

Perspectiva complementariaAnti-patterns de Estilos Arquitectónicos
Distributed Monolith

Microservicios con coupling tan fuerte que deben desplegarse juntos. Lo peor de ambos mundos: complejidad de microservicios sin sus beneficios. Origen: boundaries mal definidos o shared database.

Event-Driven Spaghetti

Sistema event-driven sin documentación de qué eventos existen, quién los produce y quién los consume. El flujo de negocio se vuelve imposible de rastrear. Requiere un event catalog desde el inicio.

CQRS everywhere

Aplicar CQRS a todos los bounded contexts cuando solo uno o dos lo justifican. Añade complejidad de eventual consistency donde no se necesita.

Nano-services

Microservicios tan pequeños que cada función es un servicio. La comunicación entre servicios domina el tiempo de procesamiento real. Señal: servicios que nunca se despliegan solos.

Serverless Monolith

Una función Lambda con 50MB de código que hace todo. Sin beneficios de serverless: cold starts destructivos, timeouts problemáticos, debugging imposible.

Shared Database Antipattern

Múltiples servicios que comparten la misma base de datos y el mismo esquema. El acoplamiento a nivel de datos es más fuerte que el acoplamiento a nivel de API.

Modelos relacionados

La selección de estilo arquitectónico está directamente informada por los Bounded Contexts de DDD (cada BC es un candidato a servicio/módulo), por Conway's Law (el estilo debe mapear a la estructura del equipo), y por los Fallacies of Distributed Computing (que penalizan la sobre-descomposición).

Perspectiva complementariaOtra forma de plantear este capítulo

Los estilos arquitectónicos no son tecnologías ni frameworks — son respuestas a contextos específicos. El error más común de los arquitectos junior es elegir un estilo por su popularidad o por lo que usa una empresa de referencia. El SA senior elige el estilo que mejor resuelve las constraints específicas del problema.

Esta sección no es un catálogo de definiciones — es una guía de cuándo cada estilo es la respuesta correcta, cuándo no lo es, y cómo evolucionan los sistemas entre estilos a lo largo del tiempo.
