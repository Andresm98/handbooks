Arquitectura Monolítica

Una aplicación monolítica es una unidad desplegable única donde todos los componentes (UI, lógica de negocio, acceso a datos) están acoplados en un solo proceso. Es el punto de partida natural de la mayoría de los sistemas.


  ┌─────────────────────────────────────────┐
  │           MONOLITO                       │
  │  ┌───────────────────────────────────┐  │
  │  │      UI / Presentación            │  │
  │  ├───────────────────────────────────┤  │
  │  │      Lógica de Negocio            │  │
  │  ├───────────────────────────────────┤  │
  │  │      Acceso a Datos / DAL         │  │
  │  └──────────────────┬────────────────┘  │
  └─────────────────────┼───────────────────┘
                        │
               ┌────────▼────────┐
               │   Base de Datos │
               │    Única (SQL)  │
               └─────────────────┘
Cuándo usar
  • Proyectos nuevos o MVPs
  • Equipos pequeños (< 10 desarrolladores)
  • Dominio del problema no bien definido
  • Aplicaciones de baja escala
Cuándo evitar
  • Equipos grandes con ownership distribuido
  • Necesidad de escalar componentes independientemente
  • Ciclos de despliegue frecuentes
  • Alta carga o tráfico variable

Microservicios

Descompone la aplicación en servicios pequeños, autónomos y enfocados en un dominio específico. Cada servicio tiene su propia base de datos, puede desplegarse de forma independiente y se comunica a través de APIs o mensajería.


                      ┌────────────────┐
     Clientes ──────► │  API Gateway   │
                      └───┬────┬───┬───┘
                          │    │   │
               ┌──────────┘    │   └───────────┐
               ▼               ▼               ▼
  ┌────────────────┐  ┌─────────────────┐  ┌────────────────┐
  │  User Service  │  │  Order Service  │  │  Payment Svc   │
  │  DB: PostgreSQL│  │  DB: MongoDB    │  │  DB: PostgreSQL│
  └────────────────┘  └────────┬────────┘  └────────────────┘
                               │
                    ┌──────────▼─────────┐
                    │  Message Broker     │
                    │  (RabbitMQ/Kafka)   │
                    └──────────┬─────────┘
                               │
                    ┌──────────▼─────────┐
                    │  Notification Svc   │
                    │  DB: Redis          │
                    └─────────────────────┘

// Ejemplo: Microservicio de Orders (Go)
// Cada servicio es un binario independiente con su propio main

package main

import (
    "net/http"
    "encoding/json"
)

type OrderService struct {
    db    OrderRepository
    events EventPublisher   // Comunicación async
}

// Handler HTTP - interfaz de entrada del servicio
func (s *OrderService) CreateOrder(w http.ResponseWriter, r *http.Request) {
    var req CreateOrderRequest
    json.NewDecoder(r.Body).Decode(&req)

    order, err := s.db.Save(Order{
        UserID: req.UserID,
        Items:  req.Items,
        Status: "PENDING",
    })
    if err != nil {
        http.Error(w, err.Error(), 500)
        return
    }

    // Publica evento para otros servicios (pago, notificaciones)
    s.events.Publish("order.created", order)
    json.NewEncoder(w).Encode(order)
}

func main() {
    svc := &OrderService{
        db:     NewPostgresRepository(),
        events: NewKafkaPublisher("kafka:9092"),
    }
    http.HandleFunc("/orders", svc.CreateOrder)
    http.ListenAndServe(":8080", nil)   // Puerto dedicado
}
Cuándo usar
  • Equipos grandes con ownership por dominio
  • Necesidad de escalar componentes independientemente
  • Tecnologías diversas por servicio
  • Alta disponibilidad como requisito crítico
Cuándo evitar
  • Dominio del problema no definido aún
  • Equipos sin experiencia en sistemas distribuidos
  • Cuando la latencia de red importa criticamente
  • Proyectos con presupuesto de operaciones reducido

Serverless (FaaS)

En una arquitectura serverless, los desarrolladores escriben funciones individuales que el proveedor cloud ejecuta bajo demanda, escalando automáticamente y cobrando solo por el tiempo de ejecución real.

AWS Lambda

Funciones en Node, Python, Go, Java. Hasta 15 minutos de ejecución. Triggers via API GW, S3, DynamoDB, SQS.

Google Cloud Functions

Integración nativa con Firebase, Pub/Sub, BigQuery. Ideal para pipelines de datos y webhooks.

Azure Functions

Deep integration con el ecosistema Microsoft. Durable Functions para workflows complejos. 

# Función AWS Lambda: Procesamiento de imagen tras upload a S3
import boto3
import json
from PIL import Image
import io

def handler(event, context):
    s3 = boto3.client('s3')

    # Trigger automático cuando se sube un archivo a S3
    bucket = event['Records'][0]['s3']['bucket']['name']
    key    = event['Records'][0]['s3']['object']['key']

    # Descargar imagen original
    response = s3.get_object(Bucket=bucket, Key=key)
    image = Image.open(response['Body'])

    # Generar thumbnail
    image.thumbnail((300, 300))
    buffer = io.BytesIO()
    image.save(buffer, format='JPEG', quality=85)

    # Guardar thumbnail en bucket de salida
    s3.put_object(
        Bucket=f"{bucket}-thumbs",
        Key=key,
        Body=buffer.getvalue(),
        ContentType='image/jpeg'
    )

    return {"statusCode": 200, "processed": key}
# BILLING: Solo se cobra por los milisegundos de ejecución real

Cold Start: Las funciones serverless sufren latencia adicional (~100ms–2s) cuando no han sido invocadas recientemente. Para APIs críticas de baja latencia, considerar provisioned concurrency o contenedores.

Event-Driven Architecture (EDA)

Los componentes del sistema se comunican emitiendo y consumiendo eventos, en lugar de llamadas síncronas directas. Desacopla productores de consumidores, permitiendo escalabilidad y extensibilidad independiente.


  PRODUCER                   BROKER                    CONSUMERS
  ┌─────────────┐            ┌──────────┐            ┌──────────────┐
  │ Order Svc   │──evento──► │          │──evento──► │ Payment Svc  │
  │             │            │  Kafka / │            └──────────────┘
  │             │            │  RabbitMQ│──evento──► ┌──────────────┐
  │             │            │          │            │ Notif. Svc   │
  └─────────────┘            │  Topics  │──evento──► └──────────────┘
  ┌─────────────┐            │  /Queues │            ┌──────────────┐
  │ Inventory   │──evento──► │          │            │ Analytics    │
  └─────────────┘            └──────────┘            └──────────────┘

  Clave: Los productores NO conocen a los consumidores

SOA – Service-Oriented Architecture

Precursor de los microservicios. Organiza la lógica de negocio en servicios reutilizables de grano grueso que se comunican mediante un Enterprise Service Bus (ESB). Común en sistemas empresariales legados.

Aspecto SOA Microservicios
Tamaño del servicio Grano grueso (módulo de negocio) Grano fino (función específica)
Comunicación ESB centralizado, SOAP/WS-* REST/gRPC, mensajería directa
Base de datos Compartida entre servicios Una por servicio
Despliegue Suele desplegarse en conjunto Totalmente independiente
Adopción típica Grandes corporaciones, ERP Tech companies, startups

Hexagonal (Ports & Adapters) y Clean Architecture

Ambas arquitecturas buscan el mismo objetivo: aislar el dominio de negocio de los detalles de infraestructura (base de datos, framework web, APIs externas). La diferencia está en la terminología y el nivel de detalle.


  HEXAGONAL (Ports & Adapters)
  ┌─────────────────────────────────────────────────┐
  │   Adapters (Driving)         Adapters (Driven)  │
  │  ┌──────────────┐           ┌──────────────────┐│
  │  │ REST API     │           │ PostgreSQL Repo   ││
  │  │ CLI          │  ┌──────┐ │ Redis Cache       ││
  │  │ Kafka Event  ├─►│DOMAIN│◄┤ SMTP Email        ││
  │  │ gRPC         │  │CORE  │ │ Stripe Payment    ││
  │  └──────────────┘  └──────┘ └──────────────────┘│
  │      Driving Ports     Driven Ports              │
  └─────────────────────────────────────────────────┘
  
  CLEAN ARCHITECTURE (Capas concéntricas)
            ┌─────────────────────────────────┐
            │         Frameworks & Drivers    │ ← DB, UI, External
            │  ┌───────────────────────────┐  │
            │  │   Interface Adapters      │  │ ← Controllers, Gateways
            │  │  ┌─────────────────────┐  │  │
            │  │  │   Use Cases (App)    │  │  │ ← Business rules
            │  │  │  ┌───────────────┐  │  │  │
            │  │  │  │   Entities    │  │  │  │ ← Enterprise rules
            │  │  │  └───────────────┘  │  │  │
            │  │  └─────────────────────┘  │  │
            │  └───────────────────────────┘  │
            └─────────────────────────────────┘
  Regla: Las dependencias apuntan HACIA ADENTRO siempre

// Clean Architecture - Capa de Dominio (sin dependencias externas)

// ENTITY: Reglas de negocio empresariales
class Order {
  constructor(
    private id: OrderId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}

  confirm(): void {
    if (this.items.length === 0) throw new Error("Order must have items");
    this.status = OrderStatus.CONFIRMED;
  }

  total(): Money {
    return this.items.reduce((acc, item) => acc.add(item.subtotal()), Money.zero());
  }
}

// USE CASE: Orquesta entidades y define flujo de la app
class ConfirmOrderUseCase {
  constructor(
    private orderRepo: OrderRepository,    // Puerto (interfaz)
    private eventBus: EventBus             // Puerto (interfaz)
  ) {}

  async execute(orderId: string): Promise {
    const order = await this.orderRepo.findById(orderId);
    order.confirm();
    await this.orderRepo.save(order);
    await this.eventBus.publish(new OrderConfirmedEvent(order));
    // Sin dependencia de HTTP, DB, o framework. Solo dominio.
  }
}

CQRS y Event Sourcing

COMMAND QUERY RESPONSIBILITY SEGREGATION (CQRS)

Separa el modelo de lectura del modelo de escritura. Los Commands modifican el estado; las Queries lo consultan. Permite optimizar cada lado de forma independiente.


  Cliente
    │
    ├──[Command: CreateOrder]──► Command Handler ──► Write DB (normalizada)
    │                                                    │
    │                                             Event: OrderCreated
    │                                                    │
    │                                             ┌──────▼──────────┐
    │                                             │  Projector      │
    │                                             │ (Event Handler) │
    │                                             └──────┬──────────┘
    │                                                    │
    └──[Query: GetOrders]────► Query Handler ◄──── Read DB (desnormalizada,
                                                         optimizada para lectura)

EVENT SOURCING

En lugar de almacenar el estado actual, se almacenan todos los eventos que llevaron a ese estado. El estado actual se reconstruye reproduciendo la cadena de eventos.

// Event Store: Historial inmutable de eventos para una Order
