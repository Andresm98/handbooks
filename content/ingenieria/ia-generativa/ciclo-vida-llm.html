Un modelo como los que consumes vía API pasa por varias fases de entrenamiento. Cada una le da capacidades y también le deja sesgos que vas a ver en producción. Entenderlas te permite anticipar comportamientos —por qué responde con seguridad algo falso, por qué tiende a darte la razón, por qué un modelo "de razonamiento" tarda más y cuesta distinto— y elegir mejor dónde intervenir: en el prompt, en el contexto o en un ajuste del modelo.

Evaluación y despliegue

1. Pre-entrenamiento: el modelo base

Se entrena al modelo a predecir el siguiente token sobre un corpus enorme (web, libros, código, datos licenciados). Así adquiere gramática, conocimiento factual, patrones de razonamiento y estilos. El resultado es un modelo base: completa texto de forma plausible, pero no está diseñado para seguir instrucciones ni para conversar.

  • Fecha de corte (knowledge cutoff): el conocimiento queda congelado en la fecha de los datos. Lo posterior solo puede llegar por contexto (RAG, herramientas).
  • Conocimiento paramétrico difuso: el modelo "recuerda" estadísticamente, no como una base de datos. Hechos raros o muy específicos se reconstruyen de forma plausible pero inexacta: esa es la raíz de muchas alucinaciones.

2. Ajuste supervisado (SFT / instruction tuning)

Se continúa el entrenamiento con ejemplos de alta calidad de instrucción → respuesta ideal, escritos o curados por personas. El modelo aprende el formato de un asistente: responder la pregunta, seguir el formato pedido, usar herramientas con el esquema esperado.

3. Alineamiento con preferencias

Sesgos que deja el alineamiento Complacencia: tendencia a confirmar lo que el usuario parece creer; formula preguntas neutrales ("¿es correcto X?" en lugar de "confirma que X"). Sobre-confianza estilística: el tono seguro no indica exactitud; exige citas. Rechazos: algunos temas legítimos pueden activar negativas; los proveedores exponen el motivo (p. ej. un stop_reason de rechazo) y tu código debe manejarlo.

4. Modelos de razonamiento y cómputo en inferencia

Una generación reciente de modelos se entrena con refuerzo sobre tareas verificables (matemáticas, código con pruebas, problemas con respuesta comprobable) para que produzcan un proceso de razonamiento antes de la respuesta final. A esto se le llama escalar el cómputo en tiempo de inferencia: el modelo "piensa más" a cambio de más tokens y más latencia.

  • Las APIs exponen controles para ese esfuerzo (por ejemplo, un nivel de effort o un modo de razonamiento adaptativo). Más esfuerzo mejora tareas difíciles; en tareas simples solo encarece.
  • Los tokens de razonamiento se facturan aunque no siempre se muestren completos al cliente.
  • Para agentes de larga duración, el razonamiento entre llamadas a herramientas mejora la planificación y la recuperación de errores.

5. Evaluación, red teaming y despliegue

Antes de publicarse, los modelos se evalúan en benchmarks de capacidad, pruebas de seguridad y red teaming (equipos que intentan provocar comportamientos dañinos). Los proveedores publican model cards o system cards con capacidades, limitaciones y resultados. Para un arquitecto, la model card es lectura obligatoria antes de aprobar un modelo para un caso regulado.

Modelos cerrados y de pesos abiertos

Modelos vía API (cerrados)

  • Mayor capacidad en la frontera, sin operar infraestructura.
  • Pago por token, límites de tasa, dependencia del proveedor.
  • Los datos salen de tu perímetro: revisa retención, región de procesamiento y acuerdos contractuales.

Modelos de pesos abiertos

  • Control total: self-hosting, fine-tuning profundo, despliegue on-premise o aislado.
  • Costo de GPUs y operación; capacidad típicamente por detrás de la frontera.
  • Revisa la licencia: "abierto" no siempre significa uso comercial sin restricciones.
Dónde intervenir

Si el problema es de conocimiento (no sabe algo, o algo cambió) la solución es contexto: RAG o herramientas. Si el problema es de comportamiento (formato, tono, criterio de una tarea estrecha que se repite millones de veces) puede justificarse un ajuste del modelo. Si el problema es de capacidad (la tarea es demasiado difícil) cambia de modelo o descompón la tarea. Confundir estos tres diagnósticos es el error más caro del área.
