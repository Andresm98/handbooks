El frontend es el único lugar del stack donde el código se ejecuta en un entorno que no controlas: el navegador del usuario. Con CPU variable, conexión variable, sistema operativo variable, y el usuario haciendo cosas que nunca anticipaste. Diseñar para esta incertidumbre es el arte central del frontend engineering.

El Navegador como Plataforma Real


  Cómo el Navegador Renderiza una Página: El Critical Rendering Path

  HTML recibido
      │
      ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │  PARSING HTML → DOM Tree                                        │
  │  Bloqueado por: <script> sin async/defer (parser blocking)      │
  ├──────────────────────────────────────────────────────────────────┤
  │  PARSING CSS → CSSOM Tree                                       │
  │  Bloqueado por: stylesheets no cargados                         │
  ├──────────────────────────────────────────────────────────────────┤
  │  DOM + CSSOM → Render Tree (solo nodos visibles)                │
  ├──────────────────────────────────────────────────────────────────┤
  │  LAYOUT (Reflow): calcular posición y tamaño de cada elemento   │
  │  Costoso: triggereado por cambios de dimensiones                │
  ├──────────────────────────────────────────────────────────────────┤
  │  PAINT: rellenar píxeles en capas                               │
  ├──────────────────────────────────────────────────────────────────┤
  │  COMPOSITE: combinar capas en la imagen final (GPU)             │
  └──────────────────────────────────────────────────────────────────┘

  Propiedades que solo triggean Composite (más baratas):
  transform, opacity → animarlas es smooth (60fps)

  Propiedades que triggean Layout (caras):
  width, height, top, left, margin → causan reflow completo

  Propiedades que triggean Paint (medias):
  color, background, box-shadow → repinta sin recalcular layout

// Layout thrashing: el error de performance más común en JS

// ❌ Fuerza reflow en cada iteración — O(n) reflows
const elements = document.querySelectorAll('.item')
elements.forEach(el => {
  const height = el.offsetHeight   // Lee → fuerza reflow
  el.style.height = (height * 2) + 'px'  // Escribe → invalida layout
  // En el siguiente .offsetHeight, el browser DEBE recalcular
  // antes de devolver el valor → thrashing
})

// ✓ Batch reads, then batch writes — un solo reflow
const elements = document.querySelectorAll('.item')
// Fase 1: leer todos los valores (un solo reflow)
const heights = [...elements].map(el => el.offsetHeight)
// Fase 2: escribir todos los valores (un solo repaint)
elements.forEach((el, i) => {
  el.style.height = (heights[i] * 2) + 'px'
})

// ✓ Para animaciones: requestAnimationFrame + CSS transforms
function animateElement(el: HTMLElement, distance: number) {
  let start: number
  function step(timestamp: number) {
    if (!start) start = timestamp
    const progress = Math.min((timestamp - start) / 300, 1)
    // transform: solo Composite — no reflow ni repaint
    el.style.transform = `translateX(${progress * distance}px)`
    if (progress < 1) requestAnimationFrame(step)
  }
  requestAnimationFrame(step)
}

Estado: El Problema Central del Frontend

La mayoría de los bugs de frontend son bugs de estado: la UI muestra algo que no refleja la realidad, o dos partes de la UI muestran estados inconsistentes. Gestionar el estado con disciplina es la habilidad más importante del frontend engineer.


  Tipos de Estado y Dónde Vivirlos

  ┌────────────────────────────────────────────────────────────────┐
  │  Estado LOCAL (useState, signals)                              │
  │  • Estado UI: ¿está abierto el dropdown? ¿qué tab es activa?  │
  │  • Solo importa a un componente o árbol pequeño               │
  │  • No compartir en global si no es necesario                   │
  ├────────────────────────────────────────────────────────────────┤
  │  Estado de SERVIDOR (React Query, SWR, TanStack Query)         │
  │  • Datos que viven en el backend                               │
  │  • Tienen cache, loading, error states automáticos             │
  │  • NO duplicar en Redux/Zustand — eso es el error más común   │
  │  • Invalidación automática tras mutaciones                     │
  ├────────────────────────────────────────────────────────────────┤
  │  Estado GLOBAL de UI (Zustand, Jotai, Redux Toolkit)           │
  │  • Tema, idioma, usuario autenticado, notificaciones           │
  │  • Solo lo que realmente necesita ser global                   │
  │  • Redux para: estado complejo con muchas transiciones         │
  │  • Zustand para: estado simple compartido entre componentes    │
  ├────────────────────────────────────────────────────────────────┤
  │  Estado en URL (query params, route params)                    │
  │  • Filtros, búsquedas, paginación, estado de modales           │
  │  • Permite compartir y bookmarkear el estado de la app         │
  │  • Subestimado — debería usarse mucho más                      │
  └────────────────────────────────────────────────────────────────┘

  Error más común: poner TODO en Redux/estado global
  cuando el 80% debería ser estado de servidor o local.

// TanStack Query: estado de servidor correcto
// En lugar de: useEffect + useState + loading + error + refetch manual

// ❌ El patrón que todos escriben y que tiene 10 bugs sutiles
function UserProfile({ userId }: { userId: string }) {
  const [user, setUser] = useState<User | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<Error | null>(null)

  useEffect(() => {
    setLoading(true)
    fetchUser(userId)
      .then(setUser)
      .catch(setError)
      .finally(() => setLoading(false))
  }, [userId])
  // Bugs: stale closure, race condition si userId cambia,
  // no hay cache, no hay refetch, no hay retry automático
}

// ✓ TanStack Query: cache, loading, error, retry, refetch — todo incluido
function UserProfile({ userId }: { userId: string }) {
  const { data: user, isLoading, error } = useQuery({
    queryKey: ['user', userId],          // Cache key
    queryFn: () => fetchUser(userId),
    staleTime: 5 * 60 * 1000,            // 5 min frescos
    retry: 3,                              // 3 reintentos automáticos
  })

  if (isLoading) return <UserSkeleton />
  if (error)     return <ErrorBoundary error={error} />
  return <UserCard user={user} />
}

// Mutación con invalidación automática del cache
function UpdateUserForm({ userId }: { userId: string }) {
  const queryClient = useQueryClient()
  const mutation = useMutation({
    mutationFn: (data: UpdateUserDTO) => updateUser(userId, data),
    onSuccess: () => {
      // Invalida el cache → refetch automático del perfil
      queryClient.invalidateQueries({ queryKey: ['user', userId] })
    }
  })
}

Performance Frontend: Lo que Realmente Importa

Métrica Qué mide Objetivo Cómo mejorarla
FCP — First Contentful Paint Cuándo el usuario ve algo < 1.8s Server-side rendering, critical CSS inline, preload fonts
LCP — Largest Contentful Paint Cuándo carga el elemento principal < 2.5s Optimizar imágenes, CDN, preload LCP image
CLS — Cumulative Layout Shift Cuánto se mueve el contenido < 0.1 Dimensiones en imágenes/videos, skeleton screens
INP — Interaction to Next Paint Responsividad a interacciones < 200ms Debounce, web workers, code splitting, avoid long tasks
TTFB — Time to First Byte Tiempo de respuesta del servidor < 800ms CDN, SSR/SSG, edge functions, caching

Conexión técnica

El frontend engineering conecta con Backend Engineering a través del diseño de API: una API que devuelve exactamente los campos que el frontend necesita (no más, no menos) es la diferencia entre un FCP de 1s y de 4s. Los patrones de estado de servidor (TanStack Query) implementan los mismos principios de caching y eventual consistency que los sistemas distribuidos del backend.
