Las bases de datos son el componente más crítico y más mal entendido del stack. Un modelo de datos incorrecto, un índice que falta, o una transacción mal diseñada pueden hacer que un sistema que funciona perfectamente con 1,000 usuarios colapse con 100,000. El conocimiento de bases de datos es lo que más distingue a un senior de un mid engineer.

Indexing Real: Más Allá de "Añadir un Índice"


  Cómo funciona un B-Tree Index (el más común)

  Tabla: users (10M filas)
  Columna: email (sin índice)

  SELECT * FROM users WHERE email = 'john@example.com'
  → Full table scan: leer las 10M filas = ~5-10 segundos

  Con índice B-Tree en email:
  → O(log n) lookups: ~3-4 niveles de árbol = microsegundos

  Estructura B-Tree:
                    [M-S]
                   /     \
            [E-J]           [T-Z]
           /     \           /    \
       [A-D]   [F-I]    [J-P]   [U-Z]
         │       │         │       │
      leaf     leaf      leaf    leaf
    pages     pages     pages   pages
      │         │         │       │
    ROWIDs    ROWIDs    ROWIDs  ROWIDs
  (punteros a las filas reales en el heap)

  B-Tree es eficiente para: =, >, <, >=, <=, BETWEEN, LIKE 'prefix%'
  B-Tree NO ayuda para: LIKE '%suffix', funciones sobre la columna

-- Índices que realmente marcan la diferencia

-- 1. Índice compuesto: el orden importa enormemente
-- Query: WHERE user_id = 123 AND status = 'active' ORDER BY created_at DESC
-- Índice correcto: (user_id, status, created_at)
-- Regla: columnas de equality primero, range/sort al final
CREATE INDEX idx_orders_user_status_date
    ON orders (user_id, status, created_at DESC);

-- 2. Índice parcial: indexar solo las filas relevantes
-- Si el 95% de las órdenes están 'completed', solo indexar 'pending'
CREATE INDEX idx_orders_pending
    ON orders (created_at)
    WHERE status = 'pending';
-- 20x más pequeño y más rápido que indexar toda la tabla

-- 3. Covering index: el índice contiene todo lo que la query necesita
-- La query NO necesita ir al heap (Index Only Scan)
CREATE INDEX idx_users_email_covering
    ON users (email) INCLUDE (id, name, plan);
-- SELECT id, name, plan FROM users WHERE email = ?
-- → Resuelto completamente desde el índice, sin tocar la tabla

-- 4. EXPLAIN ANALYZE: siempre antes de añadir/eliminar un índice
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, o.total, u.email
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'pending'
  AND o.created_at > NOW() - '24 hours'::interval;

-- Buscar en el output:
-- "Seq Scan" en tabla grande → candidato a índice
-- "Rows Removed by Filter" alto → el índice no es selectivo
-- "Buffers: shared hit=X read=Y" → X en caché, Y leyó disco (malo si Y alto)
-- "actual time" vs "estimated rows" → si muy diferente, falta ANALYZE

Transacciones: Isolation Levels que Importan

Las transacciones no son solo "ACID o no ACID". Los isolation levels permiten elegir el nivel de protección según el caso de uso — con el trade-off entre consistencia y concurrencia.

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Cuándo usar
READ UNCOMMITTED Posible Posible Posible Casi nunca — solo dashboards de analytics aproximados
READ COMMITTED No Posible Posible Default en PostgreSQL — adecuado para la mayoría de operaciones
REPEATABLE READ No No Posible Reportes financieros que necesitan snapshot consistente
SERIALIZABLE No No No Transferencias bancarias, inventario con stock crítico 
-- Caso real: transferencia bancaria que requiere SERIALIZABLE
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Leer saldo actual
SELECT balance FROM accounts WHERE id = :from_account;
-- En READ COMMITTED: otro TX podría cambiar el saldo AQUÍ
-- y este TX no lo sabría hasta el COMMIT
-- En SERIALIZABLE: se detecta el conflicto y se hace rollback

UPDATE accounts SET balance = balance - :amount WHERE id = :from_account;
UPDATE accounts SET balance = balance + :amount WHERE id = :to_account;

COMMIT; -- Si hay conflicto serializable → ERROR, el cliente reintenta

-- ─────────────────────────────────────────────────────────
-- Deadlocks: cómo evitarlos sistemáticamente
-- TX1: UPDATE accounts WHERE id = 1, luego WHERE id = 2
-- TX2: UPDATE accounts WHERE id = 2, luego WHERE id = 1
-- → Deadlock garantizado si ocurren concurrentemente

-- Solución: SIEMPRE acceder a recursos en el mismo orden
-- Ordenar los IDs antes de la transacción:
-- ids = sorted([from_id, to_id])  → siempre en el mismo orden
-- UPDATE accounts WHERE id = ids[0] ... WHERE id = ids[1]
-- → Deadlock matemáticamente imposible

Migraciones sin Downtime: La Habilidad que Más Importa en Producción


  Expand-Contract Pattern: El único patrón seguro

  OBJETIVO: Renombrar columna 'user_name' a 'full_name' en 50M filas

  ❌ Forma naive (causa downtime):
  ALTER TABLE users RENAME COLUMN user_name TO full_name;
  → Bloquea la tabla durante la migración
  → En 50M filas: puede tomar minutos → downtime total

  ✓ Expand-Contract (zero downtime):

  FASE 1 — EXPAND (añadir nueva columna):
  ALTER TABLE users ADD COLUMN full_name VARCHAR(255);
  → No bloquea. La columna empieza NULL.
  → Deploy del código que escribe en AMBAS columnas
     (user_name Y full_name simultáneamente)

  FASE 2 — BACKFILL (migrar datos existentes):
  UPDATE users SET full_name = user_name
    WHERE full_name IS NULL
    LIMIT 1000;  ← en batches, no todo de una vez
  → Ejecutar en background, sin bloquear la tabla

  FASE 3 — SWITCH (el código lee de full_name):
  → Deploy del código que solo lee full_name
  → Verificar que nada usa user_name ya

  FASE 4 — CONTRACT (eliminar la columna vieja):
  ALTER TABLE users DROP COLUMN user_name;
  → Ahora sí es seguro — nadie la usa

  Total de downtime: CERO
  Tiempo total: días o semanas, pero sin impacto en usuarios

# Backfill en batches — nunca migrar millones de filas de una vez
async def backfill_full_name(batch_size: int = 1000):
    """
    Migra datos en batches pequeños para:
    - No bloquear la tabla
    - Poder pausar y reanudar
    - No llenar el WAL de PostgreSQL
    - No causar spike de carga en la BD
    """
    last_id = 0
    total_migrated = 0

    while True:
        # Batch: solo filas pendientes (full_name NULL) y en orden
        rows = await db.fetch(
            """UPDATE users
               SET full_name = user_name
               WHERE id IN (
                 SELECT id FROM users
                 WHERE full_name IS NULL AND id > $1
                 ORDER BY id LIMIT $2
               )
               RETURNING id""",
            last_id, batch_size
        )
        if not rows:
            break  # Backfill completo

        last_id = max(row['id'] for row in rows)
        total_migrated += len(rows)

        # Pausa entre batches: dar respiro a la BD
        await asyncio.sleep(0.05)

        logger.info(f"Migrated {total_migrated} rows, last_id={last_id}")

    logger.info(f"Backfill complete: {total_migrated} total rows")
Conexión técnica

El conocimiento de bases de datos es transversal a toda la arquitectura. Los isolation levels implementan los principios de ACID que distinguen bases relacionales de NoSQL. El Expand-Contract pattern es la materialización técnica del principio Open/Closed aplicado al schema. Los índices compuestos implementan la lógica de acceso que define el diseño de las queries CQRS.
