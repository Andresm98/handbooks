Junior SQL esencial y T-SQL básico

JOINs — tipos y cuándo usar cada uno
INNER · LEFT · RIGHT · FULL OUTER · CROSS

INNER JOIN: solo filas que tienen coincidencia en ambas tablas. LEFT JOIN: todas las filas de la izquierda, con NULL donde no hay coincidencia en la derecha. El tipo más usado en la práctica. RIGHT JOIN: igual pero al revés (evitable reescribiendo como LEFT). FULL OUTER JOIN: todos los registros de ambas tablas.

T-SQL
-- INNER JOIN: solo clientes que tienen pedidos SELECT c.Nombre, COUNT(p.Id) AS TotalPedidos FROM Clientes c INNER JOIN Pedidos p ON c.Id = p.ClienteId GROUP BY c.Nombre; -- LEFT JOIN: TODOS los clientes, con 0 si no tienen pedidos SELECT c.Nombre, COUNT(p.Id) AS TotalPedidos FROM Clientes c LEFT JOIN Pedidos p ON c.Id = p.ClienteId GROUP BY c.Nombre; -- Encontrar clientes SIN pedidos (anti-join) SELECT c.Nombre FROM Clientes c LEFT JOIN Pedidos p ON c.Id = p.ClienteId WHERE p.Id IS NULL; -- filas sin coincidencia
Stored Procedures y funciones
sp · UDF · TVF · parámetros de salida

Los Stored Procedures son bloques de T-SQL compilados en el servidor. Las funciones escalares devuelven un valor; las funciones de tabla (TVF) devuelven un conjunto de filas y son muy útiles para reutilizar lógica de consulta.

T-SQL
-- Stored Procedure con parámetros
CREATE OR ALTER PROCEDURE usp_GetOrdersByClient
    @ClienteId  INT,
    @FechaDesde DATE = NULL
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        p.Id,
        p.Total,
        p.FechaCreacion,
        c.Nombre AS Cliente
    FROM Pedidos p
    INNER JOIN Clientes c ON c.Id = p.ClienteId
    WHERE p.ClienteId = @ClienteId
      AND (@FechaDesde IS NULL OR p.FechaCreacion >= @FechaDesde)
    ORDER BY p.FechaCreacion DESC;
END;

-- Table-Valued Function reutilizable
CREATE FUNCTION fn_GetTopProducts(@n INT)
RETURNS TABLE AS RETURN
(
    SELECT TOP (@n) Id, Nombre, Ventas
    FROM Productos
    ORDER BY Ventas DESC
);
💡 Siempre incluye SET NOCOUNT ON en stored procedures para evitar que se envíen mensajes de "N rows affected" innecesarios que pueden afectar el rendimiento.

Mid Índices, transacciones y concurrencia

Índices: Clustered vs Non-Clustered
B-Tree · Seek vs Scan · Include columns · covering index

El Clustered Index determina el orden físico de los datos en disco (solo puede haber uno por tabla; suele ser la PK). Los Non-Clustered Index son estructuras B-Tree separadas que apuntan a la fila. Un Covering Index incluye todas las columnas necesarias para satisfacer una query sin ir a la tabla base (seek eficiente).

T-SQL
-- Non-clustered con included columns (covering index) -- Query frecuente: filtrar por ClienteId, mostrar Total y Fecha CREATE NONCLUSTERED INDEX IX_Pedidos_ClienteId ON Pedidos (ClienteId) INCLUDE (Total, FechaCreacion); -- Las columnas de INCLUDE no son parte del key, -- pero SQL Server las guarda en las hojas del índice, -- evitando un Key Lookup a la tabla base. -- Ver el Execution Plan para diagnosticar SET STATISTICS IO ON; SELECT ClienteId, SUM(Total) FROM Pedidos WHERE ClienteId = 42 GROUP BY ClienteId; -- Buscar: Index Seek (bueno) vs Table Scan (malo) -- Índice filtrado — solo para estados activos CREATE NONCLUSTERED INDEX IX_Pedidos_Activos ON Pedidos (FechaCreacion) WHERE Estado = 'Activo'; -- mucho más pequeño
💡 Demasiados índices ralentizan los INSERT/UPDATE/DELETE porque todos deben actualizarse. Cada índice tiene un costo de mantenimiento. Crea índices basados en queries reales, no por intuición.
Transacciones y niveles de aislamiento
ACID · READ COMMITTED · SNAPSHOT · Deadlock

ACID garantiza integridad: Atomicity (todo o nada), Consistency (reglas siempre válidas), Isolation (transacciones no se interfieren), Durability (lo guardado persiste). Los niveles de aislamiento controlan qué tan estricta es esa I: más estricto = más consistencia pero más bloqueos.

T-SQL
-- READ COMMITTED (default): lee solo datos confirmados
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- SNAPSHOT: lecturas consistentes sin bloquear escrituras
-- Requiere habilitarlo en la DB primero:
ALTER DATABASE MiDB SET ALLOW_SNAPSHOT_ISOLATION ON;
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

-- Transacción explícita para operaciones múltiples
BEGIN TRANSACTION;
BEGIN TRY
    UPDATE CuentaBancaria SET Saldo -= 100 WHERE Id = 1;
    UPDATE CuentaBancaria SET Saldo += 100 WHERE Id = 2;
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    THROW;
END CATCH;
⚠️ Los deadlocks ocurren cuando dos transacciones se esperan mutuamente. Solución: acceder siempre a las tablas en el mismo orden, mantener transacciones cortas, y habilitar SNAPSHOT Isolation para lecturas.
CTEs y Window Functions
WITH · ROW_NUMBER · RANK · LAG/LEAD · PARTITION BY

Las CTEs (Common Table Expressions) hacen las queries más legibles dividiéndolas en partes nombradas. Las Window Functions calculan sobre un conjunto de filas relacionadas sin colapsar el resultado como GROUP BY.

T-SQL
-- CTE para query legible
WITH PedidosPorCliente AS (
    SELECT ClienteId, SUM(Total) AS TotalAnual
    FROM  Pedidos
    WHERE YEAR(FechaCreacion) = 2024
    GROUP BY ClienteId
),
Ranking AS (
    SELECT *, RANK() OVER (ORDER BY TotalAnual DESC) AS Posicion
    FROM  PedidosPorCliente
)
SELECT c.Nombre, r.TotalAnual, r.Posicion
FROM  Ranking r
JOIN  Clientes c ON c.Id = r.ClienteId
WHERE r.Posicion <= 10;

-- Window function: comparar con mes anterior
SELECT
    Mes,
    Ventas,
    LAG(Ventas) OVER (ORDER BY Mes) AS VentasMesAnterior,
    Ventas - LAG(Ventas) OVER (ORDER BY Mes) AS Diferencia
FROM VentasMensuales;

Senior Query tuning y diseño escalable

Execution Plans — leer e interpretar
Table Scan · Index Seek · Key Lookup · Estimated vs Actual

El Execution Plan muestra cómo SQL Server ejecuta una query. Los operadores se leen de derecha a izquierda, arriba a abajo. El grosor de las flechas indica el volumen de datos. Los warnings (iconos amarillos) señalan problemas. Estimated rows vs Actual rows: una gran diferencia indica estadísticas desactualizadas.

T-SQL
-- Ver plan estimado (no ejecuta)
SET SHOWPLAN_XML ON;

-- Ver plan real (ejecuta la query)
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Query que genera Key Lookup (problema)
SELECT Nombre, Email, Telefono
FROM Clientes
WHERE Ciudad = 'Madrid';
-- Si Ciudad tiene índice pero Email/Telefono no están incluidas,
-- habrá un Key Lookup por cada fila — caro.

-- Solución: Covering Index
CREATE INDEX IX_Clientes_Ciudad ON Clientes(Ciudad)
INCLUDE (Nombre, Email, Telefono);

-- Query Store: ver queries regresadas en performance
SELECT TOP 10 qt.query_sql_text, qs.avg_duration
FROM sys.query_store_query_text qt
JOIN sys.query_store_plan qp ON qt.query_text_id = qp.query_text_id
JOIN sys.query_store_runtime_stats qs ON qp.plan_id = qs.plan_id
ORDER BY qs.avg_duration DESC;
Table Scan = malo Index Seek = bueno Key Lookup = optimizable Hash Match = JOIN sin índice Nested Loop = JOINs pequeños
Parameter Sniffing
plan cache · OPTION RECOMPILE · optimize for unknown

SQL Server compila un plan de ejecución la primera vez que ejecuta un SP, basándose en los parámetros de esa primera llamada. Si esos parámetros son atípicos (ej: un cliente con millones de pedidos cuando la mayoría tiene 10), el plan queda "sniffed" y será malo para el resto de ejecuciones.

T-SQL
-- ❌ Vulnerable a Parameter Sniffing
CREATE PROCEDURE GetPedidosByCliente @ClienteId INT
AS
    SELECT * FROM Pedidos WHERE ClienteId = @ClienteId;

-- ✅ Solución 1: OPTION RECOMPILE (recompila cada vez)
--    Bueno para SPs que varían mucho en distribución
SELECT * FROM Pedidos WHERE ClienteId = @ClienteId
OPTION (RECOMPILE);

-- ✅ Solución 2: Variables locales (rompe el sniffing)
DECLARE @LocalId INT = @ClienteId;
SELECT * FROM Pedidos WHERE ClienteId = @LocalId;

-- ✅ Solución 3: OPTIMIZE FOR UNKNOWN
SELECT * FROM Pedidos WHERE ClienteId = @ClienteId
OPTION (OPTIMIZE FOR (@ClienteId UNKNOWN));
Temporal Tables
system-versioned · historial automático · point-in-time query

Las Temporal Tables (SQL Server 2016+) registran automáticamente el historial de cambios de cada fila. SQL Server mantiene una tabla de historial paralela con las versiones anteriores. Ideal para auditoría, "undo", o consultas de "¿cómo era esto hace 6 meses?"

T-SQL
-- Crear tabla temporal CREATE TABLE Productos ( Id INT PRIMARY KEY, Nombre NVARCHAR(100), Precio DECIMAL(18,2), ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START, ValidTo DATETIME2 GENERATED ALWAYS AS ROW END, PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo) ) WITH (SYSTEM_VERSIONING = ON); -- Consultar estado en un punto del tiempo SELECT * FROM Productos FOR SYSTEM_TIME AS OF '2024-01-01 00:00:00'; -- Ver todos los cambios de un producto SELECT *, ValidFrom, ValidTo FROM Productos FOR SYSTEM_TIME ALL WHERE Id = 42 ORDER BY ValidFrom;

Lead / Arch Alta disponibilidad y arquitectura de datos

Always On Availability Groups
primary · secondary · failover · read scale-out

Los Always On AG son el mecanismo de alta disponibilidad de SQL Server. Un primario sincroniza transacciones con uno o más secundarios. El failover automático mueve el rol primario si el nodo falla. Los secundarios pueden configurarse para lecturas (read scale-out), descargando queries pesadas del primario.

T-SQL · Connection String
-- Monitorear estado del AG SELECT ag.name AS AGNombre, rs.role_desc AS Rol, rs.synchronization_health_desc AS Salud, rs.log_send_queue_size AS ColaSinEnviar_KB FROM sys.dm_hadr_availability_replica_states rs JOIN sys.availability_groups ag ON rs.group_id = ag.group_id; -- Connection String para aplicaciones -- Escribe siempre en primario, lee en secundario Server=tcp:AGListener,1433; Database=MiDB; ApplicationIntent=ReadOnly; -- o ReadWrite MultiSubnetFailover=True; -- failover rápido ConnectTimeout=30;
