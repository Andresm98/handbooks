El código que escribes solo representa una fracción de tu impacto como ingeniero senior. La otra fracción — frecuentemente la más grande — viene de cómo trabajas con otros: qué feedback das, cómo comunicas problemas técnicos, cómo estimas con honestidad, cómo documentas decisiones que otros necesitarán entender en dos años.

Code Reviews que Elevan al Equipo

Un code review tiene dos objetivos simultáneos: mejorar el código del PR y desarrollar al ingeniero que lo escribió. Los reviews que solo logran el primero son revisiones de código. Los que logran ambos son inversiones en el equipo.

  QUÉ REVISAR (por prioridad):

Estimaciones Honestas: La Habilidad más Política

Estimar mal destruye la confianza entre ingenieros y stakeholders. Sobre-estimar crea slack artificial. Sub-estimar produce promesas rotas. La meta no es estimar perfectamente — es ser honesto sobre la incertidumbre.


  Por qué los ingenieros siempre sub-estiman: El Planning Fallacy

  Lo que los ingenieros asumen al estimar:
  • Todo va a funcionar según el plan
  • Las dependencias estarán listas
  • No habrá bugs inesperados
  • No habrá interrupciones (meetings, reviews, preguntas)
  • El código existente es como lo recuerdo
  • Los requerimientos no van a cambiar

  Lo que realmente ocurre:
  • La API de terceros tiene un comportamiento no documentado
  • El schema de BD necesita una migración no anticipada
  • Los requirements cambian a mitad de implementación
  • Los code reviews piden cambios significativos
  • Hay un bug en producción que requiere atención urgente

  Técnica de estimación honesta: Three-Point Estimation
  ┌─────────────────────────────────────────────────────────┐
  │  O = Optimista: todo sale perfecto (10%)               │
  │  M = Más probable: condiciones normales (60%)          │
  │  P = Pesimista: murphy's law activo (30%)              │
  │                                                         │
  │  Estimación = (O + 4M + P) / 6                         │
  │                                                         │
  │  Ejemplo: "Integrar el sistema de pagos"               │
  │  O = 3 días, M = 8 días, P = 20 días                   │
  │  Estimación = (3 + 32 + 20) / 6 = 9.2 días            │
  │                                                         │
  │  Comunicar como rango: "Entre 8 y 15 días, más         │
  │  probable cerca de 9. El riesgo principal es la        │
  │  documentación incompleta del proveedor de pagos."     │
  └─────────────────────────────────────────────────────────┘

CÓMO COMUNICAR RETRASOS: LA CONVERSACIÓN DIFÍCIL



**Contexto:** [Qué se está construyendo y para cuándo se prometió]

**Situación actual:** Al investigar el sistema de pagos más en profundidad,
encontramos que [problema específico]. Esto añade trabajo no anticipado.

**Nueva estimación:** La fecha original era [fecha]. La nueva estimación
más probable es [nueva fecha], con [X días de delta].

**Por qué cambia:** [Causa específica y honesta — no excusas vagas]
- La API de Stripe tiene rate limits que requieren implementar backoff
- El modelo de datos existente necesita una migración adicional

**Opciones:** Para mantener la fecha original, podemos:
1. Reducir el scope: [qué feature podemos cortar sin impacto crítico]
2. Añadir recurso: [qué persona adicional podría ayudar con qué parte]
3. Aceptar el retraso: [impacto real en el negocio de esperar X días más]

¿Cuál prefieren?

Documentación que se Lee

La documentación que nadie lee no existe. La documentación que produce valor tiene tres características: está cerca del código que describe, responde preguntas que alguien realmente tiene, y tiene un dueño que la mantiene actualizada.

README: La puerta de entrada

Qué hace este proyecto en una línea. Cómo correrlo en 5 minutos. Las decisiones de arquitectura principales. Los links a la documentación extendida. Si el README no está actualizado, nada lo estará.

ADRs: Por qué las cosas son como son

Architecture Decision Records documentan el razonamiento de las decisiones importantes. "¿Por qué usamos MongoDB aquí?" La respuesta está en el ADR, con el contexto del momento en que se tomó la decisión.

Comentarios de código: El por qué, no el qué

El código dice qué hace. Los comentarios dicen por qué. Si el código necesita un comentario para explicar qué hace, probablemente necesita un refactor. Si necesita explicar por qué hace algo no obvio, el comentario es invaluable.

Anti-pattern: Wiki graveyard

Una wiki con 500 páginas donde el 80% está desactualizado. Peor que no tener documentación: da respuestas incorrectas con apariencia de corrección. Mejor: menos documentación, toda actualizada.

Conexión técnica

Las habilidades de equipo son las que determinan si las buenas prácticas técnicas — Clean Code, TDD, diseño de API — se adoptan consistentemente o solo cuando el autor tiene tiempo. Los code reviews son el mecanismo de difusión de conocimiento técnico. Las estimaciones honestas son la interface entre el equipo técnico y las decisiones de negocio. Sin estas habilidades, el conocimiento técnico queda atrapado en silos.
