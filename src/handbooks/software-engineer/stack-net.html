Tipos de valor vs. Tipos de referencia
value types · reference types · stack vs heap

Los value types (int, bool, struct, enum) viven en el stack y se copian al asignarse. Los reference types (class, string, arrays) viven en el heap y la variable guarda una referencia. Esto afecta el comportamiento al pasar parámetros y comparar igualdad.

Stack: memoria rápida y ordenada (LIFO). Heap: memoria dinámica gestionada por el GC. Los value types en el stack no tienen overhead de GC.
C#
// Value type — se copia
int a = 10;
int b = a;
b = 20;
Console.WriteLine(a); // 10 — no cambia

// Reference type — apuntan al mismo objeto
var lista1 = new List<int> { 1, 2, 3 };
var lista2 = lista1;
lista2.Add(4);
Console.WriteLine(lista1.Count); // 4 — sí cambia

// Struct (value type personalizado)
struct Punto { public int X, Y; }
Punto p1 = new() { X = 1, Y = 2 };
Punto p2 = p1; // copia completa
💡 Usa record struct en .NET 6+ para value types inmutables con igualdad por valor automática. Ideal para coordenadas, money, IDs tipados.
async / await y el modelo de tareas
Task · async/await · no bloquear el thread

async/await permite escribir código asíncrono con sintaxis síncrona. Task representa una operación que puede completarse en el futuro. El objetivo es liberar el thread mientras espera I/O (base de datos, HTTP, disco) en lugar de bloquearlo.

C#
// ❌ Bloqueante — ocupa el thread esperando
public Usuario ObtenerUsuario(int id)
{
    return _db.Usuarios.FirstOrDefault(u => u.Id == id);
}

// ✅ Asíncrono — libera el thread
public async Task<Usuario?> ObtenerUsuarioAsync(int id)
{
    return await _db.Usuarios
        .FirstOrDefaultAsync(u => u.Id == id);
}

// Llamar múltiples tareas en paralelo
var (usuario, pedidos) = await (
    ObtenerUsuarioAsync(id),
    ObtenerPedidosAsync(id)
).WhenAll();  // ambas en paralelo
⚠️ Nunca uses .Result o .Wait() en código async — puede causar deadlocks en ASP.NET. Siempre propaga el await hacia arriba.
Inyección de Dependencias (DI)
IoC container · Transient · Scoped · Singleton

La DI desacopla clases de sus dependencias. En lugar de que OrderService cree su propio EmailService, el contenedor lo inyecta. ASP.NET Core tiene un contenedor incorporado que gestiona el ciclo de vida: Transient (nueva instancia por uso), Scoped (una por request HTTP), Singleton (una por toda la vida de la app).

C# · Program.cs
// Registro en el contenedor
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<IEmailSender, SmtpEmailSender>();
builder.Services.AddTransient<IValidator<OrderDto>, OrderValidator>();

// Consumo vía constructor
public class OrderController(IOrderService orderService) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Create(OrderDto dto)
    {
        var result = await orderService.CreateAsync(dto);
        return Ok(result);
    }
}
💡 Regla de oro: Scoped para casi todo (servicios, repos). Singleton solo para estado compartido thread-safe (cache, config). Transient para objetos ligeros sin estado.
LINQ — Language Integrated Query
IEnumerable · deferred execution · method syntax

LINQ permite consultar colecciones e IQueryable (EF Core) con sintaxis fluida. Tiene ejecución diferida: la query no se ejecuta hasta que iteras el resultado (ToList(), FirstOrDefault()). Sobre IQueryable se traduce a SQL; sobre IEnumerable se ejecuta en memoria.

C#
// Sobre IEnumerable (en memoria)
var productos = _productos
    .Where(p => p.Precio > 100)
    .OrderByDescending(p => p.Precio)
    .Select(p => new { p.Nombre, p.Precio })
    .Take(10)
    .ToList();

// Sobre IQueryable (genera SQL)
var query = _db.Pedidos
    .Where(p => p.FechaCreacion >= DateTime.Today.AddDays(-30))
    .Include(p => p.Items)
    .GroupBy(p => p.ClienteId)
    .Select(g => new {
        ClienteId = g.Key,
        Total = g.Sum(p => p.Total),
        Cantidad = g.Count()
    });

// La query aún no ejecuta — solo al llamar ToList()
var resultado = await query.ToListAsync();

Mid Patrones, arquitectura y Entity Framework

Clean Architecture
Domain · Application · Infrastructure · Presentation

Organiza el código en capas concéntricas donde las dependencias solo apuntan hacia adentro. El dominio no conoce nada externo. La aplicación orquesta casos de uso. La infraestructura implementa interfaces del dominio. La presentación (API) es el punto de entrada.

C# · Estructura de proyecto
// Domain/Entities/Order.cs — sin dependencias externas
public class Order
{
    public Guid Id { get; private set; }
    public Money Total { get; private set; }
    private readonly List<OrderItem> _items = [];

    public void AddItem(Product product, int qty)
    {
        if (qty <= 0) throw new DomainException("Qty inválida");
        _items.Add(new OrderItem(product, qty));
        Total = _items.Sum(i => i.Subtotal);
    }
}

// Application/UseCases/CreateOrder/CreateOrderCommand.cs
public record CreateOrderCommand(Guid ClienteId, List<OrderItemDto> Items)
    : IRequest<OrderDto>;

// Infrastructure/Persistence/OrderRepository.cs
public class OrderRepository(AppDbContext db) : IOrderRepository
{
    public async Task SaveAsync(Order order) =>
        await db.SaveChangesAsync();
}

Entity Framework Core — avanzado
Change Tracker · N+1 · AsNoTracking · Owned entities

El problema N+1 ocurre cuando una query carga N entidades y luego hace 1 query adicional por cada una para cargar relaciones. Solución: Include(). Para queries de solo lectura, AsNoTracking() elimina el overhead del Change Tracker (~30% más rápido).

C#
// ❌ Problema N+1 — 1 query + N queries de Items
var ordenes = await _db.Orders.ToListAsync();
foreach (var o in ordenes)
    Console.WriteLine(o.Items.Count); // lazy load por cada orden

// ✅ Eager loading — 1 query con JOIN
var ordenes = await _db.Orders
    .Include(o => o.Items)
        .ThenInclude(i => i.Product)
    .AsNoTracking()   // sin change tracking
    .ToListAsync();

// Owned Entity — value object en EF Core
public class Order
{
    public Address ShippingAddress { get; set; }  // Owned
}
// En DbContext:
modelBuilder.Entity<Order>().OwnsOne(o => o.ShippingAddress);
💡 Usa AsNoTracking() en todas las queries de lectura (GET endpoints). Solo omítelo cuando vayas a modificar las entidades cargadas.
Middleware Pipeline en ASP.NET Core
Use · Run · Map · orden importa

El pipeline es una cadena de middlewares que procesan cada request en orden. Cada middleware puede procesar la request, pasarla al siguiente (next()), o cortocircuitar la cadena. El orden de registro es crítico: Authentication debe ir antes de Authorization.

C# · Program.cs
// Orden correcto del pipeline
app.UseExceptionHandler("/error");  // 1. Siempre primero
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthentication();            // 2. Auth antes que Authz
app.UseAuthorization();
app.MapControllers();

// Middleware personalizado
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);  // pasa al siguiente
    _logger.LogInformation("Request: {ms}ms", sw.ElapsedMilliseconds);
});

Senior CQRS, performance y diseño robusto

CQRS + MediatR
Command · Query · Handler · PipelineBehavior

CQRS (Command Query Responsibility Segregation) separa operaciones de escritura (Commands) de lectura (Queries). MediatR implementa el patrón Mediator: en lugar de llamar servicios directamente, lanzas un mensaje y el Handler apropiado lo procesa. Los PipelineBehaviors son middlewares para tus handlers (validación, logging, retry).

C#
// Command — escribe, devuelve resultado
public record CreateProductCommand(
    string Nombre, decimal Precio) : IRequest<Guid>;

// Handler
public class CreateProductHandler(
    IProductRepository repo) : IRequestHandler<CreateProductCommand, Guid>
{
    public async Task<Guid> Handle(
        CreateProductCommand cmd, CancellationToken ct)
    {
        var product = Product.Create(cmd.Nombre, cmd.Precio);
        await repo.AddAsync(product, ct);
        return product.Id;
    }
}

// PipelineBehavior — validación automática
public class ValidationBehavior<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var errors = validators
            .Select(v => v.Validate(request))
            .SelectMany(r => r.Errors)
            .ToList();
        if (errors.Count > 0)
            throw new ValidationException(errors);
        return await next();
    }
}
Result Pattern — sin excepciones para flujos de negocio
Result<T> · Error · Railway-oriented

Las excepciones son costosas (generan stack traces) y no deben usarse para flujo de negocio esperado (ej: "usuario no encontrado"). El Result Pattern retorna explícitamente éxito o error, haciendo el contrato del método honesto y el código más legible.

C#
// Tipo Result genérico
public record Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public Error? Err { get; }

    public static Result<T> Ok(T value) => new(value, null);
    public static Result<T> Fail(Error error) => new(default, error);
}

// Uso en un servicio
public async Task<Result<UserDto>> GetUserAsync(int id)
{
    var user = await _repo.FindAsync(id);
    if (user is null)
        return Result<UserDto>.Fail(Errors.UserNotFound);
    return Result<UserDto>.Ok(_mapper.Map<UserDto>(user));
}

// En el controller — mapeo a HTTP
var result = await _mediator.Send(new GetUserQuery(id));
return result.IsSuccess ? Ok(result.Value) : NotFound(result.Err);
Performance: Span<T> y reducción de allocations
Span · stackalloc · object pooling · GC pressure

Span<T> es una vista sobre memoria existente (array, stack, memoria nativa) sin copiarla. Reduce drásticamente las allocations en hot paths, disminuyendo la presión sobre el GC y mejorando la latencia en código de alto rendimiento.

C#
// ❌ Crea un string intermedio en heap
string input = "2024-01-15";
int year = int.Parse(input.Substring(0, 4));

// ✅ Zero allocation — Span es solo una vista
int year = int.Parse(input.AsSpan(0, 4));

// Object Pool — reutilizar objetos costosos
private readonly ObjectPool<StringBuilder> _pool =
    new DefaultObjectPool<StringBuilder>(new StringBuilderPooledObjectPolicy());

public string BuildMessage(IEnumerable<string> parts)
{
    var sb = _pool.Get();
    try
    {
        foreach (var p in parts) sb.Append(p);
        return sb.ToString();
    }
    finally { _pool.Return(sb); }
}
💡 Usa BenchmarkDotNet para medir antes de optimizar. Las optimizaciones prematuras son costosas. Mide primero con [MemoryDiagnoser] para ver allocations reales.

Outbox Pattern — mensajes confiables
exactly-once · at-least-once · transactional outbox

El problema: guardar en DB y publicar un evento en un bus de mensajes no es atómico. Si el sistema falla entre los dos, el evento se pierde. La solución: guardar el evento dentro de la misma transacción en una tabla Outbox, y un proceso separado lo publica al bus.

C#
// 1. Guardar orden + mensaje en la misma transacción
await using var tx = await _db.BeginTransactionAsync();

_db.Orders.Add(order);
_db.OutboxMessages.Add(new OutboxMessage
{
    Type = "OrderCreated",
    Payload = JsonSerializer.Serialize(new OrderCreatedEvent(order.Id)),
    CreatedAt = DateTime.UtcNow
});

await _db.SaveChangesAsync(); // atómico
await tx.CommitAsync();

// 2. Worker publica mensajes pendientes (Background Service)
var pending = await _db.OutboxMessages
    .Where(m => m.PublishedAt == null)
    .OrderBy(m => m.CreatedAt)
    .Take(50)
    .ToListAsync();

foreach (var msg in pending)
{
    await _bus.PublishAsync(msg.Type, msg.Payload);
    msg.PublishedAt = DateTime.UtcNow;
}
await _db.SaveChangesAsync();
⚠️ El Outbox garantiza at-least-once delivery. Los consumidores deben ser idempotentes (procesar el mismo mensaje dos veces debe ser seguro).
Circuit Breaker con Polly
resiliencia · retry · fallback · timeout

El patrón Circuit Breaker protege un servicio de cascada de fallos: si un servicio downstream falla repetidamente, el circuito se "abre" y las siguientes llamadas fallan rápido en lugar de esperar el timeout. Polly es la librería estándar para esto en .NET.

C# · Polly v8 / Microsoft.Extensions.Http.Resilience
// Configuración de resiliencia para HttpClient builder.Services.AddHttpClient<IPaymentService, PaymentService>() .AddResilienceHandler("payment-pipeline", pipeline => { pipeline.AddRetry(new HttpRetryStrategyOptions { MaxRetryAttempts = 3, Delay = TimeSpan.FromMilliseconds(200), BackoffType = DelayBackoffType.Exponential }); pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions { FailureRatio = 0.5, // abre si 50% falla SamplingDuration = TimeSpan.FromSeconds(30), MinimumThroughput = 10, // mínimo de calls para evaluar BreakDuration = TimeSpan.FromSeconds(60) }); pipeline.AddTimeout(TimeSpan.FromSeconds(5)); });
