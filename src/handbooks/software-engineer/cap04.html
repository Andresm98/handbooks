El backend es el sistema nervioso de cualquier aplicación. Diseñarlo bien significa entender el protocolo sobre el que opera, gestionar el estado de forma predecible, manejar la concurrencia sin race conditions, y fallar de maneras informativas y recuperables.

HTTP: El Protocolo que Todo Backend Habla


  HTTP Request-Response: Lo que realmente ocurre

  Lo que muchos backends ignoran:
  • Connection: keep-alive — reutilizar conexiones TCP (HTTP/1.1 default)
  • ETag — permitir conditional requests (304 Not Modified)
  • X-Request-Id — tracing de requests entre servicios
  • Cache-Control — qué puede cachear el cliente/CDN

STATUS CODES: USARLOS CORRECTAMENTE IMPORTA

Código Cuándo usarlo Error común
200 OK Request exitoso con respuesta Usarlo para errores de negocio con body de error
201 Created Recurso creado exitosamente (POST) Retornar 200 en vez de 201 para creaciones
204 No Content Éxito sin cuerpo de respuesta (DELETE) Retornar 200 con body vacío
400 Bad Request Error de validación del cliente Usarlo para errores de servidor
401 Unauthorized No autenticado (sin token o token inválido) Confundirlo con 403
403 Forbidden Autenticado pero sin permiso Retornar 404 para ocultar que el recurso existe
404 Not Found Recurso no encontrado Retornar 400 cuando es realmente un 404
409 Conflict Estado del recurso en conflicto con el request No usarlo para duplicados — es exactamente para eso
422 Unprocessable Validación semántica fallida (campos válidos pero inconsistentes) Confundirlo con 400
429 Too Many Requests Rate limit excedido Retornar 503 cuando es un rate limit del cliente
500 Internal Error Error inesperado del servidor Exponer detalles del error interno al cliente
503 Unavailable Servicio temporalmente no disponible Retornar 500 cuando el servicio está en mantenimiento planificado

Autenticación y Autorización: Conceptos Diferentes

Autenticación responde "¿quién eres?". Autorización responde "¿qué puedes hacer?". Confundirlos es uno de los errores de seguridad más comunes.

# Implementación completa de JWT auth en FastAPI
from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
import bcrypt

SECRET_KEY = "env-variable-never-hardcoded"
ALGORITHM  = "HS256"

def hash_password(plain: str) -> str:
    # bcrypt: auto-salted, trabajo configurable, resistente a rainbow tables
    return bcrypt.hashpw(plain.encode(), bcrypt.gensalt(rounds=12)).decode()

def verify_password(plain: str, hashed: str) -> bool:
    return bcrypt.checkpw(plain.encode(), hashed.encode())
    # bcrypt es timing-safe por diseño — evita timing attacks

def create_access_token(user_id: str, roles: list[str]) -> str:
    payload = {
        "sub":   user_id,
        "roles": roles,
        "iat":   datetime.now(timezone.utc),
        "exp":   datetime.now(timezone.utc) + timedelta(minutes=15),
        # Access token corto (15 min). Refresh token largo en httpOnly cookie.
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def require_permission(permission: str):
    """Decorator de autorización basado en permisos"""
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, current_user: User = Depends(get_current_user), **kwargs):
            # AUTENTICACIÓN: get_current_user valida el JWT
            # AUTORIZACIÓN: verificar si tiene el permiso específico
            if permission not in current_user.permissions:
                raise HTTPException(
                    status_code=403,
                    detail=f"Permission '{permission}' required"
                )
            return await func(*args, current_user=current_user, **kwargs)
        return wrapper
    return decorator

# Uso: separación clara entre autenticación y autorización
@router.delete("/users/{user_id}")
@require_permission("users:delete")
async def delete_user(user_id: str, current_user: User = Depends()):
    await user_service.delete(user_id)

Concurrencia: Los Problemas que Solo Aparecen en Producción

# Race condition clásica — el problema más silencioso del backend

# ❌ Race condition en actualización de inventario
async def reserve_item(item_id: str, quantity: int):
    item = await db.get_item(item_id)        # Lee stock = 5
    # ← Otro request también lee stock = 5 AQUÍ
    if item.stock < quantity:
        raise InsufficientStockError()
    await db.update_stock(item_id, item.stock - quantity)
    # Ambos requests reservan 3 unidades, stock final = -1 🐛

# ✓ Solución 1: Optimistic locking — detectar conflicto, reintentar
async def reserve_item_optimistic(item_id: str, quantity: int):
    for attempt in range(3):  # Max 3 reintentos
        item = await db.get_item(item_id)
        if item.stock < quantity:
            raise InsufficientStockError()
        updated = await db.update_stock_if_version_matches(
            item_id,
            new_stock=item.stock - quantity,
            expected_version=item.version  # Falla si otro lo modificó
        )
        if updated:
            return  # Éxito
    raise ConcurrentModificationError()

# ✓ Solución 2: Pessimistic locking — SELECT FOR UPDATE
async def reserve_item_pessimistic(item_id: str, quantity: int):
    async with db.transaction():
        # Bloquea la fila — otros requests esperan hasta que esta TX termine
        item = await db.get_item_for_update(item_id)  # SELECT FOR UPDATE
        if item.stock < quantity:
            raise InsufficientStockError()
        await db.update_stock(item_id, item.stock - quantity)
        # Lock liberado al terminar la transacción

# ✓ Solución 3: Atomic operation — sin locks, más escalable
# UPDATE items SET stock = stock - :qty
#   WHERE id = :id AND stock >= :qty
# Retorna rows_affected: si es 0, no había stock suficiente
Conexión técnica

El backend engineering implementa los patrones de la arquitectura de sistemas: las race conditions se resuelven con los mismos principios de ACID que definen las bases de datos relacionales, la autenticación con JWT conecta con Zero Trust y la gestión de identidad, y el diseño de APIs bien versionadas es la base del Strangler Fig Pattern para migraciones incrementales.
