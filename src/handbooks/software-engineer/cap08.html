La regla de oro de la performance es una: medir antes de optimizar. La optimización prematura no es solo un desperdicio de tiempo — activamente empeora el código al añadir complejidad para resolver problemas que no existen o que no están donde asumes.

"Premature optimization is the root of all evil" — Knuth. El 97% del tiempo, la performance no importa. El 3% que importa, debes medir para saber dónde está. Casi nunca está donde crees que está.

Profiling: Encontrar el Cuello de Botella Real

# Profiling en Python — encontrar dónde está realmente el tiempo
import cProfile, pstats, io

def profile(func):
    """Decorator para profilear cualquier función"""
    def wrapper(*args, **kwargs):
        pr = cProfile.Profile()
        pr.enable()
        result = func(*args, **kwargs)
        pr.disable()

        s = io.StringIO()
        ps = pstats.Stats(pr, stream=s)
        ps.sort_stats('cumulative')
        ps.print_stats(20)  # Top 20 funciones por tiempo acumulado
        print(s.getvalue())
        return result
    return wrapper

#                         el problema estaba en el serializer, no en SQL

Caching: La Complejidad que Nadie Menciona

Phil Karlton dijo que hay dos problemas difíciles en CS: invalidación de caché y nombrar cosas. El caching mejora drásticamente la performance — pero introduce un sistema distribuido adicional con su propio conjunto de failure modes.


  Estrategias de Caching y Sus Trade-offs

  CACHE-ASIDE (más común):
  App → Cache hit? → Retornar
  App → Cache miss → BD → Guardar en cache → Retornar
  Pros: Solo cachea datos leídos, app controla el cache
  Cons: Cache miss = latencia extra, cold start lento

  READ-THROUGH:
  App → Cache (que consulta la BD si necesario) → Retornar
  Pros: Transparente para la app
  Cons: Cache debe soportar la lógica de lectura de BD

  WRITE-THROUGH:
  App → Cache → BD (síncronamente)
  Pros: Cache siempre actualizado
  Cons: Latencia de escritura mayor, cachea datos poco leídos

  WRITE-BEHIND (write-back):
  App → Cache → Retornar inmediatamente
  BD actualizada en batch asíncronamente
  Pros: Escrituras ultra-rápidas
  Cons: Riesgo de pérdida de datos si el cache muere antes del flush

  │  Cache Invalidation: las estrategias reales              │

El Problema N+1: El Bug de Performance más Común

# N+1 query: el problema más costoso y más fácil de introducir

# ❌ N+1: 1 query para los posts + N queries para los autores
# Con 100 posts → 101 queries a la BD
posts = db.query("SELECT * FROM posts LIMIT 100")  # 1 query
for post in posts:
    post.author = db.query(                           # N queries
        "SELECT * FROM users WHERE id = ?", post.author_id
    )

# ✓ Eager loading: 2 queries total, independientemente de N
posts = db.query("SELECT * FROM posts LIMIT 100")
author_ids = [p.author_id for p in posts]
authors = db.query("SELECT * FROM users WHERE id = ANY(?)", author_ids)
author_map = {a.id: a for a in authors}
for post in posts:
    post.author = author_map.get(post.author_id)

# ✓ JOIN: 1 query, lo más eficiente
posts_with_authors = db.query("""
    SELECT p.*, u.name as author_name, u.email as author_email
    FROM posts p
    JOIN users u ON u.id = p.author_id
    LIMIT 100
""")

Conexión técnica

Performance y escalabilidad conectan con todos los niveles del stack. El N+1 se resuelve en la capa de datos, pero se previene en el diseño de la API (GraphQL DataLoader, REST con fields de inclusion). El caching implementa los principios de consistencia eventual de sistemas distribuidos. El profiling muestra que la mayoría de problemas de performance están en la base de datos — haciendo el Capítulo 06 el más importante para el performance del sistema.
