El diseño de software ocurre constantemente, no solo al principio de un proyecto. Cada vez que nombras una función, defines una interfaz, o decides dónde vive un pedazo de lógica — estás diseñando. La diferencia entre un ingeniero que diseña bien y uno que no lo hace no está en el conocimiento de patrones, sino en la capacidad de reconocer qué problema tienen que resolver.

Patrones de Diseño como Soluciones a Problemas Reales

Los patrones de diseño son soluciones reutilizables a problemas recurrentes. El error es aprenderlos como un catálogo a memorizar. El valor está en reconocer el problema que cada patrón resuelve — y solo entonces aplicarlo.

Patrón Problema real que resuelve Señal de que lo necesitas Anti-pattern de aplicación
Strategy Comportamiento intercambiable en runtime sin if/else Tienes un switch/if-else que crece cada vez que añades un tipo Crear Strategy para comportamiento que nunca cambia
Observer Notificar a múltiples componentes sin acoplamiento directo Un cambio en objeto A requiere llamar a B, C, D directamente Observadores con side effects no predecibles ni testeables
Decorator Añadir responsabilidades a un objeto sin modificar su clase Necesitas logging/caching/retry en múltiples implementaciones Cadenas de decoradores tan profundas que el debugging es imposible
Factory Centralizar la lógica de creación de objetos complejos La lógica de crear un objeto está duplicada en múltiples lugares Factory que hace demasiado — viola SRP también
Repository Abstraer el acceso a datos del dominio de negocio SQL/ORM queries dispersas en la lógica de negocio Repository que filtra, ordena, pagina Y hace joins complejos — se convierte en un ORM wrapper
Builder Construir objetos complejos paso a paso Constructor con 7+ parámetros donde el orden importa Builder para objetos simples — añade complejidad sin valor 
// Strategy Pattern — caso real: procesadores de pago

// ❌ Sin Strategy: cada nuevo procesador requiere modificar esta clase
class PaymentService {
  charge(amount: number, provider: string) {
    if (provider === 'stripe') {
      // lógica de Stripe...
    } else if (provider === 'paypal') {
      // lógica de PayPal...
    } else if (provider === 'mercadopago') {
      // lógica de MercadoPago...
    }
    // Cada nuevo procesador = modificar esta clase = riesgo de regresión
  }
}

// ✓ Con Strategy: añadir procesador = añadir clase, sin tocar lo existente
interface PaymentProvider {
  charge(amount: Money, metadata: PaymentMetadata): Promise<PaymentResult>
  refund(transactionId: string): Promise<RefundResult>
}

class StripeProvider implements PaymentProvider { /* ... */ }
class PayPalProvider implements PaymentProvider { /* ... */ }
class MercadoPagoProvider implements PaymentProvider { /* ... */ }

class PaymentService {
  constructor(private provider: PaymentProvider) {}

  async charge(amount: Money, metadata: PaymentMetadata) {
    return this.provider.charge(amount, metadata)
    // Funciona con CUALQUIER provider — presente y futuro
  }
}

API Design: El Contrato Permanente

Una API pública es una decisión arquitectónica irreversible. Una vez que clientes dependen de ella, cambiarla tiene un costo real. El diseño de una API es el trabajo que más durará en el tiempo — más que cualquier implementación subyacente.


  Principios de API Design que Envejecen Bien

  1. NOMBRES COMO RECURSOS, VERBOS COMO ACCIONES HTTP
     ❌ GET /getUser?id=123
     ❌ POST /createOrder
     ✓  GET /users/123
     ✓  POST /orders

  2. VERSIONADO DESDE EL DÍA 1
     ✓  /api/v1/users
     Sin versión = imposible hacer breaking changes sin romper clientes

  3. ERRORES INFORMATIVO Y CONSISTENTES (RFC 7807)
     ❌ HTTP 400 { "error": "bad" }
     ✓  HTTP 422 {
           "type": "https://api.company.com/errors/validation",
           "title": "Validation Failed",
           "detail": "email must be a valid email address",
           "invalid_params": [{"name": "email", "reason": "invalid format"}]
        }

  4. PAGINACIÓN CONSISTENTE
     ✓  GET /users?page=2&per_page=50
        Response: { "data": [...], "meta": { "total": 1234,
                    "page": 2, "per_page": 50, "pages": 25 } }

  5. IDEMPOTENCY KEYS EN OPERACIONES CRÍTICAS
     POST /payments
     Idempotency-Key: client-generated-uuid
     → Si el request falla y se reintenta con la misma key,
       el servidor retorna el resultado original sin re-procesar

  6. BACKWARD COMPATIBILITY
     ✓  Añadir campos opcionales: seguro
     ✓  Deprecar campos (documentar, mantener 1 versión)
     ❌ Renombrar campos existentes: breaking change
     ❌ Cambiar tipo de un campo: breaking change
     ❌ Hacer obligatorio algo que era opcional: breaking change

Abstracciones: El Arte del Equilibrio

Una abstracción correcta oculta complejidad sin ocultar información importante. Una abstracción incorrecta — o prematura — es una de las fuentes más comunes de deuda técnica. Joel Spolsky formuló la Ley de las Abstracciones con Fugas: todas las abstracciones no triviales tienen fugas. 

# Abstracción prematura: el enemigo silencioso

# Inicio del proyecto — dos casos de uso:
def send_welcome_email(user_email: str): ...
def send_password_reset(user_email: str): ...

# ❌ Abstracción prematura — crear un EmailSender genérico
#    con factory, template engine, y 400 líneas "para ser flexible"
#    cuando todavía no sabemos qué variaciones reales necesitaremos

# ✓ Esperar hasta el tercer caso de uso para abstraer
#    La abstracción correcta solo se puede ver con suficientes ejemplos concretos
#    "Make it work, make it right, make it fast" — en ese orden

# Regla: duplicar está permitido UNA vez.
#         Al tercer caso de duplicación, abstraer.
#         Esta es la "Rule of Three" de abstracción.

# ─────────────────────────────────────────────────────────────
# Señales de que una abstracción está MAL:

# 1. Necesita un nombre genérico porque no sabes qué hace
#    Manager, Handler, Processor, Helper, Utils → red flags

# 2. Tiene más de un nivel de indirección innecesario
#    service.getRepository().findById() vs userRepo.findById()

# 3. Los casos de uso concretos necesitan "escapar" de la abstracción
#    if isinstance(repo, PostgresUserRepo):  → abstracción rota

# 4. Es más difícil de entender que el código que reemplaza
#    La abstracción debe REDUCIR la carga cognitiva, no aumentarla
Conexión técnica

El diseño de software es la capa donde los principios arquitectónicos se materializan en código. Hexagonal Architecture se implementa mediante interfaces (puertos) e implementaciones concretas (adapters). DDD se implementa mediante el modelado cuidadoso de entidades, value objects, y bounded contexts en el código. Los patrones de diseño son los bloques de construcción de cualquier arquitectura bien diseñada.
