Layered Architecture / MVC / MVVM

MVC – Model View Controller

  • Model: lógica de negocio y datos
  • View: presentación (HTML, plantillas)
  • Controller: maneja requests, orquesta
  • Usado en: Rails, Django, Laravel, Spring MVC
  • Bidireccional: View puede observar Model

MVVM – Model View ViewModel

  • Model: datos y lógica de negocio
  • View: solo presentación (declarativa)
  • ViewModel: estado de la UI, comandos
  • Usado en: Angular, Vue, SwiftUI, WPF
  • Data binding bidireccional automático

Circuit Breaker, Retry, Timeout y Bulkhead

Patrones de resiliencia para sistemas distribuidos donde los fallos parciales son inevitables.


  CIRCUIT BREAKER — Estados
  
  ┌──────────┐  failures > threshold   ┌──────────┐
  │  CLOSED  │─────────────────────────►  OPEN    │
  │ (normal) │                         │ (fail    │
  │          │◄────────────────────────│  fast)   │
  └──────────┘   success               └─────┬────┘
                                             │ timeout expires
                                      ┌──────▼──────┐
                                      │ HALF-OPEN   │
                                      │ (test call) │
                                      └─────────────┘
  
  BULKHEAD — Aislamiento de recursos (como mamparos de barco)
  ┌─────────────────────────────────────────────────────┐
  │  Thread Pool A (30 threads) │ Thread Pool B (20)    │
  │  → Servicio de Pagos        │ → Servicio de Notif.  │
  │  Si Pagos se satura:        │ Notificaciones sigue  │
  │  no afecta a Notificaciones │ funcionando ✓         │
  └─────────────────────────────┴───────────────────────┘


# Implementación con Resilience4j-style (Python / tenacity)
from tenacity import retry, stop_after_attempt, wait_exponential, CircuitBreaker

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=10),  # Backoff exponencial
    reraise=True
)
async def call_payment_service(order_id: str) -> dict:
    async with asyncio.timeout(5.0):          # Timeout: 5 segundos máximo
        return await payment_client.charge(order_id)

# Circuit Breaker: Abre si >50% de llamadas fallan en 60s
circuit_breaker = CircuitBreaker(
    failure_rate_threshold=50,
    slow_call_rate_threshold=80,
    wait_duration_in_open_state=30,
    permitted_calls_in_half_open_state=3
)

API Gateway

Punto de entrada único para todos los clientes. Centraliza cross-cutting concerns: autenticación, rate limiting, SSL termination, routing, logging y transformación de requests.

Saga Pattern

Gestiona transacciones distribuidas sin bloqueos de dos fases. Define una secuencia de transacciones locales donde cada paso publica un evento, y si falla, ejecuta transacciones compensatorias.

Tipo Descripción Ventaja Desventaja
Choreography Cada servicio reacciona a eventos y publica los suyos Sin punto central de fallo Difícil de rastrear el flujo
Orchestration Un orquestador central coordina los pasos Flujo explícito y trazable El orquestador es punto de fallo

Strangler Fig Pattern

Estrategia para migrar sistemas legacy de forma incremental. Nuevas funcionalidades se construyen como microservicios modernos mientras el monolito va siendo "estrangulado" gradualmente.


  FASE 1: Interceptar         FASE 2: Migrar           FASE 3: Eliminar
  ┌────────────────┐          ┌───────────────┐         ┌──────────────┐
  │   Facade/Proxy  │         │  Facade/Proxy  │         │ New Services │
  │                 │         │       │        │         │ completos    │
  │  Monolito       │         │  New  │Legacy  │         │              │
  │  (todo)     ◄───┤         │  Svc  │(parte) │         │ Monolito     │
  └────────────────┘         └───────────────┘         │ eliminado ✓  │
                                                         └──────────────┘
  Tiempo de migración: meses o años, sin big-bang rewrite

Pub/Sub y Sidecar Pattern

PUB/SUB

Los publicadores emiten mensajes a topics sin conocer a los suscriptores. Los suscriptores reciben solo los mensajes de los topics que les interesan. Implementaciones: Kafka, Google Pub/Sub, AWS SNS/SQS.

SIDECAR PATTERN

Desplegar un proceso auxiliar junto al servicio principal en el mismo pod/host. El sidecar gestiona preocupaciones transversales: logging, mTLS, service mesh (Envoy en Istio), configuración dinámica.


  POD (Kubernetes)
  ┌──────────────────────────────────────────────┐
  │  ┌─────────────────┐   ┌───────────────────┐ │
  │  │  Main Container  │   │  Sidecar (Envoy)  │ │
  │  │                  │   │                   │ │
  │  │  App Business    │◄─►│  mTLS             │ │
  │  │  Logic           │   │  Load Balancing   │ │
  │  │  :8080           │   │  Observability    │ │
  │  └─────────────────┘   │  :9090            │ │
  │                         └───────────────────┘ │
  │  Comparten: red localhost, volúmenes           │
  └──────────────────────────────────────────────┘
  Ventaja: La app no necesita lógica de red/seguridad
