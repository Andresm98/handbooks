Los sistemas agénticos introducen una superficie de riesgo que no existe en software determinista tradicional: el propio modelo es un punto de entrada manipulable. La gobernanza no es una capa opcional añadida al final, es parte del diseño de arquitectura desde el primer ADR.

Riesgos específicos de sistemas con LLM

Prompt injection

Contenido malicioso embebido en documentos, resultados de herramientas o entradas de usuario que intenta alterar las instrucciones del sistema. Especial cuidado en RAG, donde el contenido recuperado es, de facto, entrada no confiable.

Exfiltración de datos vía herramientas

Un agente con herramientas de escritura (email, HTTP) puede ser inducido a enviar datos sensibles fuera del perímetro si no hay validación de las acciones antes de ejecutarlas.

Escalación de privilegios

Herramientas MCP o APIs con permisos más amplios de lo que la tarea del agente requiere. El principio de mínimo privilegio aplica a cada tool, no solo al servicio contenedor.

Alucinación en dominios regulados

Respuestas plausibles pero incorrectas sobre temas normativos o financieros, con impacto directo si no hay un paso de validación o citación de fuente obligatoria.

Prompt injection indirecta: el riesgo central de los agentes

No existe hoy una defensa a nivel de modelo que elimine la prompt injection. Un correo, una página web, un PDF o el resultado de una herramienta pueden contener texto que el modelo interprete como instrucción. Por eso la defensa es arquitectónica: limitar lo que un agente manipulado puede hacer.

La combinación peligrosa ("trifecta letal") ┌──────────────────┐ ┌──────────────────────┐ ┌────────────────────┐ │ Acceso a datos │ │ Exposición a │ │ Capacidad de │ │ privados │ +│ contenido no │ +│ comunicar hacia │ │ (cuentas, CRM) │ │ confiable (web, mail)│ │ afuera (email, URL)│ └──────────────────┘ └──────────────────────┘ └────────────────────┘ Si un agente tiene las tres, un atacante puede hacer que exfiltre datos. Quita al menos una, o pon aprobación humana en el canal de salida.

Controles arquitectónicos

  • Aislamiento de identidad por agente: cada agente o servicio opera bajo su propia identidad gestionada (Entra ID / IAM Role), nunca credenciales compartidas de "la aplicación de IA" en general.
  • Guardrails de entrada y salida: filtrado de contenido antes de que llegue al modelo y validación de la respuesta antes de ejecutar una acción o mostrarla al usuario.
  • Human-in-the-loop obligatorio: cualquier acción irreversible o de alto impacto (transferencias, cambios de configuración, comunicación externa) requiere aprobación explícita, nunca autonomía plena del agente.
  • Segregación de secretos: claves de API y credenciales de herramientas gestionadas vía vault (Key Vault, AWS Secrets Manager), nunca en el system prompt ni en variables de entorno del propio contenedor del agente sin rotación.
  • Sanitización de contenido recuperado: en RAG, tratar cada chunk recuperado como entrada no confiable — no como instrucción del sistema — con separación clara en el prompt entre "datos" y "comandos".
  • Auditoría inmutable: registro de cada decisión del agente (qué se recuperó, qué herramienta se invocó, qué se respondió) en un almacén de solo-append, trazable por AGENT_RUN_ID.

Seguridad y guardrails

  • Prompt injection: los documentos ingestados pueden contener instrucciones maliciosas. Sanitiza el input antes de incluirlo en el contexto del LLM.
  • PII en chunks: implementa detección y redacción de información personal antes de indexar documentos. Usa librerías como Presidio de Microsoft.
  • Rate limiting por usuario: evita abuso y controla costos. Implementa en la API gateway.
  • Output validation: verifica que el output del LLM cumple el schema esperado antes de enviarlo al usuario o usarlo en pasos downstream.
  • Tool call sandboxing: code execution tools deben correr en entornos aislados (Docker, Firecracker) con timeouts y límites de recursos.

Red teaming de sistemas de IA

  • Incluye en el golden dataset casos adversarios: inyecciones en documentos, intentos de extraer el prompt, solicitudes fuera de alcance, intentos de escalar privilegios a través de herramientas.
  • Prueba con datos de otro tenant o de otro usuario para verificar el aislamiento.
  • Repite el red teaming al cambiar de modelo, de herramientas o de fuentes indexadas.
