Las herramientas (tools) son funciones que el LLM puede invocar para interactuar con el mundo externo. El modelo no ejecuta la herramienta directamente: genera una llamada estructurada (tool call) que el sistema de orquestación ejecuta y devuelve el resultado.

Anatomía de una herramienta

{
  "name": "search_documents",
  "description": "Busca en la base de conocimiento interna. Úsala cuando
    necesites información específica de los documentos de la empresa.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "La consulta de búsqueda en lenguaje natural"
      },
      "top_k": {
        "type": "integer",
        "default": 5,
        "description": "Número de resultados a retornar"
      }
    },
    "required": ["query"]
  }
}

Principio clave

La description de una herramienta es literalmente parte del prompt. El modelo la lee para decidir si usar la herramienta. Una descripción ambigua lleva a un uso incorrecto o a no usar la herramienta cuando se necesita.

Diseñar herramientas para un modelo

Una herramienta es una interfaz cuyo usuario es un modelo. Las reglas de buen diseño de APIs siguen valiendo, con matices:

Pocas y con propósito claro

Diez herramientas bien delimitadas superan a cuarenta que se solapan. Si dos herramientas sirven para lo mismo, el modelo dudará.

Orientadas a la tarea

Mejor buscar_cliente_por_documento que exponer un SQL genérico. Menos pasos, menos errores, menos superficie de ataque.

Respuestas compactas

Devuelve lo que el modelo necesita, no el JSON completo de 400 campos. Cada token de resultado ocupa contexto en todos los pasos siguientes.

Errores accionables

"Formato inválido: el ID debe ser TRF- seguido de 8 dígitos" permite corregir; "Error 500" no.

Idempotentes cuando escriben

Acepta una clave de idempotencia: el modelo o el loop pueden reintentar una llamada.

Mínimo privilegio

Cada herramienta con su propia credencial y alcance. Separa las de lectura de las de escritura y marca las irreversibles para aprobación humana.

Model Context Protocol (MCP)

Model Context Protocol (MCP) es un estándar abierto para conectar modelos con herramientas y fuentes de datos externas, de forma similar a como REST estandarizó la comunicación entre servicios web. En vez de escribir un integrador distinto por cada combinación de modelo y herramienta, MCP define una interfaz común.

MCP define una arquitectura cliente–servidor: la aplicación que usa el modelo (el host, por ejemplo un IDE, un asistente de escritorio o tu backend) abre un cliente MCP por cada servidor; cada servidor expone capacidades de un sistema (un gestor de tickets, una base de datos, un repositorio).

Primitivas del servidor

Vigente a la fecha de revisión. La especificación de MCP evoluciona por versiones fechadas; el transporte remoto original basado en HTTP + SSE fue reemplazado por Streamable HTTP. Consulta la versión de la especificación que soportan tu cliente y tus servidores.

Por qué importa arquitectónicamente

  • Desacoplamiento: el proveedor de la herramienta (ej. un sistema interno bancario) expone un servidor MCP una sola vez, y cualquier cliente compatible (Claude, otros LLMs) puede consumirlo.
  • Reutilización entre agentes: el mismo servidor MCP puede ser consumido por múltiples agentes o aplicaciones sin duplicar lógica de integración.
  • Seguridad centralizada: autenticación y control de acceso se implementan una vez en el servidor MCP, en lugar de en cada prompt o integración ad-hoc.

En tu contexto: si Banco Pichincha expone sistemas internos vía MCP, cualquier agente autorizado (interno o de terceros) puede integrarse sin reconstruir la capa de conexión cada vez — el mismo principio que ya aplicaste con el servidor Structurizr en Docker.

A2A: comunicación entre agentes

Mientras MCP conecta un agente con herramientas y datos, el protocolo Agent2Agent (A2A) busca estandarizar la comunicación entre agentes de distintos proveedores o equipos: cada agente publica una "tarjeta" con sus capacidades, y otros le delegan tareas con un ciclo de vida (enviada, en curso, completada) y artefactos de resultado. Es relevante cuando agentes de distintos dominios o empresas deben colaborar sin compartir implementación. Dentro de un mismo sistema, una llamada a sub-agente vía tu orquestador suele ser más simple.

Patrón empresarial Trata los servidores MCP internos como productos de plataforma: un equipo dueño, versionado semántico, autenticación centralizada, logs de auditoría por llamada y un catálogo donde los equipos descubren qué capacidades existen. Es la misma disciplina que un API Gateway, aplicada a herramientas para agentes.
