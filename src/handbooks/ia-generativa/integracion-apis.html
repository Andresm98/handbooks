Este es el capítulo más práctico para el AI Software Engineer: cómo se habla con un modelo desde código de producción. Los ejemplos usan el SDK oficial de Python de Anthropic y la API de Messages porque es el stack de referencia del resto del handbook, pero los conceptos (streaming, herramientas, salidas estructuradas, caché, lotes, errores) existen con nombres parecidos en todos los proveedores. Instala con pip install anthropic; el cliente toma la credencial del entorno (ANTHROPIC_API_KEY), nunca la escribas en el código.

Vigencia de los ejemplos Los identificadores de modelo y algunos parámetros cambian con cada generación. Los ejemplos usan claude-opus-5-5, vigente a la fecha de revisión de este capítulo. Antes de copiar a producción, consulta la lista actual de modelos (la API expone un endpoint models) y la guía de migración del proveedor.

La llamada mínima

import anthropic

client = anthropic.Anthropic()  # lee ANTHROPIC_API_KEY del entorno

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system="Eres un analista de riesgo operativo. Responde en español, en 3 viñetas.",
    messages=[{"role": "user", "content": "¿Qué riesgos tiene permitir transferencias 24/7?"}],
)

# La respuesta es una lista de bloques de contenido: revisa el tipo antes de leer.
for block in response.content:
    if block.type == "text":
        print(block.text)

print(response.stop_reason)            # end_turn | max_tokens | tool_use | refusal ...
print(response.usage.input_tokens, response.usage.output_tokens)Python
  • La API es sin estado: cada request lleva el historial completo que quieres que el modelo vea.
  • Revisa siempre stop_reason antes de usar el contenido: max_tokens significa respuesta cortada; refusal significa que el modelo declinó.
  • Registra usage en cada llamada: es la base de tu modelo de costos.

Streaming

Para interfaces de chat y para cualquier respuesta larga, usa streaming: el usuario ve texto desde el primer token y evitas timeouts HTTP en generaciones extensas.

with client.messages.stream(
    model="claude-opus-5-5",
    max_tokens=64000,
    messages=[{"role": "user", "content": "Redacta el runbook de un incidente de pagos duplicados."}],
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)      # en un backend: reenvía como Server-Sent Events
    final = stream.get_final_message()       # mensaje completo con usage y stop_reasonPython

Salidas estructuradas

Cuando la salida la consume código, define el esquema y deja que la API lo garantice. Con Pydantic, el SDK valida y te devuelve el objeto tipado.

from pydantic import BaseModel
from typing import Literal

class Reclamo(BaseModel):
    categoria: Literal["fraude", "cargo_duplicado", "demora", "otro"]
    monto: float | None
    urgencia: Literal["baja", "media", "alta"]
    resumen: str

response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=16000,
    messages=[{"role": "user", "content": f"Clasifica este reclamo:\n\n{texto_del_cliente}"}],
    output_format=Reclamo,
)
reclamo = response.parsed_output          # instancia validada de Reclamo
if reclamo.categoria == "fraude":
    abrir_caso_prioritario(reclamo)Python

El esquema garantiza la forma; las reglas de negocio (montos válidos, coherencia entre campos) siguen siendo responsabilidad de tu código.

Herramientas (tool use / function calling)

El modelo no ejecuta nada: decide llamar una herramienta y devuelve un bloque tool_use con argumentos. Tu código ejecuta, devuelve un tool_result y repite hasta que el modelo termina. Ese es el loop agéntico en su forma más simple.

import json

TOOLS = [{
    "name": "consultar_estado_transferencia",
    "description": "Devuelve el estado de una transferencia por su ID. Úsala cuando el "
                   "analista pregunte por una transferencia concreta. Solo lectura.",
    "strict": True,  # garantiza que los argumentos cumplan el esquema
    "input_schema": {
        "type": "object",
        "properties": {"transfer_id": {"type": "string", "description": "ID con formato TRF-XXXXXXXX"}},
        "required": ["transfer_id"],
        "additionalProperties": False,
    },
}]

def ejecutar(nombre: str, args: dict) -> str:
    if nombre == "consultar_estado_transferencia":
        return json.dumps(core_bancario.estado(args["transfer_id"]))
    raise ValueError(f"herramienta desconocida: {nombre}")

messages = [{"role": "user", "content": "¿En qué estado está la TRF-00012345?"}]
for paso in range(10):                                   # loop SIEMPRE acotado
    response = client.messages.create(
        model="claude-opus-5-5", max_tokens=16000, tools=TOOLS, messages=messages,
    )
    if response.stop_reason != "tool_use":
        break
    messages.append({"role": "assistant", "content": response.content})
    resultados = []
    for block in response.content:
        if block.type == "tool_use":
            try:
                salida, error = ejecutar(block.name, block.input), False
            except Exception as e:                       # el error vuelve al modelo, no se oculta
                salida, error = f"Error: {e}", True
            resultados.append({"type": "tool_result", "tool_use_id": block.id,
                               "content": salida, "is_error": error})
    messages.append({"role": "user", "content": resultados})  # todos los resultados en UN mensaje

print(next(b.text for b in response.content if b.type == "text"))Python
  • La descripción de la herramienta es parte del prompt: di cuándo usarla, qué devuelve y qué no hace.
  • Devuelve los errores al modelo con is_error: con un mensaje accionable suele corregirse solo.
  • Si el modelo pide varias herramientas en paralelo, ejecútalas y devuelve todos los resultados en un único mensaje.
  • Para no escribir el loop a mano, el SDK ofrece un tool runner que lo gestiona; el loop manual sigue siendo útil para entender el mecanismo y para controles muy específicos.
  • En algunos modelos recientes no se puede forzar el uso de una herramienta concreta: se pide en el prompt y se mantiene strict para garantizar argumentos válidos.

Caché de prompts

Si muchas llamadas comparten un prefijo largo (system prompt, manual de producto, definiciones de herramientas), el caché reutiliza ese procesamiento: la lectura desde caché cuesta una fracción del precio normal de entrada y reduce la latencia del primer token.

response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=16000,
    system=[{
        "type": "text",
        "text": MANUAL_DE_PRODUCTOS,                 # decenas de miles de tokens, estable
        "cache_control": {"type": "ephemeral"},      # marca el fin del prefijo cacheable
    }],
    messages=[{"role": "user", "content": pregunta}],  # lo variable va DESPUÉS
)
print(response.usage.cache_read_input_tokens)       # > 0 en llamadas siguientes = caché funcionandoPython
Invalidadores silenciosos Una fecha u hora en el system prompt, un JSON serializado sin orden de claves fijo, o una lista de herramientas que cambia entre requests rompen la coincidencia de prefijo y el caché nunca acierta. Si cache_read_input_tokens es siempre cero, busca uno de estos.

Procesamiento por lotes

Para cargas que no necesitan respuesta inmediata (clasificar el histórico de reclamos, generar resúmenes nocturnos, evals masivas), la API de lotes procesa de forma asíncrona con un descuento significativo frente a las llamadas síncronas.

Errores, reintentos y rechazos

SituaciónSeñalQué hacer
Límite de tasaHTTP 429Reintentar con backoff exponencial y jitter respetando retry-after; a nivel de sistema, colas y presupuestos por tenant.
Sobrecarga o error del servidorHTTP 5xx / 529Reintentar con backoff; si persiste, fallback a otro modelo o región.
Request inválidoHTTP 400No reintentar: es un bug. Registrar con el request_id.
Respuesta cortadastop_reason = max_tokensSubir max_tokens, usar streaming o pedir salidas más acotadas.
Rechazo del modelostop_reason = refusalNo leer el contenido como respuesta válida; mostrar mensaje controlado, registrar la categoría o usar fallback.
Timeout de redError de conexiónReintentar si la operación es idempotente; para respuestas largas, streaming.
 
import anthropic

client = anthropic.Anthropic(max_retries=3, timeout=120.0)  # el SDK ya reintenta 429/5xx

def responder(pregunta: str) -> str:
    try:
        # Fallback del lado del servidor: si el modelo declina por política,
        # la misma llamada se reintenta en otro modelo según la categoría.
        r = client.beta.messages.create(
            model="claude-opus-5-5",
            max_tokens=16000,
            betas=["server-side-fallback-2026-07-01"],
            fallbacks="default",
            messages=[{"role": "user", "content": pregunta}],
        )
    except anthropic.RateLimitError:
        raise ServicioOcupado()                   # el SDK ya agotó sus reintentos
    except anthropic.APIStatusError as e:
        log.error("llm_error", status=e.status_code, request_id=e.response.headers.get("request-id"))
        raise
    except anthropic.APIConnectionError:
        raise ServicioNoDisponible()

    if r.stop_reason == "refusal":
        return "No puedo ayudar con esa solicitud. Un asesor revisará tu caso."
    if r.stop_reason == "max_tokens":
        log.warning("respuesta_truncada", request_id=r._request_id)
    return "".join(b.text for b in r.content if b.type == "text")Python

Diseño independiente del proveedor

Trata al modelo como cualquier dependencia externa: detrás de un puerto propio (arquitectura hexagonal), con el adaptador de cada proveedor aislado. Así cambiar de modelo o de nube es cambiar un adaptador, no reescribir el dominio.

Dominio (casos de uso) │ usa ▼ Puerto: Generador / Clasificador / Agente ← interfaz propia, tipos propios │ ┌────┴─────────────────┬───────────────────┐ ▼ ▼ ▼ Adaptador API A Adaptador nube B Adaptador self-hosted (SDK oficial) (Bedrock/Vertex/...) (vLLM, Ollama) │ ▼ AI Gateway: auth, cuotas por tenant, caché, trazas, costos, fallback
Ojo con la abstracción excesiva Un "mínimo común denominador" entre proveedores te quita las capacidades diferenciales (caché de prompts, razonamiento, herramientas del servidor, citas). Abstrae en el nivel del caso de uso, no en el de cada parámetro de la API.

Checklist de integración para producción

  • Credenciales desde un gestor de secretos o identidad federada, nunca en código ni en el prompt.
  • Timeouts y reintentos configurados; operaciones con efectos laterales protegidas con idempotencia.
  • Manejo explícito de stop_reason (truncado, herramientas, rechazo).
  • Salidas estructuradas para todo lo que consume código.
  • Streaming en interfaces de usuario y respuestas largas.
  • Caché de prompts verificado con métricas de uso.
  • Trazas por llamada: modelo, versión de prompt, tokens, costo, latencia, request_id.
  • Límites de gasto y de tasa por tenant o por usuario.
