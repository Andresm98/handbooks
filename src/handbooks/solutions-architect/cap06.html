# Deployment de producción con todas las best practices
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payments-service
  namespace: fintech-prod
  labels:
    app: payments
    version: v3.2.1
    team: payments-squad
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0      # Zero-downtime deploy
      maxSurge: 1
  selector:
    matchLabels:
      app: payments
  template:
    spec:
      affinity:
        podAntiAffinity:     # No dos pods en el mismo nodo
          requiredDuringSchedulingIgnoredDuringExecution:
          - topologyKey: kubernetes.io/hostname
      containers:
      - name: payments
        image: registry/payments:v3.2.1
        resources:
          requests:
            cpu: "500m"
            memory: "512Mi"
          limits:            # SIN limit de CPU en producción — causa throttling
            memory: "1Gi"    # Solo limitar memoria para evitar OOM
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
          initialDelaySeconds: 30
          periodSeconds: 10
          failureThreshold: 3
        readinessProbe:      # Diferente al liveness — controla si recibe tráfico
          httpGet: { path: /ready, port: 8080 }
          initialDelaySeconds: 5
          periodSeconds: 5
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:    # Nunca hardcodear secrets
              name: payments-secrets
              key: db-password
      topologySpreadConstraints: # Distribuir entre AZs
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule

Error crítico de producción #1: Poner limits.cpu en Kubernetes causa CPU throttling aunque el nodo tenga CPU disponible. Un servicio que debería responder en 10ms puede tardar 200ms por throttling. En la mayoría de los casos, omitir el CPU limit y usar solo request es la práctica correcta.

Perspectiva complementariaKubernetes en Producción Real

Kubernetes resuelve problemas reales de orquestación de contenedores. También introduce una capa de complejidad operacional significativa. Un SA debe evaluar honestamente si el problema justifica Kubernetes o si una alternativa más simple es superior.

Alternativa Complejidad Casos ideales Limitaciones
AWS ECS + Fargate Baja Startups, equipos pequeños en AWS, microservicios simples Vendor lock-in AWS, menos flexible que K8s
Google Cloud Run Muy baja Servicios HTTP stateless, scaling a cero, GCP Solo HTTP, vendor lock-in GCP
Kubernetes (EKS/GKE/AKS) Alta Equipos >15 ingenieros, multi-cloud, control total Requiere equipo de platform engineering dedicado
Nomad (HashiCorp) Media Organizaciones con Vault/Consul, no solo containers Ecosistema más pequeño que K8s
PaaS (Render, Railway) Muy baja MVPs, proyectos pequeños, developer experience prioritaria Costo mayor a escala, menos control

La trampa de Kubernetes: Organizaciones con <10 servicios y <15 ingenieros que adoptan Kubernetes dedican el 40-60% de la capacidad de ingeniería a operar la plataforma en lugar de construir producto. Considera seriamente ECS o Cloud Run primero. 

# Kubernetes: Deployment de producción con best practices
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
  namespace: production
  labels:
    app: payment-service
    version: "v2.3.1"
    team: "payments"
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0      # Zero downtime: nunca menos de 3 replicas
      maxSurge: 1            # Permite 4 replicas durante el rolling update
  selector:
    matchLabels:
      app: payment-service
  template:
    metadata:
      labels:
        app: payment-service
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/port: "9090"
    spec:
      # Nunca correr como root
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      containers:
      - name: payment-service
        image: myregistry/payment-service:v2.3.1
        ports:
        - containerPort: 8080
          name: http
        - containerPort: 9090
          name: metrics
        # Resources: requests = lo que garantiza K8s, limits = techo absoluto
        resources:
          requests:
            cpu: "200m"
            memory: "256Mi"
          limits:
            cpu: "1000m"
            memory: "512Mi"
        # Liveness: si falla → K8s reinicia el pod
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 10
          failureThreshold: 3
        # Readiness: si falla → K8s deja de enviar tráfico (no reinicia)
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 5
        # Secrets via variables de entorno desde K8s Secret (no en imagen)
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: payment-service-secrets
              key: db-password
      # Graceful shutdown: esperar a que requests en vuelo terminen
      terminationGracePeriodSeconds: 30
  # PodDisruptionBudget separado: nunca menos de 2 pods disponibles
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-service-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-service

Estrategias de Deployment: Trade-offs Reales

Estrategia Cómo funciona Ventaja Riesgo Cuándo usar
Rolling Update Reemplaza pods gradualmente Zero-downtime, simple Dos versiones simultáneas — APIs deben ser backward compatible Default para la mayoría de servicios
Blue/Green Dos entornos completos, switch instantáneo Rollback instantáneo, sin coexistencia de versiones Doble costo de infra durante deployment Cambios de schema de BD, APIs con breaking changes
Canary % de tráfico a nueva versión, incremento gradual Validación con tráfico real, blast radius controlado Complejidad de routing, monitoreo activo necesario Features de alto riesgo, cambios de performance críticos
Shadow Réplica del tráfico real a nueva versión sin impacto Testing con tráfico real sin riesgo Doble procesamiento, efectos secundarios en nueva versión Validación de migraciones de datos, cambios de algoritmo
Feature Flags Deploy desacoplado del release Control granular, rollback por feature sin redeploy Deuda técnica de flags, paths de código condicionales Features experimentales, A/B testing, releases graduales
Perspectiva complementariaEstrategias de Deployment

La estrategia de deployment es una decisión arquitectónica con implicaciones directas en el riesgo de cada release, el costo de rollback, y la velocidad de entrega.


  BLUE/GREEN DEPLOYMENT
  
  Antes del release:
  Load Balancer → [Blue: v1.0] (100% tráfico)
                  [Green: v1.1] (0% tráfico, listo)
  
  Durante el switch:
  Load Balancer → [Blue: v1.0] (0% tráfico)   ← rollback instantáneo
                  [Green: v1.1] (100% tráfico) ← nuevo activo
  
  Pros: Rollback instantáneo. Sin downtime.
  Cons: Doble infraestructura durante el switch. Costo.
  Ideal para: Sistemas críticos donde el rollback debe ser inmediato.

  ─────────────────────────────────────────────────────────

  CANARY DEPLOYMENT
  
  t=0:  Load Balancer → [v1.0] (100%)
  t=1:  Load Balancer → [v1.0] (95%) + [v1.1] (5%)   ← canary
  t=2:  Load Balancer → [v1.0] (80%) + [v1.1] (20%)  ← métricas OK
  t=3:  Load Balancer → [v1.0] (50%) + [v1.1] (50%)
  t=4:  Load Balancer → [v1.1] (100%)                  ← rollout completo
  
  Si métricas degradan en cualquier paso → rollback automático a t-1
  
  Pros: Exposure gradual de riesgo. Validación con tráfico real.
  Cons: Dos versiones en producción simultáneamente (DB schema compatibility).
  Ideal para: Features nuevas, cambios de performance, sistemas de alto tráfico.

  ─────────────────────────────────────────────────────────

  FEATURE FLAGS (más allá del deployment)
  
  Deploy ≠ Release. Con feature flags, puedes:
  → Desplegar código a producción sin activarlo
  → Activar para 1% de usuarios (canary funcional)
  → A/B testing integrado en el deployment
  → Kill switch instantáneo sin rollback de código
  
  Herramientas: LaunchDarkly, Unleash, Flipt, Flagsmith

Disaster Recovery, HA y RTO/RPO: Diseño Real


  Relación entre Disponibilidad, RTO y RPO:

  AVAILABILITY TIERS:
  99%    = 87.6h downtime/año  → Sistemas internos no críticos
  99.9%  = 8.7h  downtime/año  → Aplicaciones de negocio standard
  99.95% = 4.4h  downtime/año  → Plataformas de e-commerce
  99.99% = 52min downtime/año  → Sistemas financieros, infraestructura
  99.999%=  5min downtime/año  → Trading, telecomunicaciones

  RTO (Recovery Time Objective) = ¿Cuánto tiempo para recuperar?
  RPO (Recovery Point Objective) = ¿Cuántos datos podemos perder?

  Solución         │ RTO      │ RPO      │ Costo relativo
  ─────────────────┼──────────┼──────────┼────────────────
  Backup + Restore │ Horas    │ 24h      │ 1x  (baseline)
  Warm Standby     │ Minutos  │ Minutos  │ 2x
  Hot Standby      │ Segundos │ Segundos │ 3-4x
  Active-Active    │ ~0       │ ~0       │ 5-10x

  Pregunta crítica del SA: "¿Cuánto vale 1 hora de downtime para el negocio?"
  Si la respuesta es $10K/hora → el costo de Active-Active se justifica.
  Si la respuesta es $500/hora  → Warm Standby es suficiente.

# Multi-AZ RDS con failover automático — IaC real
resource "aws_db_instance" "payments_db" {
  identifier        = "payments-prod"
  engine            = "postgres"
  engine_version    = "15.4"
  instance_class    = "db.r6g.xlarge"
  allocated_storage = 500

  # Multi-AZ: réplica síncrona en otra AZ, failover ~60-120s
  multi_az               = true
  backup_retention_period = 30    # RPO: 5 min con PITR
  backup_window          = "03:00-04:00"
  maintenance_window     = "Mon:04:00-Mon:05:00"

  # Performance Insights para observabilidad de queries
  performance_insights_enabled          = true
  performance_insights_retention_period = 7

  # Encryption at rest obligatorio
  storage_encrypted = true
  kms_key_id        = aws_kms_key.db_key.arn

  # Deletion protection: evitar borrado accidental
  deletion_protection = true
  skip_final_snapshot = false
  final_snapshot_identifier = "payments-prod-final"

  tags = {
    Team        = "payments"
    Environment = "production"
    RTO         = "2min"
    RPO         = "5min"
  }
}

La infraestructura cloud se diseña en función del estilo arquitectónico: Microservicios en Kubernetes requieren service mesh (Istio/Linkerd), service discovery y distributed tracing desde el diseño. Serverless se diseña alrededor de managed services. Event-Driven requiere un broker resiliente (Kafka en multi-AZ mínimo). La estrategia de deployment (canary, blue/green) es una decisión arquitectónica que impacta el contrato de API y el modelo de datos.
