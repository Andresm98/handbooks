El trabajo más difícil y más valioso del Solutions Architect no es diseñar sistemas nuevos — es modernizar los existentes sin destruir el negocio que los necesita. Cualquiera puede diseñar en el vacío. La verdadera habilidad está en navegar la complejidad de sistemas que llevan 10 años en producción, con deuda técnica acumulada, sin documentación, y con el negocio dependiendo de cada transacción.

Por qué los Rewrites Fallan: El Análisis Honesto

Estadística real: El 70-80% de los proyectos de "rewrite completo" fallan o son cancelados. Los que se completan frecuentemente recapitulan los mismos problemas del sistema original. Joel Spolsky lo llamó "la única decisión peor que puedes tomar".


  Por qué los Rewrites Completos Fallan:

  SUPOSICIÓN INCORRECTA: "El sistema legacy es malo porque fue mal escrito"

  REALIDAD: El sistema legacy acumula AÑOS de:
  ├── Reglas de negocio implícitas no documentadas
  │   ("Este campo no puede ser 0 el primer día del mes" — nadie sabe por qué)
  ├── Edge cases del mundo real
  │   (Maneja IVA de 5 países diferentes con reglas distintas)
  ├── Workarounds de bugs de proveedores
  │   (La API de X no funciona si el monto tiene más de 2 decimales)
  ├── Comportamiento contractual implícito
  │   (Los clientes grandes asumen cierto comportamiento "buggy" y lo usan)
  └── Decisiones de negocio que ya no se recuerdan
      ("No se puede cancelar una orden 48h después" — hay razón legal)

  El rewrite asume que SABES todo esto. No lo sabes.
  Descubres que no lo sabías cuando el sistema en producción
  hace algo diferente al legacy y el negocio se rompe.

  Resultado típico:
  Año 1: "Vamos bien, el nuevo sistema es más limpio"
  Año 2: "Estamos encontrando casos edge inesperados"
  Año 3: "El nuevo sistema tiene los mismos problemas que el legacy"
        + "El legacy siguió evolucionando y el gap es mayor"
  Año 3.5: Proyecto cancelado o "mantenemos ambos indefinidamente"

Strangler Fig Pattern: La Alternativa Real

El Strangler Fig (Martin Fowler) es la estrategia de migración que consistentemente funciona. Nombrado por el árbol que crece alrededor de otro árbol, eventualmente reemplazándolo, sin que el árbol original deje de funcionar durante el proceso. 


  Strangler Fig: Fases de Migración

  FASE 0: Facade Layer (semanas 1-4)
  ┌─────────────────────────────────────────────────────────────────┐
  │  Todo el tráfico pasa por un facade/proxy                       │
  │  El facade inicialmente re-envía TODO al legacy                 │
  │                                                                 │
  │  Client ──► Facade Proxy ──► Legacy System (100% del tráfico)  │
  └─────────────────────────────────────────────────────────────────┘

  FASE 1: Extracción del primer dominio (meses 1-3)
  ┌─────────────────────────────────────────────────────────────────┐
  │  Extraer el dominio más aislado (menor acoplamiento al resto)   │
  │                                                                 │
  │             ┌──► Legacy (80% del tráfico)                       │
  │  Client──► Facade                                               │
  │             └──► New Service: Users (20%)                       │
  │                  (solo endpoints de usuario migrados)           │
  └─────────────────────────────────────────────────────────────────┘

  FASES 2-N: Migración incremental (meses 3-24+)
  ┌─────────────────────────────────────────────────────────────────┐
  │  Cada sprint: migrar un endpoint, un dominio, un flujo           │
  │                                                                 │
  │             ┌──► Legacy (20% — solo partes no migradas)         │
  │  Client──► Facade                                               │
  │             ├──► New Service: Users                             │
  │             ├──► New Service: Orders                            │
  │             ├──► New Service: Payments                          │
  │             └──► New Service: Catalog                           │
  └─────────────────────────────────────────────────────────────────┘

  FASE FINAL: Legacy apagado
  ┌─────────────────────────────────────────────────────────────────┐
  │  Client ──► Facade (o eliminado) ──► New Services (100%)        │
  │  Legacy: APAGADO                                                │
  └─────────────────────────────────────────────────────────────────┘

  CLAVE: El negocio nunca se interrumpe. En ninguna fase.

Anti-Corruption Layer (ACL)

Cuando el sistema nuevo debe comunicarse con el legacy, el ACL actúa como traductor. Evita que el modelo de dominio del legacy "contamine" el modelo del nuevo sistema.

// El legacy usa un modelo de datos feo de los años 90
interface LegacyCustomer {
  CUST_ID: string      // "00123456"
  CUST_NM: string      // "SMITH, JOHN A."
  ADDR_LN1: string
  ADDR_CITY: string
  STS_CD: string       // "A" = active, "I" = inactive, "S" = suspended
  CRT_DT: string       // "20240115" — YYYYMMDD sin separadores
}

// Nuestro nuevo modelo de dominio limpio
interface Customer {
  id: string
  name: { first: string; last: string; middle?: string }
  address: Address
  status: 'active' | 'inactive' | 'suspended'
  createdAt: Date
}

// Anti-Corruption Layer: traduce entre ambos mundos
class CustomerACL {
  fromLegacy(legacy: LegacyCustomer): Customer {
    const [lastName, rest] = legacy.CUST_NM.split(', ')
    const [firstName, middle] = rest.split(' ')

    return {
      id: legacy.CUST_ID.replace(/^0+/, ''),  // Quitar leading zeros
      name: { first: firstName, last: lastName, middle },
      address: this.parseAddress(legacy),
      status: this.mapStatus(legacy.STS_CD),
      createdAt: parse(legacy.CRT_DT, 'yyyyMMdd', new Date())
    }
  }

  private mapStatus(code: string): Customer['status'] {
    const map = { 'A': 'active', 'I': 'inactive', 'S': 'suspended' } as const
    return map[code] ?? 'inactive'
  }
}

Estrategias de Migración de Base de Datos

Estrategia Cómo Riesgo Cuándo usar
Expand/Contract Fase expand: añadir nueva columna. Migrar datos. Fase contract: eliminar columna vieja. Bajo — zero-downtime Cambios de schema en producción con zero-downtime
Dual-write App escribe en BD vieja Y nueva simultáneamente durante migración Medio — consistencia eventual entre ambas Migración de base de datos completa manteniendo el negocio activo
CDC (Change Data Capture) Debezium captura cambios del WAL de la BD vieja y los replica a la nueva Medio — requiere sincronización inicial Migración de BD con mínimo impacto en la aplicación existente
Shadow Read App lee de ambas BDs, compara resultados, alerta si difieren Muy bajo — sin impacto en producción Validar que la nueva BD produce resultados idénticos antes del cutover
Modelos relacionados

La modernización de legacy se apoya en múltiples patrones arquitectónicos: Strangler Fig como estrategia macro, Anti-Corruption Layer para aislar modelos de dominio, Event-Driven Architecture para desacoplar gradualmente (el legacy publica eventos que el nuevo sistema consume), y Hexagonal Architecture como el patrón de destino que hace el nuevo sistema adaptable a futuros cambios.
