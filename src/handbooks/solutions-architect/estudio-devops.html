🔄 CI/CD — Continuous Integration / Continuous Delivery

Continuous Integration (CI)

  • Integrar cambios frecuentemente (varias veces al día)
  • Build automático en cada commit
  • Tests automáticos (unit, integration)
  • Feedback rápido al desarrollador

Continuous Delivery vs Deployment

  • CD (Delivery): código siempre en estado deployable. Deploy a producción requiere aprobación humana.
  • CD (Deployment): cada cambio que pasa CI se despliega automáticamente a producción sin intervención humana.

Pipeline típico

commit → Build → Unit Tests → Integration Tests → Security Scan → Artifact → Deploy Staging → E2E Tests → Deploy Prod

# Herramientas CI/CD
GitHub Actions | GitLab CI | Jenkins | CircleCI | Azure DevOps | AWS CodePipeline

Estrategias de Deploy

Estrategia Descripción Riesgo Rollback
Rolling Reemplaza instancias gradualmente Bajo Complejo
Blue/Green Dos entornos idénticos; switch de tráfico Mínimo Instantáneo (switch back)
Canary % pequeño de tráfico a nueva versión Muy bajo Fácil (reduce %)
Feature Flags Features desactivadas en código, activadas por config Mínimo Toggle OFF

🏗️ Infrastructure as Code (IaC)

🌍 Terraform

IaC multi-cloud, declarativa, HCL. El estándar de la industria para multi-cloud.

  • Provider ecosystem enorme (AWS, Azure, GCP, K8s)
  • State management (local o remote con S3/Terraform Cloud)
  • Módulos reutilizables
  • Plan → Apply workflow

🔧 AWS CloudFormation / CDK

CloudFormation: YAML/JSON declarativo. CDK: código real (TypeScript/Python) que genera CloudFormation.

  • Nativo AWS, integrado con todos los servicios
  • CDK = type-safe, testeable, reutilizable
  • Stacks y nested stacks

🔵 Azure Bicep

DSL de Microsoft para Azure Resource Manager. Más legible que ARM templates JSON.

  • Transpila a ARM templates
  • Type safety, módulos
  • Integrado con Azure DevOps

⚙️ Ansible / Pulumi

Ansible: configuration management imperativo (idempotente). Pulumi: IaC en lenguajes reales (Python, Go, TS).

  • Ansible: excelente para OS-level config
  • Pulumi: cuando se necesita lógica compleja

👁️ Observabilidad — Los 3 Pilares

La observabilidad es la capacidad de entender el estado interno de un sistema desde el exterior. Se basa en 3 pilares complementarios:

📊 Metrics

Mediciones numéricas agregadas en el tiempo. Responden: ¿Está el sistema sano? ¿Hay anomalías?

Tipos de métricas

  • RED: Rate, Errors, Duration (para servicios)
  • USE: Utilization, Saturation, Errors (para recursos)

Herramientas

  • Prometheus, Grafana, CloudWatch, Datadog

📝 Logs

Registros de eventos discretos. El logging registra; el monitoring analiza esos datos.

Best practices

  • Logs estructurados (JSON)
  • Correlation IDs para tracing
  • Niveles: DEBUG, INFO, WARN, ERROR
  • Retención y compresión

Herramientas

  • ELK Stack, Splunk, CloudWatch Logs, Loki

🔍 Traces (Distributed Tracing)

Seguimiento end-to-end de una request a través de múltiples servicios. Responden: ¿Dónde está la latencia?

Conceptos

  • Trace: journey completo de un request
  • Span: operación individual dentro de un trace
  • Context propagation: headers W3C TraceContext

Herramientas

  • Jaeger, Zipkin, AWS X-Ray, OpenTelemetry
✅
En cloud, priorizar: Observabilidad de métricas, logs y trazas para análisis en tiempo real. OpenTelemetry es el estándar open-source para instrumentación unificada.

🛡️ Resiliencia y Tolerancia a Fallos

Patrones de Resiliencia

  • Circuit Breaker: evita cascade failures
  • Retry with backoff: reintentos con espera exponencial
  • Timeout: no esperar indefinidamente
  • Bulkhead: aislar recursos entre funciones (ej: thread pools)
  • Health checks: liveness + readiness probes (K8s)
  • Graceful degradation: funcionalidad reducida ante fallos

Contenedores — Ciclo de vida ante fallo

  1. Contenedor detectado como unresponsive
  2. Deja de recibir tráfico (remove from load balancer)
  3. Guarda error logs y debug info
  4. Shutdown del contenedor
  5. Lanzamiento de contenedor reemplazo

Orquestado por: Kubernetes, ECS, GKE.
