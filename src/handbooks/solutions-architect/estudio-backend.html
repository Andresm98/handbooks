🔌 Tipos de API y Protocolos

Protocolo Estilo Formato Cuándo usar Trade-offs
REST Stateless, resource-based JSON/XML sobre HTTP/1.1 APIs públicas, CRUD, web estándar Verboso, over/under-fetching, múltiples round-trips
GraphQL Query language, client-driven JSON sobre HTTP UI complejas, múltiples clientes, BFF N+1 problem, caching complejo, curva de aprendizaje
gRPC RPC, contract-first Protocol Buffers sobre HTTP/2 Microservicios internos, baja latencia, streaming No legible por humanos, requiere codegen, browser support limitado
WebSockets Bidireccional, stateful Frames sobre TCP Real-time (chat, gaming, trading) Conexión persistente, escalado complejo, no HTTP cache
Webhooks Push-based, event-driven JSON sobre HTTP POST Notificaciones de eventos externos No hay garantía de entrega, requiere retry logic
✅
Long Polling es una alternativa a WebSockets: el cliente hace request y el servidor mantiene la conexión abierta hasta tener datos. Desventaja: latencia inherente y overhead HTTP por cada request.

Versionado de APIs REST

Crítico para compatibilidad con clientes existentes al evolucionar la API. Estrategias:

# URL versioning (más común)
GET /api/v1/users
GET /api/v2/users

# Header versioning
GET /api/users
Accept: application/vnd.myapi.v2+json

# Query param versioning
GET /api/users?version=2

🔐 Autenticación y Autorización

Flujo: Autenticación → Autorización

Autenticación responde: "¿Quién dice ser?" | Autorización responde: "¿Qué puede hacer?" | Auditoría responde: "¿Qué hizo?"

JWT — JSON Web Token

Token de 3 partes separadas por puntos: Header.Payload.Signature

  • Header: algoritmo de firma (HS256, RS256)
  • Payload: claims (sub, exp, roles)
  • Signature: hash firmado con clave secreta

Stateless: el servidor no guarda sesión. Verifica firma en cada request.

OAuth 2.0 Grants

  • Authorization Code: apps web server-side (más seguro)
  • PKCE: apps móviles/SPA (sin client secret)
  • Client Credentials: machine-to-machine
  • Implicit: obsoleto, no usar

OAuth 2.0 es un framework de autorización. OpenID Connect (OIDC) agrega autenticación encima.

Access Control Models

Modelo Descripción Uso típico
RBAC Role-Based: permisos asignados a roles Sistemas empresariales, admin panels
ABAC Attribute-Based: políticas basadas en atributos del usuario/recurso Sistemas complejos, multi-tenant
DAC Discretionary: el dueño del recurso decide quién accede Sistemas de archivos, Google Drive
MAC Mandatory: el sistema decide según clasificación Sistemas militares/gubernamentales

Mejores prácticas de Auth

  • ✅ Hashear passwords con bcrypt/Argon2 (NUNCA plain text)
  • ✅ Rate limiting en login endpoints
  • ✅ HTTPS obligatorio (tokens interceptables en plain HTTP)
  • ✅ Tokens con expiración corta + refresh tokens
  • ✅ Usar secrets manager para claves (nunca en código fuente)
  • ✅ Estructurar roles (RBAC) desde el diseño inicial
  • ❌ Nunca almacenar passwords en plain text
  • ❌ No usar auth por IP (fácilmente spoofeable)

📈 Escalabilidad y Concurrencia

Vertical Scaling (Scale Up)

Más CPU/RAM al mismo servidor. Simple pero con límite físico. Sin particionamiento de datos.

Horizontal Scaling (Scale Out)

Más instancias/nodos. Cada nodo puede contener parte de los datos (sharding). Requiere stateless apps o sticky sessions.

Database Scaling

  • Read Replicas: réplicas de solo lectura para distribuir queries
  • Sharding horizontal: particionar datos entre nodos (cada nodo = parte de los datos) — respuesta a la evaluación sobre el banco
  • Caching: Redis/Memcached para reducir carga en DB
  • Connection pooling: PgBouncer, HikariCP

⚖️ Load Balancing

🌐 HTTP/L7 Load Balancer

Opera a nivel de aplicación. Puede enrutar por URL path, headers, cookies.

  • AWS ALB, Azure Application Gateway
  • Soporta SSL termination, WAF

🔌 Network/L4 Load Balancer

Opera a nivel de transporte. Distribuye por protocolos específicos (TCP/UDP). Ultra-baja latencia.

  • AWS NLB, Azure Load Balancer
  • Ideal para gaming, VoIP, IoT

💻 Virtual Load Balancer

Software-based, corre a nivel de OS del servidor. Distribuye según reglas configuradas.

  • HAProxy, Nginx como LB
  • Flexible, barato, configurable

🔩 Hardware Load Balancer

Dispositivo físico dedicado. Máximo rendimiento, máximo costo.

  • F5 BIG-IP, Citrix ADC
  • Usado en grandes enterprises on-prem

Algoritmos de Balanceo

Algoritmo Descripción Caso de uso
Round Robin Distribuye secuencialmente entre servidores Servidores homogéneos, stateless
Weighted Round Robin Más requests a servidores más potentes Servidores heterogéneos
Least Connections Al servidor con menos conexiones activas Requests de duración variable
Weighted Least Connection Least connections + peso por capacidad Microservicios con distinta capacidad
Source IP Hash Hash de IP del cliente → mismo servidor siempre Session persistence / Sticky sessions
Weighted Response Time Al servidor con menor tiempo de respuesta Optimización de latencia dinámica
