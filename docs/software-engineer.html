CAP. 01

Qué es Realmente un Ingeniero Senior

La definición más común de "senior" en la industria es incorrecta. No es el ingeniero con más años de experiencia, ni el que conoce más tecnologías, ni el que escribe el código más sofisticado. Un ingeniero senior es el que multiplica el output del equipo, convierte la ambigüedad en claridad técnica, y reduce activamente la complejidad del sistema.

La diferencia entre un junior y un senior no es de conocimiento — es de modelo mental. El junior ve un problema técnico. El senior ve el problema técnico, el problema de negocio detrás, las consecuencias de las diferentes soluciones en el tiempo, y el impacto en el equipo que lo va a mantener.

Axioma #1: Un ingeniero senior que hace el trabajo de tres juniors no es tres veces mejor — está haciendo algo incorrecto. El leverage real de un senior está en elevar a los que están alrededor, no en escribir más código.

La Progresión Real: Junior → Mid → Senior → Staff

Nivel Scope de impacto Input necesario Output primario Lo que los distingue
Junior Una tarea, un componente Instrucciones detalladas, supervisión continua Código que funciona según lo especificado Aprenden rápido, hacen buenas preguntas
Mid Una feature completa Requerimientos claros, revisión en puntos clave Features completas con tests y documentación Trabajan de forma independiente, identifican problemas
Senior Un dominio o sistema completo Objetivos de negocio, sin especificaciones técnicas Soluciones técnicas a problemas de negocio Multiplican al equipo, toman buenas decisiones de trade-off
Staff Múltiples equipos, dirección técnica Estrategia de alto nivel Visión técnica, estándares, alineación cross-team Cambian el rumbo técnico de la organización

El Efecto Multiplicador del Senior

Los seniors más valiosos no son los mejores programadores del equipo. Son los que hacen mejores a todos los demás. Esto se manifiesta de formas concretas:

Code reviews que enseñan

No solo señalan qué está mal — explican por qué, con alternativas concretas. Un buen code review transfiere conocimiento al autor. Una semana de buenos reviews puede acelerar el crecimiento de un junior más que un mes de trabajo independiente.

Clarificar antes de codificar

Identifican ambigüedad en los requerimientos antes de escribir una línea. "¿Qué pasa cuando el usuario no tiene email?" es una pregunta que ahorra días de re-trabajo. Los juniors implementan lo que les dijeron; los seniors preguntan lo que no les dijeron.

Simplificar lo que ya existe

Cada semana eliminan complejidad del sistema: refactorizan código difícil de entender, eliminar abstracciones incorrectas, consolidan duplicación. El código que eliminan es la contribución más valiosa que nadie ve.

Decir "no sé" estratégicamente

Admiten incertidumbre en lugar de especular. "No sé, pero lo investigo y te digo en 30 minutos" construye más confianza que una respuesta incorrecta dada con seguridad.

Anti-pattern: Hero engineer

El senior que resuelve todos los problemas él mismo crea una dependencia del equipo en su persona, no transfiere conocimiento, y es un single point of failure. Si el equipo colapsa cuando se va de vacaciones, algo está mal.

Anti-pattern: Complexity as status

Escribir código sofisticado para demostrar habilidad. La solución más simple que resuelve el problema es casi siempre superior. "Si no puedes explicarlo simplemente, no lo entiendes bien." — Feynman.

Cómo se Desarrolla el Criterio Técnico

El criterio — la capacidad de tomar buenas decisiones técnicas con información incompleta — no viene de leer documentación. Viene de un ciclo específico que la mayoría de los ingenieros no hace conscientemente: 


  El Ciclo de Desarrollo del Criterio Técnico

  1. DECISIÓN   →   Tomar una decisión técnica con la información disponible
       │            Documentar el razonamiento (aunque sea mentalmente)
       │
  2. OBSERVAR   →   Observar las consecuencias en producción real
       │            ¿Se cumplieron las predicciones? ¿Qué fue diferente?
       │
  3. ANALIZAR   →   Postmortem personal: ¿por qué fue diferente?
       │            ¿Qué información faltaba? ¿Qué asumí incorrectamente?
       │
  4. ACTUALIZAR →   Actualizar el modelo mental con el aprendizaje
       │            La próxima decisión similar incorpora este conocimiento
       │
       └─────────── Repetir ──────────────────────────────────────────┐

  El error más común: saltar de 1 a 1 sin pasar por 2, 3, y 4.
  Acumular años de experiencia sin extraer el aprendizaje de cada experiencia
  produce antigüedad, no criterio.
Conexión técnica

El modelo mental del ingeniero senior se aplica directamente a las decisiones arquitectónicas: elegir entre Clean Architecture y un monolito simple, entre consistencia fuerte y eventual consistency, entre construir y comprar. El criterio técnico es lo que convierte el conocimiento de patrones en decisiones correctas para el contexto específico.

CAP. 02

El Oficio del Código

El código se escribe una vez y se lee decenas de veces. Un estudio de Microsoft Research encontró que los ingenieros pasan el 70% del tiempo leyendo código — el propio y el ajeno. Escribir código que otros puedan leer, entender, y modificar sin miedo no es un lujo estético — es una habilidad de ingeniería con impacto directo en la velocidad del equipo.

Naming: La Habilidad más Subestimada

Phil Karlton dijo que hay dos problemas difíciles en ciencias de la computación: invalidación de caché y nombrar cosas. El naming incorrecto es una mentira que el código cuenta sobre sí mismo. Cada nombre incorrecto es deuda cognitiva que se paga cada vez que alguien lee ese código.

// ❌ Naming que miente o que no dice nada
function process(d: any): any {
  const r = d.filter((x: any) => x.s === 1)
  return r.map((x: any) => ({ ...x, t: Date.now() }))
}

// ✓ Naming que documenta la intención
function markActiveUsersAsProcessed(users: User[]): User[] {
  const activeUsers = users.filter(user => user.status === UserStatus.Active)
  return activeUsers.map(user => ({
    ...user,
    processedAt: Date.now()
  }))
}

def process_order(order_data: dict) -> dict:
    # Validación de campos
    if not order_data.get('user_id'):
        raise ValueError('user_id required')
    if not order_data.get('items') or len(order_data['items']) == 0:
        raise ValueError('items required')

    # Cálculo de totales
    subtotal = sum(item['price'] * item['quantity'] for item in order_data['items'])
    tax = subtotal * 0.21
    total = subtotal + tax

    # Guardar en base de datos

    cursor = conn.cursor()
    cursor.execute("INSERT INTO orders (user_id, total) VALUES (?, ?)",
                   (order_data['user_id'], total))
    order_id = cursor.lastrowid
    conn.commit()

    # Enviar email
    send_email(order_data['user_email'], f"Order {order_id} confirmed")

    return {'order_id': order_id, 'total': total}

SOLID: Aplicado con Profundidad Real

Principio La regla simple Lo que realmente significa Señal de violación
S — SRP Una clase, una razón para cambiar Una clase debe ser responsable ante un único actor del sistema. No "hace una cosa" — responde a un único stakeholder La clase cambia cuando el equipo de finanzas cambia algo Y cuando el equipo de UI cambia algo
O — OCP Abierto a extensión, cerrado a modificación Añadir comportamiento nuevo sin tocar código existente. Logrado con polimorfismo, no con if/else Añadir un nuevo tipo de pago requiere modificar la clase PaymentProcessor existente
L — LSP Subtipos sustituibles por el supertipo Si tienes código que funciona con Animal, debe funcionar con Perro sin cambios ni sorpresas Una subclase que lanza una excepción en un método que el padre implementa silenciosamente
I — ISP Interfaces pequeñas y focalizadas Los clientes no deben depender de métodos que no usan. Múltiples interfaces pequeñas > una grande Implementar una interfaz y dejar métodos con throw NotImplementedException
D — DIP Depender de abstracciones, no de implementaciones El módulo de alto nivel define la interfaz que necesita. El módulo de bajo nivel la implementa La lógica de negocio hace new PostgresRepository() directamente

Deuda Técnica: Herramienta, No Excusa

La deuda técnica no es sinónimo de código malo. Es una metáfora financiera: a veces tiene sentido tomar una deuda deliberada (lanzar más rápido con una solución subóptima) si el retorno justifica el costo del interés (el trabajo adicional para mantenerla).


  Tipos de Deuda Técnica (Cuadrante de Fowler)

                    DELIBERADA          INADVERTIDA
                  ┌───────────────────┬──────────────────────┐
   PRUDENTE       │ "No tenemos       │ "Ahora sabemos que   │
                  │ tiempo de         │ deberíamos haber     │
                  │ diseñar bien"     │ usado esta           │
                  │                   │ arquitectura"        │
                  │ → Documentar,     │                      │
                  │   pagar pronto    │ → Aprender, mejorar  │
                  ├───────────────────┼──────────────────────┤
   IMPRUDENTE     │ "No hay tiempo    │ "¿Qué son las        │
                  │ para tests"       │ capas?"              │
                  │                   │                      │
                  │ → Problema real   │ → Problema de        │
                  │   a corto plazo   │   contratación /     │
                  │                   │   formación          │
                  └───────────────────┴──────────────────────┘

  La deuda deliberada-prudente es una herramienta válida.
  La deuda inadvertida o imprudente es un problema de proceso o equipo.

  El costo real de la deuda técnica:
  • Velocidad de desarrollo reducida (interés compuesto)
  • Bugs más difíciles de aislar (código acoplado)
  • Onboarding más lento (código incomprensible)
  • Miedo a cambiar (código sin tests)
  • Rotación de ingenieros (trabajo frustrante)

La regla del boy scout: Deja el código un poco mejor de como lo encontraste. No un gran refactor — renombrar una variable confusa, extraer una función, añadir un test que faltaba. Aplicado consistentemente por todo el equipo, revierte la entropía del código sin interrumpir el desarrollo de features.

CAP. 03

Diseño de Software

El diseño de software ocurre constantemente, no solo al principio de un proyecto. Cada vez que nombras una función, defines una interfaz, o decides dónde vive un pedazo de lógica — estás diseñando. La diferencia entre un ingeniero que diseña bien y uno que no lo hace no está en el conocimiento de patrones, sino en la capacidad de reconocer qué problema tienen que resolver.

Patrones de Diseño como Soluciones a Problemas Reales

Los patrones de diseño son soluciones reutilizables a problemas recurrentes. El error es aprenderlos como un catálogo a memorizar. El valor está en reconocer el problema que cada patrón resuelve — y solo entonces aplicarlo.

Patrón Problema real que resuelve Señal de que lo necesitas Anti-pattern de aplicación
Strategy Comportamiento intercambiable en runtime sin if/else Tienes un switch/if-else que crece cada vez que añades un tipo Crear Strategy para comportamiento que nunca cambia
Observer Notificar a múltiples componentes sin acoplamiento directo Un cambio en objeto A requiere llamar a B, C, D directamente Observadores con side effects no predecibles ni testeables
Decorator Añadir responsabilidades a un objeto sin modificar su clase Necesitas logging/caching/retry en múltiples implementaciones Cadenas de decoradores tan profundas que el debugging es imposible
Factory Centralizar la lógica de creación de objetos complejos La lógica de crear un objeto está duplicada en múltiples lugares Factory que hace demasiado — viola SRP también
Repository Abstraer el acceso a datos del dominio de negocio SQL/ORM queries dispersas en la lógica de negocio Repository que filtra, ordena, pagina Y hace joins complejos — se convierte en un ORM wrapper
Builder Construir objetos complejos paso a paso Constructor con 7+ parámetros donde el orden importa Builder para objetos simples — añade complejidad sin valor

API Design: El Contrato Permanente

Una API pública es una decisión arquitectónica irreversible. Una vez que clientes dependen de ella, cambiarla tiene un costo real. El diseño de una API es el trabajo que más durará en el tiempo — más que cualquier implementación subyacente.


  Principios de API Design que Envejecen Bien

  1. NOMBRES COMO RECURSOS, VERBOS COMO ACCIONES HTTP
     ❌ GET /getUser?id=123
     ❌ POST /createOrder
     ✓  GET /users/123
     ✓  POST /orders

  2. VERSIONADO DESDE EL DÍA 1
     ✓  /api/v1/users
     Sin versión = imposible hacer breaking changes sin romper clientes

  3. ERRORES INFORMATIVO Y CONSISTENTES (RFC 7807)
     ❌ HTTP 400 { "error": "bad" }
     ✓  HTTP 422 {
           "type": "https://api.company.com/errors/validation",
           "title": "Validation Failed",
           "detail": "email must be a valid email address",
           "invalid_params": [{"name": "email", "reason": "invalid format"}]
        }

  4. PAGINACIÓN CONSISTENTE
     ✓  GET /users?page=2&per_page=50
        Response: { "data": [...], "meta": { "total": 1234,
                    "page": 2, "per_page": 50, "pages": 25 } }

  5. IDEMPOTENCY KEYS EN OPERACIONES CRÍTICAS
     POST /payments
     Idempotency-Key: client-generated-uuid
     → Si el request falla y se reintenta con la misma key,
       el servidor retorna el resultado original sin re-procesar

  6. BACKWARD COMPATIBILITY
     ✓  Añadir campos opcionales: seguro
     ✓  Deprecar campos (documentar, mantener 1 versión)
     ❌ Renombrar campos existentes: breaking change
     ❌ Cambiar tipo de un campo: breaking change
     ❌ Hacer obligatorio algo que era opcional: breaking change

Abstracciones: El Arte del Equilibrio

Una abstracción correcta oculta complejidad sin ocultar información importante. Una abstracción incorrecta — o prematura — es una de las fuentes más comunes de deuda técnica. Joel Spolsky formuló la Ley de las Abstracciones con Fugas: todas las abstracciones no triviales tienen fugas. 

# Abstracción prematura: el enemigo silencioso

# Inicio del proyecto — dos casos de uso:
def send_welcome_email(user_email: str): ...
def send_password_reset(user_email: str): ...

# ❌ Abstracción prematura — crear un EmailSender genérico
#    con factory, template engine, y 400 líneas "para ser flexible"
#    cuando todavía no sabemos qué variaciones reales necesitaremos

# ✓ Esperar hasta el tercer caso de uso para abstraer
#    La abstracción correcta solo se puede ver con suficientes ejemplos concretos
#    "Make it work, make it right, make it fast" — en ese orden

# Regla: duplicar está permitido UNA vez.
#         Al tercer caso de duplicación, abstraer.
#         Esta es la "Rule of Three" de abstracción.

# ─────────────────────────────────────────────────────────────
# Señales de que una abstracción está MAL:

# 1. Necesita un nombre genérico porque no sabes qué hace
#    Manager, Handler, Processor, Helper, Utils → red flags

# 2. Tiene más de un nivel de indirección innecesario
#    service.getRepository().findById() vs userRepo.findById()

# 3. Los casos de uso concretos necesitan "escapar" de la abstracción
#    if isinstance(repo, PostgresUserRepo):  → abstracción rota

# 4. Es más difícil de entender que el código que reemplaza
#    La abstracción debe REDUCIR la carga cognitiva, no aumentarla
Conexión técnica

El diseño de software es la capa donde los principios arquitectónicos se materializan en código. Hexagonal Architecture se implementa mediante interfaces (puertos) e implementaciones concretas (adapters). DDD se implementa mediante el modelado cuidadoso de entidades, value objects, y bounded contexts en el código. Los patrones de diseño son los bloques de construcción de cualquier arquitectura bien diseñada.

CAP. 04

Backend Engineering

El backend es el sistema nervioso de cualquier aplicación. Diseñarlo bien significa entender el protocolo sobre el que opera, gestionar el estado de forma predecible, manejar la concurrencia sin race conditions, y fallar de maneras informativas y recuperables.

Autenticación y Autorización: Conceptos Diferentes

Autenticación responde "¿quién eres?". Autorización responde "¿qué puedes hacer?". Confundirlos es uno de los errores de seguridad más comunes.

# Implementación completa de JWT auth en FastAPI
from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
import bcrypt

SECRET_KEY = "env-variable-never-hardcoded"
ALGORITHM  = "HS256"

def hash_password(plain: str) -> str:
    # bcrypt: auto-salted, trabajo configurable, resistente a rainbow tables
    return bcrypt.hashpw(plain.encode(), bcrypt.gensalt(rounds=12)).decode()

def verify_password(plain: str, hashed: str) -> bool:
    return bcrypt.checkpw(plain.encode(), hashed.encode())
    # bcrypt es timing-safe por diseño — evita timing attacks

def create_access_token(user_id: str, roles: list[str]) -> str:
    payload = {
        "sub":   user_id,
        "roles": roles,
        "iat":   datetime.now(timezone.utc),
        "exp":   datetime.now(timezone.utc) + timedelta(minutes=15),
        # Access token corto (15 min). Refresh token largo en httpOnly cookie.
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

            if permission not in current_user.permissions:
                raise HTTPException(
                    status_code=403,
                    detail=f"Permission '{permission}' required"
                )
            return await func(*args, current_user=current_user, **kwargs)
        return wrapper
    return decorator

async def reserve_item_optimistic(item_id: str, quantity: int):

        item = await db.get_item(item_id)
        if item.stock < quantity:
            raise InsufficientStockError()
        updated = await db.update_stock_if_version_matches(
            item_id,
            new_stock=item.stock - quantity,
            expected_version=item.version  # Falla si otro lo modificó
        )
        if updated:
            return  # Éxito
    raise ConcurrentModificationError()

        if item.stock < quantity:
            raise InsufficientStockError()
        await db.update_stock(item_id, item.stock - quantity)
        # Lock liberado al terminar la transacción

// Fase 2: escribir todos los valores (un solo repaint)

  el.style.height = (heights[i] * 2) + 'px'

// ✓ Para animaciones: requestAnimationFrame + CSS transforms
function animateElement(el: HTMLElement, distance: number) {
  let start: number
  function step(timestamp: number) {
    if (!start) start = timestamp
    const progress = Math.min((timestamp - start) / 300, 1)
    // transform: solo Composite — no reflow ni repaint
    el.style.transform = `translateX(${progress * distance}px)`
    if (progress < 1) requestAnimationFrame(step)
  }
  requestAnimationFrame(step)
}

Bases de Datos

Las bases de datos son el componente más crítico y más mal entendido del stack. Un modelo de datos incorrecto, un índice que falta, o una transacción mal diseñada pueden hacer que un sistema que funciona perfectamente con 1,000 usuarios colapse con 100,000. El conocimiento de bases de datos es lo que más distingue a un senior de un mid engineer.

Indexing Real: Más Allá de "Añadir un Índice"


  Cómo funciona un B-Tree Index (el más común)

  Tabla: users (10M filas)
  Columna: email (sin índice)

  SELECT * FROM users WHERE email = 'john@example.com'
  → Full table scan: leer las 10M filas = ~5-10 segundos

  Con índice B-Tree en email:
  → O(log n) lookups: ~3-4 niveles de árbol = microsegundos

  Estructura B-Tree:
                    [M-S]
                   /     \
            [E-J]           [T-Z]
           /     \           /    \
       [A-D]   [F-I]    [J-P]   [U-Z]
         │       │         │       │
      leaf     leaf      leaf    leaf
    pages     pages     pages   pages
      │         │         │       │
    ROWIDs    ROWIDs    ROWIDs  ROWIDs
  (punteros a las filas reales en el heap)

  B-Tree es eficiente para: =, >, <, >=, <=, BETWEEN, LIKE 'prefix%'
  B-Tree NO ayuda para: LIKE '%suffix', funciones sobre la columna

-- Índices que realmente marcan la diferencia

-- 1. Índice compuesto: el orden importa enormemente
-- Query: WHERE user_id = 123 AND status = 'active' ORDER BY created_at DESC
-- Índice correcto: (user_id, status, created_at)
-- Regla: columnas de equality primero, range/sort al final
CREATE INDEX idx_orders_user_status_date
    ON orders (user_id, status, created_at DESC);

-- 2. Índice parcial: indexar solo las filas relevantes
-- Si el 95% de las órdenes están 'completed', solo indexar 'pending'
CREATE INDEX idx_orders_pending
    ON orders (created_at)
    WHERE status = 'pending';
-- 20x más pequeño y más rápido que indexar toda la tabla

-- 3. Covering index: el índice contiene todo lo que la query necesita
-- La query NO necesita ir al heap (Index Only Scan)
CREATE INDEX idx_users_email_covering
    ON users (email) INCLUDE (id, name, plan);
-- SELECT id, name, plan FROM users WHERE email = ?
-- → Resuelto completamente desde el índice, sin tocar la tabla

-- 4. EXPLAIN ANALYZE: siempre antes de añadir/eliminar un índice
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT o.id, o.total, u.email
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'pending'
  AND o.created_at > NOW() - '24 hours'::interval;

-- Buscar en el output:
-- "Seq Scan" en tabla grande → candidato a índice
-- "Rows Removed by Filter" alto → el índice no es selectivo
-- "Buffers: shared hit=X read=Y" → X en caché, Y leyó disco (malo si Y alto)
-- "actual time" vs "estimated rows" → si muy diferente, falta ANALYZE

Transacciones: Isolation Levels que Importan

Las transacciones no son solo "ACID o no ACID". Los isolation levels permiten elegir el nivel de protección según el caso de uso — con el trade-off entre consistencia y concurrencia.

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Cuándo usar
READ UNCOMMITTED Posible Posible Posible Casi nunca — solo dashboards de analytics aproximados
READ COMMITTED No Posible Posible Default en PostgreSQL — adecuado para la mayoría de operaciones
REPEATABLE READ No No Posible Reportes financieros que necesitan snapshot consistente
SERIALIZABLE No No No Transferencias bancarias, inventario con stock crítico 
-- Caso real: transferencia bancaria que requiere SERIALIZABLE
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Leer saldo actual
SELECT balance FROM accounts WHERE id = :from_account;
-- En READ COMMITTED: otro TX podría cambiar el saldo AQUÍ
-- y este TX no lo sabría hasta el COMMIT
-- En SERIALIZABLE: se detecta el conflicto y se hace rollback

UPDATE accounts SET balance = balance - :amount WHERE id = :from_account;
UPDATE accounts SET balance = balance + :amount WHERE id = :to_account;

COMMIT; -- Si hay conflicto serializable → ERROR, el cliente reintenta

-- ─────────────────────────────────────────────────────────
-- Deadlocks: cómo evitarlos sistemáticamente
-- TX1: UPDATE accounts WHERE id = 1, luego WHERE id = 2
-- TX2: UPDATE accounts WHERE id = 2, luego WHERE id = 1
-- → Deadlock garantizado si ocurren concurrentemente

-- Solución: SIEMPRE acceder a recursos en el mismo orden
-- Ordenar los IDs antes de la transacción:
-- ids = sorted([from_id, to_id])  → siempre en el mismo orden
-- UPDATE accounts WHERE id = ids[0] ... WHERE id = ids[1]
-- → Deadlock matemáticamente imposible

Migraciones sin Downtime: La Habilidad que Más Importa en Producción


  Expand-Contract Pattern: El único patrón seguro

  OBJETIVO: Renombrar columna 'user_name' a 'full_name' en 50M filas

  ❌ Forma naive (causa downtime):
  ALTER TABLE users RENAME COLUMN user_name TO full_name;
  → Bloquea la tabla durante la migración
  → En 50M filas: puede tomar minutos → downtime total

  ✓ Expand-Contract (zero downtime):

  FASE 1 — EXPAND (añadir nueva columna):
  ALTER TABLE users ADD COLUMN full_name VARCHAR(255);
  → No bloquea. La columna empieza NULL.
  → Deploy del código que escribe en AMBAS columnas
     (user_name Y full_name simultáneamente)

  FASE 2 — BACKFILL (migrar datos existentes):
  UPDATE users SET full_name = user_name
    WHERE full_name IS NULL
    LIMIT 1000;  ← en batches, no todo de una vez
  → Ejecutar en background, sin bloquear la tabla

  FASE 3 — SWITCH (el código lee de full_name):
  → Deploy del código que solo lee full_name
  → Verificar que nada usa user_name ya

  FASE 4 — CONTRACT (eliminar la columna vieja):
  ALTER TABLE users DROP COLUMN user_name;
  → Ahora sí es seguro — nadie la usa

  Total de downtime: CERO
  Tiempo total: días o semanas, pero sin impacto en usuarios

# Backfill en batches — nunca migrar millones de filas de una vez
async def backfill_full_name(batch_size: int = 1000):
    """
    Migra datos en batches pequeños para:
    - No bloquear la tabla
    - Poder pausar y reanudar
    - No llenar el WAL de PostgreSQL
    - No causar spike de carga en la BD
    """
    last_id = 0
    total_migrated = 0

    while True:
        # Batch: solo filas pendientes (full_name NULL) y en orden
        rows = await db.fetch(
            """UPDATE users
               SET full_name = user_name
               WHERE id IN (
                 SELECT id FROM users
                 WHERE full_name IS NULL AND id > $1
                 ORDER BY id LIMIT $2
               )
               RETURNING id""",
            last_id, batch_size
        )
        if not rows:
            break  # Backfill completo

        last_id = max(row['id'] for row in rows)
        total_migrated += len(rows)

        # Pausa entre batches: dar respiro a la BD
        await asyncio.sleep(0.05)

        logger.info(f"Migrated {total_migrated} rows, last_id={last_id}")

    logger.info(f"Backfill complete: {total_migrated} total rows")

CAP. 07

Testing: Confianza, No Coverage

El objetivo del testing no es tener un número alto de coverage. Es tener la confianza de que el código hace lo que se supone que debe hacer, y la certeza de que si alguien lo cambia y algo se rompe, los tests lo detectarán. Un 95% de coverage con tests que nunca fallan aunque introduzcas bugs es peor que un 60% con tests que detectan regresiones reales.

Axioma de testing: Un test que nunca puede fallar es inútil. Un test que solo puede fallar cuando el código tiene un bug real — eso tiene valor. Antes de escribir un test, pregúntate: "¿De qué bug me protege este test?"

TDD como Herramienta de Diseño

TDD (Test-Driven Development) no es escribir tests antes del código por disciplina. Es usar los tests para diseñar la interfaz pública de tu código antes de implementarla. Cuando escribes el test primero, estás forzado a pensar desde el punto de vista del consumidor del código — lo que produce APIs más limpias y más usables.


  Red-Green-Refactor: El ciclo de TDD

  RED   → Escribir el test que describe el comportamiento deseado
          El test FALLA porque el código no existe aún
          Esto confirma que el test puede detectar el bug

  GREEN → Escribir el código MÁS SIMPLE posible que hace pasar el test
          No importa si es "feo" — el objetivo es pasar el test
          "Fake it till you make it" está permitido aquí

  REFACTOR → Con el test verde como red de seguridad,
             mejorar el código sin cambiar el comportamiento
             Si el test sigue verde, el refactor fue correcto

  Repetir para cada comportamiento nuevo.

  El beneficio real no es tener tests — es que el diseño
  emergente de escribir tests primero produce código
  más modular, más testeable, y más bajo acoplamiento.

  Señal de que el diseño es incorrecto: si es difícil
  escribir el test, la función tiene demasiadas dependencias.
  El dolor de testing es información de diseño.

from dataclasses import dataclass, field

@dataclass
class ValidationResult:
    is_valid: bool
    errors: list[str] = field(default_factory=list)

def validate_password(password: str) -> ValidationResult:
    errors = []
    if len(password) < 8:
        errors.append("Password must be at least 8 characters")
    if not any(c.isupper() for c in password):
        errors.append("Password must contain at least one uppercase letter")
    return ValidationResult(is_valid=len(errors) == 0, errors=errors)

CAP. 08

Performance y Escalabilidad

La regla de oro de la performance es una: medir antes de optimizar. La optimización prematura no es solo un desperdicio de tiempo — activamente empeora el código al añadir complejidad para resolver problemas que no existen o que no están donde asumes.

  Estrategias de Caching y Sus Trade-offs

  CACHE-ASIDE (más común):
  App → Cache hit? → Retornar
  App → Cache miss → BD → Guardar en cache → Retornar
  Pros: Solo cachea datos leídos, app controla el cache
  Cons: Cache miss = latencia extra, cold start lento

  READ-THROUGH:
  App → Cache (que consulta la BD si necesario) → Retornar
  Pros: Transparente para la app
  Cons: Cache debe soportar la lógica de lectura de BD

  WRITE-THROUGH:
  App → Cache → BD (síncronamente)
  Pros: Cache siempre actualizado
  Cons: Latencia de escritura mayor, cachea datos poco leídos

  WRITE-BEHIND (write-back):
  App → Cache → Retornar inmediatamente
  BD actualizada en batch asíncronamente
  Pros: Escrituras ultra-rápidas
  Cons: Riesgo de pérdida de datos si el cache muere antes del flush

Idempotencia: El Principio que Salva Datos


  Por qué los retries ocurren aunque el servidor respondió exitosamente

  Cliente                    Red                    Servidor
     │                        │                         │
     │──POST /payments──────►│──────────────────────►  │
     │                        │                         │ Procesa pago ✓
     │                        │◄─── Timeout / Drop ──   │ Envía 200 OK
     │                        │  (respuesta perdida)    │
     │   Timeout!             │                         │
     │──POST /payments──────►│──────────────────────►  │
     │  (retry)               │                         │ Procesa pago OTRA VEZ ❌
     │◄──────────────────────│◄────────────────────────│ 201 Created

  El cliente nunca recibió el 200 original.
  El servidor procesó el pago DOS veces.
  El cliente tiene razón al reintentar.
  El servidor tiene razón al procesar.
  Resultado: cobro duplicado.

  Solución: Idempotency Key
  El cliente genera un UUID antes del primer intento.
  Lo envía en cada retry con el MISMO UUID.
  El servidor: "¿Ya vi este UUID? → Retornar el resultado anterior."

// Implementación de idempotency keys en servidor
async function processPayment(
  req: Request,
  paymentData: PaymentDTO
): Promise<PaymentResult> {

  const idempotencyKey = req.headers['idempotency-key']
  if (!idempotencyKey) {
    throw new BadRequestError('Idempotency-Key header required')
  }

  // Verificar si ya procesamos esta operación
  const cached = await redis.get(`idempotency:payment:${idempotencyKey}`)
  if (cached) {
    // Retornar el resultado original — sin re-procesar
    return JSON.parse(cached) as PaymentResult
  }

  // Primer intento: procesar y guardar resultado
  const result = await paymentProvider.charge(paymentData)

  // Guardar por 24 horas (ventana de retries del cliente)
  await redis.setex(
    `idempotency:payment:${idempotencyKey}`,
    86400,
    JSON.stringify(result)
  )

  return result
}

// Cliente: generar la key ANTES del primer request
async function chargeWithRetry(paymentData: PaymentDTO): Promise<PaymentResult> {
  const idempotencyKey = crypto.randomUUID()  // Generado una vez

  for (let attempt = 0; attempt < 3; attempt++) {
    try {
      return await fetch('/payments', {
        method: 'POST',
        headers: {
          'Idempotency-Key': idempotencyKey,  // Misma key en cada retry
          'Content-Type': 'application/json'
        },
        body: JSON.stringify(paymentData)
      })
    } catch (error) {
      if (attempt === 2) throw error
      await sleep(Math.pow(2, attempt) * 1000)  // Exponential backoff
    }
  }
}

Retry con Backoff Exponencial y Circuit Breaker

# Retry con exponential backoff + jitter — el estándar de producción
import asyncio
import random
from typing import TypeVar, Callable

T = TypeVar('T')

async def retry_with_backoff(
    func: Callable[[], T],
    max_attempts: int = 3,
    base_delay: float = 1.0,
    max_delay: float = 30.0,
    retryable_exceptions: tuple = (ConnectionError, TimeoutError)
) -> T:
    """
    Exponential backoff con jitter:
    intento 1: espera 1s + random(0-0.5s)
    intento 2: espera 2s + random(0-1s)
    intento 3: espera 4s + random(0-2s)

    El jitter evita el "thundering herd": si 1000 clientes fallan
    al mismo tiempo y todos esperan exactamente 2s, el servidor
    recibe 1000 requests simultáneos al segundo 2 → otro fallo.
    Con jitter: los 1000 se distribuyen en una ventana de tiempo.
    """
    last_exception = None

    for attempt in range(max_attempts):
        try:
            return await func()
        except retryable_exceptions as e:
            last_exception = e
            if attempt == max_attempts - 1:
                break
            delay = min(base_delay * (2 ** attempt), max_delay)
            jitter = random.uniform(0, delay * 0.5)
            await asyncio.sleep(delay + jitter)

    raise last_exception

# Circuit Breaker: evitar llamadas a servicios que están caídos

from enum import Enum

class CircuitState(Enum):
    CLOSED = "closed"       # Normal: deja pasar las llamadas
    OPEN = "open"           # Fallo: rechaza inmediatamente
    HALF_OPEN = "half_open" # Probando: deja pasar una llamada

class CircuitBreaker:
    def __init__(self, failure_threshold=5, recovery_timeout=60):
        self.state = CircuitState.CLOSED
        self.failure_count = 0
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.last_failure_time = None

    async def call(self, func):
        if self.state == CircuitState.OPEN:
            if self._should_attempt_recovery():
                self.state = CircuitState.HALF_OPEN
            else:
                raise CircuitOpenError("Circuit is OPEN — service unavailable")
        try:
            result = await func()
            self._on_success()
            return result
        except Exception as e:
            self._on_failure()
            raise

    def _on_success(self):
        self.failure_count = 0
        self.state = CircuitState.CLOSED

    def _on_failure(self):
        self.failure_count += 1
        self.last_failure_time = time.time()
        if self.failure_count >= self.failure_threshold:
            self.state = CircuitState.OPEN
Conexión técnica

Los patrones de sistemas distribuidos del día a día implementan principios arquitectónicos fundamentales: la idempotencia hace posible el at-least-once delivery seguro. El circuit breaker es el patrón que implementa la resiliencia y tolerancia a fallos a nivel de código. El exponential backoff con jitter evita el thundering herd que puede convertir un fallo temporal en un fallo total en cascada.

Sin estas habilidades, el conocimiento técnico queda atrapado en silos.

Desarrollo Profesional

La carrera de un ingeniero de software es una serie de aprendizajes que, si se hacen bien, produce compuesto. Cada tecnología aprendida transfiere conocimiento a la siguiente. Cada sistema construido calibra mejor el juicio para el siguiente. Pero esto solo ocurre con intencionalidad — no por el simple paso del tiempo.

Cómo Aprender Tecnologías Nuevas sin Perderse


  El Framework de Aprendizaje de Tecnologías

  NIVEL 1 — CONCEPTUAL (1-2 horas):
  ¿Qué problema resuelve esta tecnología?
  ¿Por qué existe? ¿Qué hacía la gente antes?
  ¿Cuáles son sus trade-offs fundamentales?
  → Leer el README oficial, el "Why we built X" del autor

  NIVEL 2 — TUTORIAL (1 día):
  Seguir el tutorial oficial de principio a fin.
  No saltar secciones. No adaptar a tu caso de uso todavía.
  El objetivo: entender la forma de pensar de la tecnología,
  no construir algo útil.

  NIVEL 3 — PROYECTO PEQUEÑO (1 semana):
  Construir algo pequeño pero completo con la tecnología.
  Un proyecto que resuelva un problema real (aunque trivial).
  Encuentras los edge cases que el tutorial no muestra.
  El debugging te enseña más que el tutorial.

  NIVEL 4 — PRODUCCIÓN (meses):
  Operar la tecnología bajo carga real.
  Incidentes, migraciones, degradaciones de performance.
  Este nivel tarda años en acumularse para una tecnología.
  La mayoría de los "expertos" reales están en este nivel.

  Trampa común: confundir Nivel 2 con Nivel 4.
  "Hice el tutorial de Kubernetes" ≠ "sé Kubernetes"

La Diferencia entre Experiencia y Antigüedad

Antigüedad (tiempo sin aprendizaje)

  • 5 años haciendo el mismo tipo de trabajo
  • Soluciones basadas en "siempre lo hicimos así"
  • Resistencia a tecnologías o patrones nuevos
  • Conocimiento profundo de una tecnología específica
  • No puede explicar el "por qué" de sus decisiones
  • Su valor es el contexto histórico del sistema

Experiencia (ciclos de aprendizaje deliberado)

  • Múltiples tecnologías, dominios, y tipos de sistema
  • Decisiones basadas en trade-offs documentados
  • Adopta lo nuevo cuando el contexto lo justifica
  • Conocimiento transferible entre tecnologías
  • Puede defender sus decisiones con razonamiento
  • Su valor es el criterio aplicable a problemas nuevos

Cómo Evaluar si una Empresa Tiene Cultura Técnica Real

Antes de aceptar una oferta, hay preguntas que revelan la cultura técnica real de una empresa — no la que describen en la página de careers.

Pregunta a hacer Respuesta que indica cultura sana Red flag
"¿Cuándo fue el último incidente de producción significativo y qué aprendieron?" Describen el incidente con detalle, mencionan el postmortem y las acciones tomadas "No tenemos muchos incidentes" o respuesta vaga sin postmortem
"¿Cómo se toman las decisiones técnicas importantes?" ADRs, RFCs, discusiones técnicas abiertas, consenso del equipo "El arquitecto principal decide" o "el CTO decide"
"¿Con qué frecuencia hacen deploys a producción?" Daily o múltiples veces al día con feature flags "Tenemos una release mensual" o "el deploy es complejo"
"¿Cómo manejan la deuda técnica?" Parte del sprint, refinamiento continuo, backlog priorizado "La vamos a limpiar en el próximo sprint" (desde hace 2 años)
"¿Puedo hablar con alguien del equipo fuera del proceso formal?" Sí, conectan con un IC (Individual Contributor) sin filtros No, o solo con el manager/líder técnico presente

Entrevistas Técnicas: Desde Ambos Lados

Como candidato: mostrar el proceso

Los entrevistadores no evalúan si llegas a la solución correcta — evalúan cómo piensas. Preguntar sobre constraints, mencionar trade-offs en voz alta, y explicar por qué eliges un approach sobre otro es más valioso que la solución óptima en silencio.

Como candidato: preguntar es una señal de fortaleza

"¿Qué escala de datos estamos asumiendo?" y "¿Cuáles son los requerimientos de consistencia?" son preguntas que hacen los seniors antes de escribir código. Si el entrevistador las ve como debilidad, eso dice más sobre el entrevistador que sobre el candidato.

Como entrevistador: evaluar lo que importa

La capacidad de memorizar algoritmos es un proxy pobre de la ingeniería real. Mejores señales: cómo descompone problemas ambiguos, cómo maneja el feedback durante la entrevista, cómo razona sobre trade-offs, y si puede comunicar sus ideas con claridad.

Anti-pattern como entrevistador: gotcha questions

Preguntas de trivia que solo alguien que memorizó la respuesta puede responder. Revelan si el candidato leyó ese artículo específico — no si puede pensar bien bajo presión. Producen falsos negativos en candidatos excelentes y falsos positivos en quienes memorizaron las preguntas de Glassdoor.

Conexión técnica

El desarrollo profesional es lo que hace que todos los capítulos anteriores sean transferibles. Un ingeniero que aprendió principios (SOLID, trade-offs, diseño de sistemas) puede aplicarlos a tecnologías nuevas. Uno que solo aprendió herramientas específicas necesita empezar de cero con cada nueva tecnología. La inversión en fundamentos tiene el mayor retorno compuesto en una carrera de ingeniería.

Complejidad Algorítmica: Lo que Realmente Importa

Complejidad Nombre Ejemplo n=1M ¿Problema?
O(1) Constante HashMap get, array index 1 op Nunca
O(log n) Logarítmica Binary search, B-Tree lookup ~20 ops Nunca
O(n) Lineal Array scan, linked list 1M ops Rara vez
O(n log n) Linearítmica Merge sort, heap sort ~20M ops A veces
O(n²) Cuadrática Bubble sort, nested loops 1T ops Sí — revisar
O(2ⁿ) Exponencial Recursive fib sin memo ∞ efectivo Siempre

Regla práctica: O(n²) con n > 10,000 necesita revisión. O(n) con n > 10M puede necesitar optimización. La complejidad importa cuando los datos crecen — siempre preguntar "¿qué tan grande puede ser n en producción?"

Git Avanzado: Los Comandos que Salvan Incidentes

# Encontrar qué commit introdujo un bug (bisect)
git bisect start
git bisect bad                     # El commit actual tiene el bug
git bisect good v2.1.0             # Este tag estaba bien
# Git hace checkout de commits intermedios automáticamente
# Tú ejecutas los tests y marcas: git bisect good / git bisect bad
# En ~10 pasos encuentra el commit exacto en miles de commits
git bisect reset                   # Volver al HEAD original

# Reescribir historia de commits antes de merge (interactive rebase)
git rebase -i HEAD~5               # Últimos 5 commits
# pick → mantener, squash → combinar, reword → editar mensaje
# fixup → combinar sin mensaje, drop → eliminar

# Recuperar código eliminado accidentalmente
git reflog                         # Historial de todos los HEAD
git checkout HEAD@{2}              # Volver al estado de hace 2 operaciones

# Guardar trabajo en progreso rápidamente
git stash push -m "WIP: payment form validation"
git stash list
git stash pop stash@{0}

# Cherry-pick: aplicar un commit específico a otra rama
git cherry-pick abc1234            # Aplica solo ese commit
# Útil para: hotfixes que van a main Y a la rama de release

# Ver qué línea introdujo un bug (blame con movimiento de código)
git log -S "bug_function_name" --all   # Busca en el diff de cada commit
git log --all --full-history -- "path/to/deleted/file.py"  # Archivo eliminado

El Checklist Antes de ir a Producción

## Pre-deploy Checklist

### Código
- [ ] Tests pasan localmente Y en CI
- [ ] No hay console.log / print / debug statements
- [ ] No hay secrets hardcodeados (API keys, passwords)
- [ ] Las migraciones de BD son backward compatible (Expand, no Rename)
- [ ] Los feature flags están configurados correctamente

### Performance
- [ ] Las nuevas queries tienen EXPLAIN ANALYZE revisado
- [ ] No hay N+1 queries introducidos
- [ ] Los endpoints nuevos tienen paginación si retornan listas

### Seguridad
- [ ] El input del usuario está validado y sanitizado
- [ ] Los endpoints nuevos tienen autorización correcta
- [ ] No hay IDOR en accesos a recursos por ID

### Operabilidad
- [ ] Los nuevos endpoints están en los dashboards de monitoreo
- [ ] Los errores nuevos tienen alertas configuradas
- [ ] El runbook está actualizado si el comportamiento cambia
- [ ] El rollback está planeado: ¿cómo revertir si algo falla?

### Comunicación
- [ ] El equipo está informado del deploy
- [ ] El cliente/stakeholder está informado si hay cambio de comportamiento
- [ ] El on-call sabe qué buscar en las próximas 2 horas post-deploy

Comandos de Debugging en Producción

# Debugging de red — verificar conectividad
curl -v -w "\n\nTime: %{time_total}s\nHTTP: %{http_code}\n" https://api.service.com/health
# -v muestra headers completos de request y response
# -w añade métricas de timing al output

# Ver conexiones activas de un proceso
ss -tlnp | grep :8080         # Qué está escuchando en el puerto 8080
lsof -p $(pgrep python) -i    # Conexiones del proceso Python

# CPU y memoria en tiempo real
top -p $(pgrep -d',' python)  # Solo los procesos Python
vmstat 1 10                    # Sistema cada 1s durante 10s

# Logs con contexto — encontrar errores con su contexto
journalctl -u myapp --since "10 minutes ago" | grep -A 5 "ERROR"
# -A 5: 5 líneas después del match (el stack trace)

# Ver qué hace un proceso en este momento (Linux)
strace -p $(pgrep myapp) -e trace=network,file  # Solo syscalls de red y archivo
