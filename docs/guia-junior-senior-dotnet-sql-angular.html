Junior Fundamentos del lenguaje y la plataforma
Tipos de valor vs. Tipos de referencia
value types · reference types · stack vs heap
▾

Los value types (int, bool, struct, enum) viven en el stack y se copian al asignarse. Los reference types (class, string, arrays) viven en el heap y la variable guarda una referencia. Esto afecta el comportamiento al pasar parámetros y comparar igualdad.

Stack: memoria rápida y ordenada (LIFO). Heap: memoria dinámica gestionada por el GC. Los value types en el stack no tienen overhead de GC.
C#
// Value type — se copia
int a = 10;
int b = a;
b = 20;
Console.WriteLine(a); // 10 — no cambia

// Reference type — apuntan al mismo objeto
var lista1 = new List<int> { 1, 2, 3 };
var lista2 = lista1;
lista2.Add(4);
Console.WriteLine(lista1.Count); // 4 — sí cambia

// Struct (value type personalizado)
struct Punto { public int X, Y; }
Punto p1 = new() { X = 1, Y = 2 };
Punto p2 = p1; // copia completa
💡 Usa record struct en .NET 6+ para value types inmutables con igualdad por valor automática. Ideal para coordenadas, money, IDs tipados.
async / await y el modelo de tareas
Task · async/await · no bloquear el thread
▾

async/await permite escribir código asíncrono con sintaxis síncrona. Task representa una operación que puede completarse en el futuro. El objetivo es liberar el thread mientras espera I/O (base de datos, HTTP, disco) en lugar de bloquearlo.

C#
// ❌ Bloqueante — ocupa el thread esperando
public Usuario ObtenerUsuario(int id)
{
    return _db.Usuarios.FirstOrDefault(u => u.Id == id);
}

// ✅ Asíncrono — libera el thread
public async Task<Usuario?> ObtenerUsuarioAsync(int id)
{
    return await _db.Usuarios
        .FirstOrDefaultAsync(u => u.Id == id);
}

// Llamar múltiples tareas en paralelo
var (usuario, pedidos) = await (
    ObtenerUsuarioAsync(id),
    ObtenerPedidosAsync(id)
).WhenAll();  // ambas en paralelo
⚠️ Nunca uses .Result o .Wait() en código async — puede causar deadlocks en ASP.NET. Siempre propaga el await hacia arriba.
Inyección de Dependencias (DI)
IoC container · Transient · Scoped · Singleton
▾

La DI desacopla clases de sus dependencias. En lugar de que OrderService cree su propio EmailService, el contenedor lo inyecta. ASP.NET Core tiene un contenedor incorporado que gestiona el ciclo de vida: Transient (nueva instancia por uso), Scoped (una por request HTTP), Singleton (una por toda la vida de la app).

C# · Program.cs
// Registro en el contenedor
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<IEmailSender, SmtpEmailSender>();
builder.Services.AddTransient<IValidator<OrderDto>, OrderValidator>();

// Consumo vía constructor
public class OrderController(IOrderService orderService) : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Create(OrderDto dto)
    {
        var result = await orderService.CreateAsync(dto);
        return Ok(result);
    }
}
💡 Regla de oro: Scoped para casi todo (servicios, repos). Singleton solo para estado compartido thread-safe (cache, config). Transient para objetos ligeros sin estado.
LINQ — Language Integrated Query
IEnumerable · deferred execution · method syntax
▾

LINQ permite consultar colecciones e IQueryable (EF Core) con sintaxis fluida. Tiene ejecución diferida: la query no se ejecuta hasta que iteras el resultado (ToList(), FirstOrDefault()). Sobre IQueryable se traduce a SQL; sobre IEnumerable se ejecuta en memoria.

C#
// Sobre IEnumerable (en memoria)
var productos = _productos
    .Where(p => p.Precio > 100)
    .OrderByDescending(p => p.Precio)
    .Select(p => new { p.Nombre, p.Precio })
    .Take(10)
    .ToList();

// Sobre IQueryable (genera SQL)
var query = _db.Pedidos
    .Where(p => p.FechaCreacion >= DateTime.Today.AddDays(-30))
    .Include(p => p.Items)
    .GroupBy(p => p.ClienteId)
    .Select(g => new {
        ClienteId = g.Key,
        Total = g.Sum(p => p.Total),
        Cantidad = g.Count()
    });

// La query aún no ejecuta — solo al llamar ToList()
var resultado = await query.ToListAsync();
Mid Patrones, arquitectura y Entity Framework
Clean Architecture
Domain · Application · Infrastructure · Presentation
▾

Organiza el código en capas concéntricas donde las dependencias solo apuntan hacia adentro. El dominio no conoce nada externo. La aplicación orquesta casos de uso. La infraestructura implementa interfaces del dominio. La presentación (API) es el punto de entrada.

C# · Estructura de proyecto
// Domain/Entities/Order.cs — sin dependencias externas
public class Order
{
    public Guid Id { get; private set; }
    public Money Total { get; private set; }
    private readonly List<OrderItem> _items = [];

    public void AddItem(Product product, int qty)
    {
        if (qty <= 0) throw new DomainException("Qty inválida");
        _items.Add(new OrderItem(product, qty));
        Total = _items.Sum(i => i.Subtotal);
    }
}

// Application/UseCases/CreateOrder/CreateOrderCommand.cs
public record CreateOrderCommand(Guid ClienteId, List<OrderItemDto> Items)
    : IRequest<OrderDto>;

// Infrastructure/Persistence/OrderRepository.cs
public class OrderRepository(AppDbContext db) : IOrderRepository
{
    public async Task SaveAsync(Order order) =>
        await db.SaveChangesAsync();
}

Entity Framework Core — avanzado
Change Tracker · N+1 · AsNoTracking · Owned entities
▾

El problema N+1 ocurre cuando una query carga N entidades y luego hace 1 query adicional por cada una para cargar relaciones. Solución: Include(). Para queries de solo lectura, AsNoTracking() elimina el overhead del Change Tracker (~30% más rápido).

C#
// ❌ Problema N+1 — 1 query + N queries de Items
var ordenes = await _db.Orders.ToListAsync();
foreach (var o in ordenes)
    Console.WriteLine(o.Items.Count); // lazy load por cada orden

// ✅ Eager loading — 1 query con JOIN
var ordenes = await _db.Orders
    .Include(o => o.Items)
        .ThenInclude(i => i.Product)
    .AsNoTracking()   // sin change tracking
    .ToListAsync();

// Owned Entity — value object en EF Core
public class Order
{
    public Address ShippingAddress { get; set; }  // Owned
}
// En DbContext:
modelBuilder.Entity<Order>().OwnsOne(o => o.ShippingAddress);
💡 Usa AsNoTracking() en todas las queries de lectura (GET endpoints). Solo omítelo cuando vayas a modificar las entidades cargadas.
Middleware Pipeline en ASP.NET Core
Use · Run · Map · orden importa
▾

El pipeline es una cadena de middlewares que procesan cada request en orden. Cada middleware puede procesar la request, pasarla al siguiente (next()), o cortocircuitar la cadena. El orden de registro es crítico: Authentication debe ir antes de Authorization.

C# · Program.cs
// Orden correcto del pipeline
app.UseExceptionHandler("/error");  // 1. Siempre primero
app.UseHttpsRedirection();
app.UseStaticFiles();
app.UseRouting();
app.UseAuthentication();            // 2. Auth antes que Authz
app.UseAuthorization();
app.MapControllers();

// Middleware personalizado
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);  // pasa al siguiente
    _logger.LogInformation("Request: {ms}ms", sw.ElapsedMilliseconds);
});
Senior CQRS, performance y diseño robusto
CQRS + MediatR
Command · Query · Handler · PipelineBehavior
▾

CQRS (Command Query Responsibility Segregation) separa operaciones de escritura (Commands) de lectura (Queries). MediatR implementa el patrón Mediator: en lugar de llamar servicios directamente, lanzas un mensaje y el Handler apropiado lo procesa. Los PipelineBehaviors son middlewares para tus handlers (validación, logging, retry).

C#
// Command — escribe, devuelve resultado
public record CreateProductCommand(
    string Nombre, decimal Precio) : IRequest<Guid>;

// Handler
public class CreateProductHandler(
    IProductRepository repo) : IRequestHandler<CreateProductCommand, Guid>
{
    public async Task<Guid> Handle(
        CreateProductCommand cmd, CancellationToken ct)
    {
        var product = Product.Create(cmd.Nombre, cmd.Precio);
        await repo.AddAsync(product, ct);
        return product.Id;
    }
}

// PipelineBehavior — validación automática
public class ValidationBehavior<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(
        TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct)
    {
        var errors = validators
            .Select(v => v.Validate(request))
            .SelectMany(r => r.Errors)
            .ToList();
        if (errors.Count > 0)
            throw new ValidationException(errors);
        return await next();
    }
}
Result Pattern — sin excepciones para flujos de negocio
Result<T> · Error · Railway-oriented
▾

Las excepciones son costosas (generan stack traces) y no deben usarse para flujo de negocio esperado (ej: "usuario no encontrado"). El Result Pattern retorna explícitamente éxito o error, haciendo el contrato del método honesto y el código más legible.

C#
// Tipo Result genérico
public record Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public Error? Err { get; }

    public static Result<T> Ok(T value) => new(value, null);
    public static Result<T> Fail(Error error) => new(default, error);
}

// Uso en un servicio
public async Task<Result<UserDto>> GetUserAsync(int id)
{
    var user = await _repo.FindAsync(id);
    if (user is null)
        return Result<UserDto>.Fail(Errors.UserNotFound);
    return Result<UserDto>.Ok(_mapper.Map<UserDto>(user));
}

// En el controller — mapeo a HTTP
var result = await _mediator.Send(new GetUserQuery(id));
return result.IsSuccess ? Ok(result.Value) : NotFound(result.Err);
Performance: Span<T> y reducción de allocations
Span · stackalloc · object pooling · GC pressure
▾

Span<T> es una vista sobre memoria existente (array, stack, memoria nativa) sin copiarla. Reduce drásticamente las allocations en hot paths, disminuyendo la presión sobre el GC y mejorando la latencia en código de alto rendimiento.

C#
// ❌ Crea un string intermedio en heap
string input = "2024-01-15";
int year = int.Parse(input.Substring(0, 4));

// ✅ Zero allocation — Span es solo una vista
int year = int.Parse(input.AsSpan(0, 4));

// Object Pool — reutilizar objetos costosos
private readonly ObjectPool<StringBuilder> _pool =
    new DefaultObjectPool<StringBuilder>(new StringBuilderPooledObjectPolicy());

public string BuildMessage(IEnumerable<string> parts)
{
    var sb = _pool.Get();
    try
    {
        foreach (var p in parts) sb.Append(p);
        return sb.ToString();
    }
    finally { _pool.Return(sb); }
}
💡 Usa BenchmarkDotNet para medir antes de optimizar. Las optimizaciones prematuras son costosas. Mide primero con [MemoryDiagnoser] para ver allocations reales.
Lead / Arch Microservicios y diseño de sistemas
Outbox Pattern — mensajes confiables
exactly-once · at-least-once · transactional outbox
▾

El problema: guardar en DB y publicar un evento en un bus de mensajes no es atómico. Si el sistema falla entre los dos, el evento se pierde. La solución: guardar el evento dentro de la misma transacción en una tabla Outbox, y un proceso separado lo publica al bus.

C#
// 1. Guardar orden + mensaje en la misma transacción
await using var tx = await _db.BeginTransactionAsync();

_db.Orders.Add(order);
_db.OutboxMessages.Add(new OutboxMessage
{
    Type = "OrderCreated",
    Payload = JsonSerializer.Serialize(new OrderCreatedEvent(order.Id)),
    CreatedAt = DateTime.UtcNow
});

await _db.SaveChangesAsync(); // atómico
await tx.CommitAsync();

// 2. Worker publica mensajes pendientes (Background Service)
var pending = await _db.OutboxMessages
    .Where(m => m.PublishedAt == null)
    .OrderBy(m => m.CreatedAt)
    .Take(50)
    .ToListAsync();

foreach (var msg in pending)
{
    await _bus.PublishAsync(msg.Type, msg.Payload);
    msg.PublishedAt = DateTime.UtcNow;
}
await _db.SaveChangesAsync();
⚠️ El Outbox garantiza at-least-once delivery. Los consumidores deben ser idempotentes (procesar el mismo mensaje dos veces debe ser seguro).
Circuit Breaker con Polly
resiliencia · retry · fallback · timeout
▾

El patrón Circuit Breaker protege un servicio de cascada de fallos: si un servicio downstream falla repetidamente, el circuito se "abre" y las siguientes llamadas fallan rápido en lugar de esperar el timeout. Polly es la librería estándar para esto en .NET.

C# · Polly v8 / Microsoft.Extensions.Http.Resilience
// Configuración de resiliencia para HttpClient builder.Services.AddHttpClient<IPaymentService, PaymentService>() .AddResilienceHandler("payment-pipeline", pipeline => { pipeline.AddRetry(new HttpRetryStrategyOptions { MaxRetryAttempts = 3, Delay = TimeSpan.FromMilliseconds(200), BackoffType = DelayBackoffType.Exponential }); pipeline.AddCircuitBreaker(new HttpCircuitBreakerStrategyOptions { FailureRatio = 0.5, // abre si 50% falla SamplingDuration = TimeSpan.FromSeconds(30), MinimumThroughput = 10, // mínimo de calls para evaluar BreakDuration = TimeSpan.FromSeconds(60) }); pipeline.AddTimeout(TimeSpan.FromSeconds(5)); });

Junior SQL esencial y T-SQL básico
JOINs — tipos y cuándo usar cada uno
INNER · LEFT · RIGHT · FULL OUTER · CROSS
▾

INNER JOIN: solo filas que tienen coincidencia en ambas tablas. LEFT JOIN: todas las filas de la izquierda, con NULL donde no hay coincidencia en la derecha. El tipo más usado en la práctica. RIGHT JOIN: igual pero al revés (evitable reescribiendo como LEFT). FULL OUTER JOIN: todos los registros de ambas tablas.

T-SQL
-- INNER JOIN: solo clientes que tienen pedidos SELECT c.Nombre, COUNT(p.Id) AS TotalPedidos FROM Clientes c INNER JOIN Pedidos p ON c.Id = p.ClienteId GROUP BY c.Nombre; -- LEFT JOIN: TODOS los clientes, con 0 si no tienen pedidos SELECT c.Nombre, COUNT(p.Id) AS TotalPedidos FROM Clientes c LEFT JOIN Pedidos p ON c.Id = p.ClienteId GROUP BY c.Nombre; -- Encontrar clientes SIN pedidos (anti-join) SELECT c.Nombre FROM Clientes c LEFT JOIN Pedidos p ON c.Id = p.ClienteId WHERE p.Id IS NULL; -- filas sin coincidencia
Stored Procedures y funciones
sp · UDF · TVF · parámetros de salida
▾

Los Stored Procedures son bloques de T-SQL compilados en el servidor. Las funciones escalares devuelven un valor; las funciones de tabla (TVF) devuelven un conjunto de filas y son muy útiles para reutilizar lógica de consulta.

T-SQL
-- Stored Procedure con parámetros
CREATE OR ALTER PROCEDURE usp_GetOrdersByClient
    @ClienteId  INT,
    @FechaDesde DATE = NULL
AS
BEGIN
    SET NOCOUNT ON;

    SELECT
        p.Id,
        p.Total,
        p.FechaCreacion,
        c.Nombre AS Cliente
    FROM Pedidos p
    INNER JOIN Clientes c ON c.Id = p.ClienteId
    WHERE p.ClienteId = @ClienteId
      AND (@FechaDesde IS NULL OR p.FechaCreacion >= @FechaDesde)
    ORDER BY p.FechaCreacion DESC;
END;

-- Table-Valued Function reutilizable
CREATE FUNCTION fn_GetTopProducts(@n INT)
RETURNS TABLE AS RETURN
(
    SELECT TOP (@n) Id, Nombre, Ventas
    FROM Productos
    ORDER BY Ventas DESC
);
💡 Siempre incluye SET NOCOUNT ON en stored procedures para evitar que se envíen mensajes de "N rows affected" innecesarios que pueden afectar el rendimiento.
Mid Índices, transacciones y concurrencia
Índices: Clustered vs Non-Clustered
B-Tree · Seek vs Scan · Include columns · covering index
▾

El Clustered Index determina el orden físico de los datos en disco (solo puede haber uno por tabla; suele ser la PK). Los Non-Clustered Index son estructuras B-Tree separadas que apuntan a la fila. Un Covering Index incluye todas las columnas necesarias para satisfacer una query sin ir a la tabla base (seek eficiente).

T-SQL
-- Non-clustered con included columns (covering index) -- Query frecuente: filtrar por ClienteId, mostrar Total y Fecha CREATE NONCLUSTERED INDEX IX_Pedidos_ClienteId ON Pedidos (ClienteId) INCLUDE (Total, FechaCreacion); -- Las columnas de INCLUDE no son parte del key, -- pero SQL Server las guarda en las hojas del índice, -- evitando un Key Lookup a la tabla base. -- Ver el Execution Plan para diagnosticar SET STATISTICS IO ON; SELECT ClienteId, SUM(Total) FROM Pedidos WHERE ClienteId = 42 GROUP BY ClienteId; -- Buscar: Index Seek (bueno) vs Table Scan (malo) -- Índice filtrado — solo para estados activos CREATE NONCLUSTERED INDEX IX_Pedidos_Activos ON Pedidos (FechaCreacion) WHERE Estado = 'Activo'; -- mucho más pequeño
💡 Demasiados índices ralentizan los INSERT/UPDATE/DELETE porque todos deben actualizarse. Cada índice tiene un costo de mantenimiento. Crea índices basados en queries reales, no por intuición.
Transacciones y niveles de aislamiento
ACID · READ COMMITTED · SNAPSHOT · Deadlock
▾

ACID garantiza integridad: Atomicity (todo o nada), Consistency (reglas siempre válidas), Isolation (transacciones no se interfieren), Durability (lo guardado persiste). Los niveles de aislamiento controlan qué tan estricta es esa I: más estricto = más consistencia pero más bloqueos.

T-SQL
-- READ COMMITTED (default): lee solo datos confirmados
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

-- SNAPSHOT: lecturas consistentes sin bloquear escrituras
-- Requiere habilitarlo en la DB primero:
ALTER DATABASE MiDB SET ALLOW_SNAPSHOT_ISOLATION ON;
SET TRANSACTION ISOLATION LEVEL SNAPSHOT;

-- Transacción explícita para operaciones múltiples
BEGIN TRANSACTION;
BEGIN TRY
    UPDATE CuentaBancaria SET Saldo -= 100 WHERE Id = 1;
    UPDATE CuentaBancaria SET Saldo += 100 WHERE Id = 2;
    COMMIT TRANSACTION;
END TRY
BEGIN CATCH
    ROLLBACK TRANSACTION;
    THROW;
END CATCH;
⚠️ Los deadlocks ocurren cuando dos transacciones se esperan mutuamente. Solución: acceder siempre a las tablas en el mismo orden, mantener transacciones cortas, y habilitar SNAPSHOT Isolation para lecturas.
CTEs y Window Functions
WITH · ROW_NUMBER · RANK · LAG/LEAD · PARTITION BY
▾

Las CTEs (Common Table Expressions) hacen las queries más legibles dividiéndolas en partes nombradas. Las Window Functions calculan sobre un conjunto de filas relacionadas sin colapsar el resultado como GROUP BY.

T-SQL
-- CTE para query legible
WITH PedidosPorCliente AS (
    SELECT ClienteId, SUM(Total) AS TotalAnual
    FROM  Pedidos
    WHERE YEAR(FechaCreacion) = 2024
    GROUP BY ClienteId
),
Ranking AS (
    SELECT *, RANK() OVER (ORDER BY TotalAnual DESC) AS Posicion
    FROM  PedidosPorCliente
)
SELECT c.Nombre, r.TotalAnual, r.Posicion
FROM  Ranking r
JOIN  Clientes c ON c.Id = r.ClienteId
WHERE r.Posicion <= 10;

-- Window function: comparar con mes anterior
SELECT
    Mes,
    Ventas,
    LAG(Ventas) OVER (ORDER BY Mes) AS VentasMesAnterior,
    Ventas - LAG(Ventas) OVER (ORDER BY Mes) AS Diferencia
FROM VentasMensuales;
Senior Query tuning y diseño escalable
Execution Plans — leer e interpretar
Table Scan · Index Seek · Key Lookup · Estimated vs Actual
▾

El Execution Plan muestra cómo SQL Server ejecuta una query. Los operadores se leen de derecha a izquierda, arriba a abajo. El grosor de las flechas indica el volumen de datos. Los warnings (iconos amarillos) señalan problemas. Estimated rows vs Actual rows: una gran diferencia indica estadísticas desactualizadas.

T-SQL
-- Ver plan estimado (no ejecuta)
SET SHOWPLAN_XML ON;

-- Ver plan real (ejecuta la query)
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Query que genera Key Lookup (problema)
SELECT Nombre, Email, Telefono
FROM Clientes
WHERE Ciudad = 'Madrid';
-- Si Ciudad tiene índice pero Email/Telefono no están incluidas,
-- habrá un Key Lookup por cada fila — caro.

-- Solución: Covering Index
CREATE INDEX IX_Clientes_Ciudad ON Clientes(Ciudad)
INCLUDE (Nombre, Email, Telefono);

-- Query Store: ver queries regresadas en performance
SELECT TOP 10 qt.query_sql_text, qs.avg_duration
FROM sys.query_store_query_text qt
JOIN sys.query_store_plan qp ON qt.query_text_id = qp.query_text_id
JOIN sys.query_store_runtime_stats qs ON qp.plan_id = qs.plan_id
ORDER BY qs.avg_duration DESC;
Table Scan = malo Index Seek = bueno Key Lookup = optimizable Hash Match = JOIN sin índice Nested Loop = JOINs pequeños
Parameter Sniffing
plan cache · OPTION RECOMPILE · optimize for unknown
▾

SQL Server compila un plan de ejecución la primera vez que ejecuta un SP, basándose en los parámetros de esa primera llamada. Si esos parámetros son atípicos (ej: un cliente con millones de pedidos cuando la mayoría tiene 10), el plan queda "sniffed" y será malo para el resto de ejecuciones.

T-SQL
-- ❌ Vulnerable a Parameter Sniffing
CREATE PROCEDURE GetPedidosByCliente @ClienteId INT
AS
    SELECT * FROM Pedidos WHERE ClienteId = @ClienteId;

-- ✅ Solución 1: OPTION RECOMPILE (recompila cada vez)
--    Bueno para SPs que varían mucho en distribución
SELECT * FROM Pedidos WHERE ClienteId = @ClienteId
OPTION (RECOMPILE);

-- ✅ Solución 2: Variables locales (rompe el sniffing)
DECLARE @LocalId INT = @ClienteId;
SELECT * FROM Pedidos WHERE ClienteId = @LocalId;

-- ✅ Solución 3: OPTIMIZE FOR UNKNOWN
SELECT * FROM Pedidos WHERE ClienteId = @ClienteId
OPTION (OPTIMIZE FOR (@ClienteId UNKNOWN));
Temporal Tables
system-versioned · historial automático · point-in-time query
▾

Las Temporal Tables (SQL Server 2016+) registran automáticamente el historial de cambios de cada fila. SQL Server mantiene una tabla de historial paralela con las versiones anteriores. Ideal para auditoría, "undo", o consultas de "¿cómo era esto hace 6 meses?"

T-SQL
-- Crear tabla temporal CREATE TABLE Productos ( Id INT PRIMARY KEY, Nombre NVARCHAR(100), Precio DECIMAL(18,2), ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START, ValidTo DATETIME2 GENERATED ALWAYS AS ROW END, PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo) ) WITH (SYSTEM_VERSIONING = ON); -- Consultar estado en un punto del tiempo SELECT * FROM Productos FOR SYSTEM_TIME AS OF '2024-01-01 00:00:00'; -- Ver todos los cambios de un producto SELECT *, ValidFrom, ValidTo FROM Productos FOR SYSTEM_TIME ALL WHERE Id = 42 ORDER BY ValidFrom;
Lead / Arch Alta disponibilidad y arquitectura de datos
Always On Availability Groups
primary · secondary · failover · read scale-out
▾

Los Always On AG son el mecanismo de alta disponibilidad de SQL Server. Un primario sincroniza transacciones con uno o más secundarios. El failover automático mueve el rol primario si el nodo falla. Los secundarios pueden configurarse para lecturas (read scale-out), descargando queries pesadas del primario.

T-SQL · Connection String
-- Monitorear estado del AG SELECT ag.name AS AGNombre, rs.role_desc AS Rol, rs.synchronization_health_desc AS Salud, rs.log_send_queue_size AS ColaSinEnviar_KB FROM sys.dm_hadr_availability_replica_states rs JOIN sys.availability_groups ag ON rs.group_id = ag.group_id; -- Connection String para aplicaciones -- Escribe siempre en primario, lee en secundario Server=tcp:AGListener,1433; Database=MiDB; ApplicationIntent=ReadOnly; -- o ReadWrite MultiSubnetFailover=True; -- failover rápido ConnectTimeout=30;

Data Binding — los 4 tipos
interpolation · property · event · two-way
▾

Angular tiene cuatro formas de conectar el componente con la vista: Interpolación muestra valores. Property binding pasa datos al DOM. Event binding escucha eventos del DOM. Two-way binding sincroniza en ambas direcciones (típico en formularios).

Angular Template HTML
<!-- 1. Interpolación: Component → DOM (solo texto) -->
<h1>Hola, {{ usuario.nombre }}</h1>
<p>Total: {{ precio * cantidad | currency }}</p>

<!-- 2. Property binding: Component → DOM (cualquier prop) -->
<img [src]="usuario.avatar" [alt]="usuario.nombre">
<button [disabled]="!formulario.valid">Guardar</button>

<!-- 3. Event binding: DOM → Component -->
<button (click)="guardar()">Guardar</button>
<input (input)="onInput($event)">

<!-- 4. Two-way binding: sincronización bidireccional -->
<input [(ngModel)]="usuario.nombre">
<!-- Equivale a: -->
<input [ngModel]="usuario.nombre" (ngModelChange)="usuario.nombre = $event">
Comunicación entre componentes
@Input · @Output · EventEmitter · padre-hijo
▾

@Input() pasa datos del padre al hijo. @Output() con EventEmitter emite eventos del hijo al padre. Para comunicación entre componentes no relacionados, usar un servicio con Subject o BehaviorSubject.

TypeScript · Angular
@Component({ selector: 'app-producto', template: ` <div>{{ producto.nombre }} — {{ producto.precio | currency }}</div> <button (click)="agregar()">Agregar al carrito</button> ` }) export class ProductoComponent { @Input({ required: true }) producto!: Producto; @Output() agregado = new EventEmitter<Producto>(); agregar() { this.agregado.emit(this.producto); } } // En el padre: // <app-producto [producto]="item" (agregado)="onAgregado($event)">
Routing y Lazy Loading
RouterModule · loadComponent · Guards · ActivatedRoute
▾

El router de Angular gestiona la navegación SPA sin recargar la página. El Lazy Loading carga los módulos/componentes solo cuando el usuario navega a esa ruta, reduciendo el bundle inicial. Los Guards protegen rutas (autenticación, permisos).

TypeScript · app.routes.ts (Angular 17+)
export const routes: Routes = [ { path: '', redirectTo: '/home', pathMatch: 'full' }, // Lazy loading de standalone component { path: 'productos', loadComponent: () => import('./productos/productos.component') .then(m => m.ProductosComponent) }, // Ruta protegida con guard funcional { path: 'admin', canActivate: [authGuard], loadComponent: () => import('./admin/admin.component') .then(m => m.AdminComponent) } ]; // Guard funcional (Angular 15+) export const authGuard: CanActivateFn = () => { const auth = inject(AuthService); const router = inject(Router); return auth.isLoggedIn() || router.createUrlTree(['/login']); };
Mid RxJS, estado y formularios reactivos
RxJS — operadores esenciales
switchMap · mergeMap · combineLatest · takeUntilDestroyed
▾

RxJS gestiona flujos de datos asíncronos. switchMap cancela la petición anterior si llega una nueva (ideal para búsquedas). mergeMap no cancela, ejecuta todas en paralelo. combineLatest combina múltiples observables emitiendo cuando cualquiera cambia.

TypeScript · Angular
@Component({ ... }) export class BuscadorComponent { private destroyRef = inject(DestroyRef); productos$ = toObservable(this.searchTerm).pipe( debounceTime(300), distinctUntilChanged(), switchMap(term => // cancela búsqueda anterior term.length > 2 ? this._api.search(term) : of([]) ), takeUntilDestroyed(this.destroyRef) // auto-unsubscribe ); // Combinar múltiples fuentes vm$ = combineLatest({ usuario: this._auth.currentUser$, permisos: this._permisos.permisos$, config: this._config.config$ }).pipe( map(({ usuario, permisos, config }) => ({ nombre: usuario.nombre, puedeEditar: permisos.includes('editar'), theme: config.theme })) ); }
💡 Usa el async pipe en el template (*ngIf="vm$ | async as vm") — maneja la suscripción y desuscripción automáticamente. Es la forma más segura de consumir observables en templates.
Reactive Forms
FormGroup · FormControl · validators · FormBuilder
▾

Los Reactive Forms definen la estructura del formulario en TypeScript, no en el template. Esto da control total sobre validaciones, valores dinámicos, y hace el código testeable. Son la opción recomendada para formularios complejos.

TypeScript · Angular
export class RegistroComponent { private fb = inject(FormBuilder); form = this.fb.group({ nombre: ['', [Validators.required, Validators.minLength(3)]], email: ['', [Validators.required, Validators.email]], password: this.fb.group({ valor: ['', Validators.minLength(8)], confirmar: '' }, { validators: passwordsMatch }) // validator de grupo }); submit() { if (this.form.invalid) return; const data = this.form.getRawValue(); // data está completamente tipado } } // Custom validator const passwordsMatch: ValidatorFn = (group) => { const pass = group.get('valor')?.value; const confirm = group.get('confirmar')?.value; return pass === confirm ? null : { noCoinciden: true }; };
Senior Signals, performance y Angular moderno
Signals — reactividad granular
signal() · computed() · effect() · toSignal()
▾

Los Signals (Angular 17+) son el nuevo modelo de reactividad. A diferencia de los Observables, son síncronos y Angular sabe exactamente qué componentes dependen de cada signal. Esto permite actualizaciones quirúrgicas sin necesidad de Zone.js ni markForCheck().

TypeScript · Angular 17+
@Component({ template: ` <p>Contador: {{ contador() }}</p> <p>Doble: {{ doble() }}</p> <button (click)="incrementar()">+1</button> ` }) export class ContadorComponent { // Signal writable contador = signal(0); // Computed: se recalcula solo cuando contador cambia doble = computed(() => this.contador() * 2); incrementar() { this.contador.update(v => v + 1); // o: this.contador.set(this.contador() + 1); } } // Interop con RxJS private _usuario$ = inject(AuthService).currentUser$; usuario = toSignal(this._usuario$, { initialValue: null }); // Effect: código que corre cuando un signal cambia constructor() { effect(() => { console.log('Contador cambió a:', this.contador()); }); }
Change Detection OnPush
zona · markForCheck · immutability · performance
▾

Por defecto, Angular verifica todos los componentes en cada evento. Con OnPush, un componente solo se re-renderiza si sus @Input() cambian por referencia, si un observable emite, o si llamas markForCheck() manualmente. Esencial para apps de alto rendimiento.

TypeScript · Angular
@Component({ selector: 'app-lista-productos', changeDetection: ChangeDetectionStrategy.OnPush, template: ` @for (p of productos(); track p.id) { <app-producto [producto]="p" /> } ` }) export class ListaProductosComponent { // Signal como @Input — OnPush detecta el cambio productos = input.required<Producto[]>(); // Con Observable: usar async pipe + OnPush es la combinación ideal // El async pipe llama markForCheck() automáticamente } // ❌ Trampa: mutaciones no disparan OnPush this.productos.push(nuevoProducto); // NO actualiza la vista // ✅ Crear nueva referencia this.productos = [...this.productos, nuevoProducto];
💡 Con Signals + Standalone Components + OnPush, Angular puede eventualmente funcionar sin Zone.js (zoneless). Es la dirección del framework para el futuro.
Deferrable Views (@defer)
lazy rendering · @placeholder · @loading · interaction trigger
▾

El bloque @defer (Angular 17+) carga componentes de forma diferida directamente desde el template, con control de cuándo hacerlo (al hacer scroll, al interactuar, tras N ms) y qué mostrar mientras tanto.

Angular Template HTML
<!-- Cargar solo cuando el usuario llega a este elemento --> @defer (on viewport) { <app-grafico-complejo [data]="data" /> } @loading { <div class="skeleton">Cargando gráfico...</div> } @placeholder { <div>Haz scroll para ver el gráfico</div> } @error { <p>Error al cargar el gráfico</p> } <!-- Cargar al hacer hover --> @defer (on hover) { <app-detalle-producto [id]="productoId" /> } <!-- Cargar después de 2 segundos --> @defer (after 2s) { <app-chat-widget /> }
Lead / Arch Arquitectura frontend y Module Federation
Micro Frontends con Module Federation
shell · remote · shared · Nx workspace
▾

Module Federation (Webpack 5) permite que múltiples apps Angular se carguen en runtime compartiendo dependencias. Un shell carga remotes (otros deploys) como si fueran módulos locales. Cada equipo deploya su micro-frontend independientemente.

TypeScript · webpack.config.js (Shell)
const { ModuleFederationPlugin } = require('webpack/lib/container/ModuleFederationPlugin'); module.exports = { plugins: [ new ModuleFederationPlugin({ name: 'shell', remotes: { pedidos: 'pedidos@http://localhost:4201/remoteEntry.js', catalogo: 'catalogo@http://localhost:4202/remoteEntry.js' }, shared: { '@angular/core': { singleton: true, strictVersion: true }, '@angular/router': { singleton: true } } }) ] }; // En las routes del shell — lazy load de remote { path: 'pedidos', loadComponent: () => import('pedidos/PedidosComponent') .then(m => m.PedidosComponent) }
💡 Con Nx, gestionar un monorepo con múltiples apps Angular y librerías compartidas es mucho más manejable. Usa nx graph para visualizar dependencias y affected para solo buildear lo que cambió.
