01 — FUNDAMENTOS

Arquitectura de Software

🧱 Estilos Arquitectónicos Principales

Un estilo arquitectónico define la organización global del sistema: cómo se dividen los componentes, cómo se comunican y cuáles son los trade-offs de la decisión.

🏛️ Monolítico

Toda la funcionalidad se despliega como una sola unidad. Sencillo de desarrollar y debuggear inicialmente.

Cuándo usarlo

  • Equipos pequeños (< 10 devs)
  • Dominio poco entendido todavía
  • MVP o prototipo
  • Aplicaciones con bajo tráfico predecible

Desventajas

  • Escalado solo horizontal completo
  • Deploy de todo el sistema por cambio mínimo
  • Acoplamiento tecnológico
Junior

🔬 Microservicios

El sistema se divide en servicios pequeños, independientes, desplegables de forma autónoma, organizados en torno a capacidades de negocio.

Principios clave

  • Single Responsibility por servicio
  • Comunicación via APIs o mensajes
  • Base de datos por servicio (DB per service)
  • Despliegue independiente
  • Failure isolation

Cuándo NO usarlo

  • Equipo pequeño sin madurez operacional
  • Dominio no bien delimitado (riesgo: nano-servicios)
Senior

⚡ Event-Driven Architecture

Los componentes se comunican a través de eventos asíncronos. Alta desacoplamiento temporal y espacial.

Patrones internos

  • Event Notification: notifica que algo ocurrió
  • Event-Carried State Transfer: el evento lleva el estado completo
  • Event Sourcing: el estado es la secuencia de eventos
  • CQRS: separación de lectura y escritura

Herramientas

  • Apache Kafka, AWS SNS/SQS, Azure Service Bus, GCP Pub/Sub
Senior

☁️ Serverless

El proveedor cloud gestiona completamente la infraestructura. El código se ejecuta en respuesta a eventos.

Modelos

  • FaaS: AWS Lambda, Azure Functions, Cloud Run
  • BaaS: Firebase, Auth0, Stripe (lógica backend gestionada)

Trade-offs

  • ✅ No gestión de servidores, pago por uso
  • ❌ Cold starts, límites de ejecución, vendor lock-in
  • ❌ Debugging complejo, stateless by design
Mid

🎯 Principios SOLID

SOLID es un conjunto de 5 principios para diseño orientado a objetos que guían la creación de software mantenible, extensible y testeable. Como Arquitecto, los aplicas a nivel de módulos y servicios, no solo clases.

Principio Significado Aplicación en Arquitectura Nivel
SRP Single Responsibility — una clase/módulo = una razón para cambiar Microservicio por capacidad de negocio. Clase Square no debe calcular área Y mostrar output. Junior
OCP Open/Closed — abierto a extensión, cerrado a modificación Plugins, strategy pattern, feature flags en arquitectura Mid
LSP Liskov Substitution — subtipos sustituibles sin romper el sistema Contratos de API compatibles entre versiones (v1 → v2) Mid
ISP Interface Segregation — interfaces específicas por cliente APIs granulares; no exponer endpoints innecesarios Mid
DIP Dependency Inversion — depender de abstracciones, no implementaciones Service Mesh, abstracciones de storage, repositorio pattern Senior

📐 CAP Theorem

En un sistema distribuido, ante una partición de red (Partition Tolerance), debes elegir entre:

CP — Consistency + Partition Tolerance

Prioriza datos consistentes. Puede no estar disponible durante una partición. Ejemplos: HBase, Zookeeper, MongoDB (configuración stricta).

Uso: Sistemas financieros, transacciones bancarias.

AP — Availability + Partition Tolerance

Siempre responde, pero puede dar datos stale. Ejemplos: Cassandra, DynamoDB, CouchDB.

Uso: Redes sociales, catálogos de productos, carritos de compra.

⚠️
En la práctica, la partición de red es inevitable. La verdadera decisión es entre consistencia eventual (AP) vs indisponibilidad temporal (CP). El teorema PACELC extiende CAP para considerar también latencia vs consistencia en condiciones normales.

📋 12-Factor App

Metodología para construir aplicaciones SaaS modernas, cloud-native, altamente portables y mantenibles.

I. Codebase

Un repo, múltiples deploys (dev, staging, prod).

II. Dependencies

Declaradas explícitamente y aisladas (requirements.txt, package.json).

III. Config

Configuración en variables de entorno, no en código. Nunca hardcodear credenciales.

IV. Backing Services

Bases de datos, queues, APIs externas tratadas como recursos adjuntos intercambiables.

V. Build, Release, Run

Separación estricta de fases. Build → artifact; Release → artifact + config; Run → proceso.

VI. Processes

Stateless, share-nothing. Estado en backing services (DB, cache).

VII. Port Binding

La app es auto-contenida y exporta servicios via puerto. No depende de un servidor externo (Apache, Nginx).

VIII. Concurrency

Escalar horizontalmente via procesos (process model).

IX. Disposability

Inicio rápido, shutdown graceful. Resiliente a fallos repentinos.

X. Dev/Prod Parity

Reducir diferencias entre entornos. Usar mismas versiones de DB/cache en local.

XI. Logs

Logs como streams de eventos. La app no gestiona archivos de log; los agrega el entorno.

XII. Admin Processes

Tareas de administración (migraciones, scripts) como procesos one-off.

🔄 Patrones de Arquitectura Distribuida

⚡ CQRS

Command Query Responsibility Segregation. Separa las operaciones de escritura (Commands) de las de lectura (Queries) en modelos y bases de datos distintas.

Ventajas

  • Escalado independiente de lectura y escritura
  • Modelos optimizados para cada operación
  • Ideal con Event Sourcing

Desventaja clave

  • Eventual consistency entre read/write stores

📖 Event Sourcing

El estado de la aplicación se deriva de una secuencia inmutable de eventos, no de valores actuales en DB.

Ventajas

  • Auditoría completa del historial
  • Reconstrucción de cualquier estado pasado
  • Temporal decoupling

Uso típico

  • Sistemas bancarios, pedidos, auditoría

🔌 Circuit Breaker

Patrón de resiliencia. Cuando un servicio downstream falla repetidamente, el "breaker" se abre y deja de llamarlo temporalmente, evitando cascade failures.

Estados

  • Closed: operación normal
  • Open: bloqueando llamadas (fallo)
  • Half-Open: probando recuperación

Implementaciones

  • Hystrix, Resilience4j, Polly, Istio

🔀 Saga Pattern

Gestión de transacciones distribuidas sin 2PC. Cada servicio ejecuta su transacción local y publica un evento; si falla, se ejecutan compensaciones.

Tipos

  • Choreography: cada servicio reacciona a eventos
  • Orchestration: un orquestador dirige el flujo (Temporal, Camunda)

🚪 API Gateway

Punto de entrada único para clientes. Maneja routing, auth, rate limiting, logging, transformación de requests.

Funciones

  • Autenticación/Autorización centralizada
  • Load balancing
  • SSL termination
  • Caching, rate limiting
  • Request aggregation (BFF pattern)

🕸️ Service Mesh

Infraestructura dedicada a manejar la comunicación service-to-service. Se implementa como sidecar proxy por servicio o por nodo.

Capacidades

  • mTLS automático entre servicios
  • Observabilidad (traces, metrics)
  • Traffic management (canary, A/B)
  • Circuit breaking, retries

Herramientas

  • Istio, Linkerd, Consul Connect

🏭 Producer-Consumer

Desacopla productores de mensajes de consumidores vía cola/broker. Ideal para baja acoplamiento en microservicios.

Herramientas

  • RabbitMQ, Apache Kafka, AWS SQS
  • Azure Service Bus, GCP Pub/Sub

vs Pub/Sub

  • Queue: un consumer por mensaje
  • Pub/Sub: múltiples subscribers por mensaje

🗄️ Database per Service

Cada microservicio es dueño de su propia base de datos. Ningún servicio accede directamente a la DB de otro.

Ventajas

  • Loose coupling real entre servicios
  • Libertad de elegir DB por servicio
  • Escalado independiente

Consecuencia

  • Joins distribuidos → Saga o API composition

💡 SRP en la Práctica — Ejemplo Real

La clase Square vista en la evaluación viola SRP porque tiene dos responsabilidades: calcular área Y formatear output.

// ❌ MAL: dos responsabilidades en una clase
class Square {
    public $length;
    function __construct($pLength) { $this->length = $pLength; }
    
    public function getArea() { return pow($this->length, 2); }
    
    // ❌ Responsabilidad de presentación mezclada
    public function output() {
        return 'The area of square is: ' . $this->getArea($this->length);
    }
}

// ✅ BIEN: separación de responsabilidades
class Square {
    public $length;
    function __construct($pLength) { $this->length = $pLength; }
    public function getArea() { return pow($this->length, 2); }
}

class SquarePresenter {
    public function output(Square $square) {
        return 'The area of square is: ' . $square->getArea();
    }
}

🌐 Tipos de Nube y Estrategias de Despliegue

🔒 Private Cloud / On-Premise

Infraestructura propia o gestionada exclusivamente para una organización. Control total, costos fijos altos.

  • Cumplimiento regulatorio estricto
  • Datos altamente sensibles
  • Latencia ultra-baja requerida

🌍 Public Cloud

Infraestructura compartida gestionada por el proveedor (AWS, Azure, GCP). Pago por uso, elasticidad máxima.

  • Startups y proyectos con crecimiento variable
  • Menor inversión inicial (CAPEX → OPEX)

🔀 Hybrid Cloud

Integración de nubes de diferentes tipos (public + private/on-premise). Conectadas via VPN o Direct Connect.

  • Mantener legacy systems críticos on-prem
  • Migración gradual a la nube
  • Datos sensibles on-prem + cómputo en cloud

🌐 Multi-Cloud

Uso de múltiples nubes del mismo tipo (dos o más proveedores públicos) para diferentes propósitos.

  • Evitar vendor lock-in
  • Best-of-breed: mejor servicio de cada proveedor
  • Redundancia geográfica/proveedor

🔌 Tipos de API y Protocolos

Protocolo Estilo Formato Cuándo usar Trade-offs
REST Stateless, resource-based JSON/XML sobre HTTP/1.1 APIs públicas, CRUD, web estándar Verboso, over/under-fetching, múltiples round-trips

Long Polling es una alternativa a WebSockets: el cliente hace request y el servidor mantiene la conexión abierta hasta tener datos. Desventaja: latencia inherente y overhead HTTP por cada request.

🔐 Autenticación y Autorización

Flujo: Autenticación → Autorización

Autenticación responde: "¿Quién dice ser?" | Autorización responde: "¿Qué puede hacer?" | Auditoría responde: "¿Qué hizo?"

JWT — JSON Web Token

Token de 3 partes separadas por puntos: Header.Payload.Signature

  • Header: algoritmo de firma (HS256, RS256)
  • Payload: claims (sub, exp, roles)
  • Signature: hash firmado con clave secreta

Stateless: el servidor no guarda sesión. Verifica firma en cada request.

OAuth 2.0 Grants

  • Authorization Code: apps web server-side (más seguro)
  • PKCE: apps móviles/SPA (sin client secret)
  • Client Credentials: machine-to-machine
  • Implicit: obsoleto, no usar

OAuth 2.0 es un framework de autorización. OpenID Connect (OIDC) agrega autenticación encima.

Access Control Models

Modelo Descripción Uso típico
RBAC Role-Based: permisos asignados a roles Sistemas empresariales, admin panels
ABAC Attribute-Based: políticas basadas en atributos del usuario/recurso Sistemas complejos, multi-tenant
DAC Discretionary: el dueño del recurso decide quién accede Sistemas de archivos, Google Drive
MAC Mandatory: el sistema decide según clasificación Sistemas militares/gubernamentales

Mejores prácticas de Auth

  • ✅ Hashear passwords con bcrypt/Argon2 (NUNCA plain text)
  • ✅ Rate limiting en login endpoints
  • ✅ HTTPS obligatorio (tokens interceptables en plain HTTP)
  • ✅ Tokens con expiración corta + refresh tokens
  • ✅ Usar secrets manager para claves (nunca en código fuente)
  • ✅ Estructurar roles (RBAC) desde el diseño inicial
  • ❌ Nunca almacenar passwords en plain text
  • ❌ No usar auth por IP (fácilmente spoofeable)

📈 Escalabilidad y Concurrencia

Vertical Scaling (Scale Up)

Más CPU/RAM al mismo servidor. Simple pero con límite físico. Sin particionamiento de datos.

Horizontal Scaling (Scale Out)

Más instancias/nodos. Cada nodo puede contener parte de los datos (sharding). Requiere stateless apps o sticky sessions.

Database Scaling

  • Read Replicas: réplicas de solo lectura para distribuir queries
  • Sharding horizontal: particionar datos entre nodos (cada nodo = parte de los datos) — respuesta a la evaluación sobre el banco
  • Caching: Redis/Memcached para reducir carga en DB
  • Connection pooling: PgBouncer, HikariCP

Uptime y SLA

SLA Downtime/año Estado
99% ~87.6 horas Unhealthy
99.9% (3 nines) ~8.7 horas ✅ Healthy target
99.99% (4 nines) ~52 minutos Excelente
99.999% (5 nines) ~5 minutos Mission-critical

⚖️ Load Balancing

🌐 HTTP/L7 Load Balancer

Opera a nivel de aplicación. Puede enrutar por URL path, headers, cookies.

  • AWS ALB, Azure Application Gateway
  • Soporta SSL termination, WAF

🔌 Network/L4 Load Balancer

Opera a nivel de transporte. Distribuye por protocolos específicos (TCP/UDP). Ultra-baja latencia.

  • AWS NLB, Azure Load Balancer
  • Ideal para gaming, VoIP, IoT

💻 Virtual Load Balancer

Software-based, corre a nivel de OS del servidor. Distribuye según reglas configuradas.

  • HAProxy, Nginx como LB
  • Flexible, barato, configurable

🔩 Hardware Load Balancer

Dispositivo físico dedicado. Máximo rendimiento, máximo costo.

  • F5 BIG-IP, Citrix ADC
  • Usado en grandes enterprises on-prem

Algoritmos de Balanceo

Algoritmo Descripción Caso de uso
Round Robin Distribuye secuencialmente entre servidores Servidores homogéneos, stateless
Weighted Round Robin Más requests a servidores más potentes Servidores heterogéneos
Least Connections Al servidor con menos conexiones activas Requests de duración variable
Weighted Least Connection Least connections + peso por capacidad Microservicios con distinta capacidad
Source IP Hash Hash de IP del cliente → mismo servidor siempre Session persistence / Sticky sessions
Weighted Response Time Al servidor con menor tiempo de respuesta Optimización de latencia dinámica

Bases de Datos y Pipelines

🔍 SQL vs NoSQL — Cuándo usar cada uno

Aspecto SQL (Relacional) NoSQL
Estructura Schema fijo, tablas, relaciones Schema flexible (document, key-value, graph, column-family)
Consistencia ACID completo — fuerte BASE (Basically Available, Soft state, Eventually consistent)
Escalado Vertical principalmente (horizontal complejo) Horizontal nativo (sharding)
Transacciones ✅ Transacciones complejas multi-tabla ❌ Limitado (problema en finanzas)
Queries SQL estándar, JOINs complejos APIs propias, sin JOINs (denormalización)
Latencia NoSQL Más latencia en alta escala ✅ Baja latencia a escala masiva
Casos de uso Finanzas, ERP, CRM, sistemas legacy Redes sociales, IoT, catálogos, gaming
Ejemplos PostgreSQL, MySQL, MSSQL, Oracle MongoDB, DynamoDB, Cassandra, Redis

Tipos de NoSQL

📄 Document

Datos como documentos JSON/BSON. Flexible, bueno para datos heterogéneos.

MongoDB, Firestore, CouchDB

🔑 Key-Value

Acceso ultra-rápido por clave. Ideal para caché y sesiones.

Redis, DynamoDB, Memcached

📊 Column-Family

Datos organizados por columnas. Excelente para series de tiempo y analytics.

Cassandra, HBase, Bigtable

🕸️ Graph

Nodos y relaciones. Ideal para redes sociales, recomendaciones, fraude.

Neo4j, Amazon Neptune, ArangoDB

⚠️
Limitación crítica NoSQL en finanzas: Las bases NoSQL tienen menor rendimiento en transacciones complejas y consistencia fuerte. Los sistemas financieros requieren ACID completo → preferir PostgreSQL, Aurora, o Spanner.

⚡ Caching — Estrategias y Tipos

Por qué usar caché

  • ✅ Reducir latencia de consultas (evitar round-trip a DB)
  • ✅ Mejorar responsividad de la aplicación
  • ✅ Disponibilidad de datos si DB temporalmente no disponible
  • ✅ Reducir carga en base de datos

Patrones de Caché

  • Cache-Aside: app gestiona cache manualmente
  • Read-Through: cache delante de DB, transparente
  • Write-Through: escribe en cache + DB sincrónicamente
  • Write-Behind: escribe en cache, DB async (eventual)

Distributed Cache (Redis, Memorystore) es el mecanismo clave para minimizar latencia en sistemas distribuidos de alta disponibilidad.

CI/CD, IaC y Observabilidad

🔄 CI/CD — Continuous Integration / Continuous Delivery

Continuous Integration (CI)

  • Integrar cambios frecuentemente (varias veces al día)
  • Build automático en cada commit
  • Tests automáticos (unit, integration)
  • Feedback rápido al desarrollador

Continuous Delivery vs Deployment

  • CD (Delivery): código siempre en estado deployable. Deploy a producción requiere aprobación humana.
  • CD (Deployment): cada cambio que pasa CI se despliega automáticamente a producción sin intervención humana.

Pipeline típico

commit → Build → Unit Tests → Integration Tests → Security Scan → Artifact → Deploy Staging → E2E Tests → Deploy Prod

# Herramientas CI/CD
GitHub Actions | GitLab CI | Jenkins | CircleCI | Azure DevOps | AWS CodePipeline

Estrategias de Deploy

Estrategia Descripción Riesgo Rollback

🏗️ Infrastructure as Code (IaC)

🌍 Terraform

IaC multi-cloud, declarativa, HCL. El estándar de la industria para multi-cloud.

  • Provider ecosystem enorme (AWS, Azure, GCP, K8s)
  • State management (local o remote con S3/Terraform Cloud)
  • Módulos reutilizables
  • Plan → Apply workflow

🔧 AWS CloudFormation / CDK

CloudFormation: YAML/JSON declarativo. CDK: código real (TypeScript/Python) que genera CloudFormation.

  • Nativo AWS, integrado con todos los servicios
  • CDK = type-safe, testeable, reutilizable
  • Stacks y nested stacks

🔵 Azure Bicep

DSL de Microsoft para Azure Resource Manager. Más legible que ARM templates JSON.

  • Transpila a ARM templates
  • Type safety, módulos
  • Integrado con Azure DevOps

⚙️ Ansible / Pulumi

Ansible: configuration management imperativo (idempotente). Pulumi: IaC en lenguajes reales (Python, Go, TS).

  • Ansible: excelente para OS-level config
  • Pulumi: cuando se necesita lógica compleja

👁️ Observabilidad — Los 3 Pilares

La observabilidad es la capacidad de entender el estado interno de un sistema desde el exterior. Se basa en 3 pilares complementarios:

📊 Metrics

Mediciones numéricas agregadas en el tiempo. Responden: ¿Está el sistema sano? ¿Hay anomalías?

Tipos de métricas

  • RED: Rate, Errors, Duration (para servicios)
  • USE: Utilization, Saturation, Errors (para recursos)

Herramientas

  • Prometheus, Grafana, CloudWatch, Datadog

📝 Logs

Registros de eventos discretos. El logging registra; el monitoring analiza esos datos.

Best practices

  • Logs estructurados (JSON)
  • Correlation IDs para tracing
  • Niveles: DEBUG, INFO, WARN, ERROR
  • Retención y compresión

Herramientas

  • ELK Stack, Splunk, CloudWatch Logs, Loki

🔍 Traces (Distributed Tracing)

Seguimiento end-to-end de una request a través de múltiples servicios. Responden: ¿Dónde está la latencia?

Conceptos

  • Trace: journey completo de un request
  • Span: operación individual dentro de un trace
  • Context propagation: headers W3C TraceContext

Herramientas

  • Jaeger, Zipkin, AWS X-Ray, OpenTelemetry
✅
En cloud, priorizar: Observabilidad de métricas, logs y trazas para análisis en tiempo real. OpenTelemetry es el estándar open-source para instrumentación unificada.

🛡️ Resiliencia y Tolerancia a Fallos

Patrones de Resiliencia

  • Circuit Breaker: evita cascade failures
  • Retry with backoff: reintentos con espera exponencial
  • Timeout: no esperar indefinidamente
  • Bulkhead: aislar recursos entre funciones (ej: thread pools)
  • Health checks: liveness + readiness probes (K8s)
  • Graceful degradation: funcionalidad reducida ante fallos

Contenedores — Ciclo de vida ante fallo

  1. Contenedor detectado como unresponsive
  2. Deja de recibir tráfico (remove from load balancer)
  3. Guarda error logs y debug info
  4. Shutdown del contenedor
  5. Lanzamiento de contenedor reemplazo

Orquestado por: Kubernetes, ECS, GKE.

07 — SEGURIDAD

IAM, Zero Trust y Mejores Prácticas

🔐 Criptografía — Servicios de Seguridad

Los servicios de seguridad criptográficos son:

🔒 Confidentiality

Proteger datos de acceso no autorizado. Implementado con cifrado simétrico (AES) y asimétrico (RSA).

✅ Integrity

Garantizar que datos no fueron alterados. Implementado con hashes (SHA-256) y MACs.

👤 Authentication

Verificar la identidad del comunicante. Implementado con firmas digitales, certificados X.509.

📝 Non-Repudiation

Garantizar que el emisor no puede negar haber enviado el mensaje. Firmas digitales.

⚠️
Disponibilidad (Availability) NO es un servicio criptográfico. Es parte del CIA Triad general de seguridad, pero la criptografía no la garantiza directamente.

🛡️ Zero Trust Architecture

Principio: "Never trust, always verify." No asumas confianza basada en ubicación de red (ni dentro del datacenter).

Principios Zero Trust

  • Verificar explícitamente (identidad, device, contexto)
  • Least-privilege access
  • Assume breach (diseña como si ya estuvieras comprometido)
  • Microsegmentación de red
  • mTLS entre servicios

Implementación

  • Identity Provider (Azure AD, Okta)
  • MFA obligatorio
  • Service Mesh con mTLS (Istio)
  • SIEM para detección de anomalías
  • PAM (Privileged Access Management)

🗝️ Gestión de Secretos

Best practice en microservicios: usar un gestor de secretos dedicado. NUNCA almacenar credenciales en código o archivos de configuración.

Práctica Estado Razón
Variables de entorno en código fuente ❌ Riesgo alto Expuestas en repositorio, logs
Credenciales en archivos de configuración ❌ Riesgo alto Versionadas en git, accesibles a todos
Secretos en logs (aunque encriptados) ❌ Anti-patrón Logs tienen retención larga, múltiples accesos
Azure Key Vault / AWS Secrets Manager ✅ Best Practice Centralizado, auditado, rotación automática, RBAC
HashiCorp Vault ✅ Best Practice Open-source, multi-cloud, dynamic secrets

08 — NETWORKING

VPC, Load Balancing y CDN

🔌 Configuración Dinámica de Servidores

DHCP (Dynamic Host Configuration Protocol) es el protocolo que asigna dinámicamente configuración de red (IP, gateway, DNS) a dispositivos/servidores. Es la definición de "dynamic server configuration".

Static vs Dynamic Configuration

  • Static: IP y config asignadas manualmente
  • Dynamic (DHCP): asignación automática al conectarse

Source IP Hash en Load Balancing

Usa el IP del cliente para determinar siempre el mismo servidor. Garantiza session persistence (sticky sessions). Ideal cuando el servidor guarda estado de sesión localmente.

📡 CDN — Content Delivery Network

Red de servidores distribuidos globalmente que cachean contenido cerca del usuario. Reduce latencia y carga en el origin server.

Qué cachear en CDN

  • Assets estáticos (JS, CSS, imágenes, fuentes)
  • Videos y archivos grandes
  • Respuestas de API con TTL definido
  • Páginas SSG

Servicios CDN

  • AWS CloudFront
  • Azure CDN / Azure Front Door (con WAF)
  • GCP Cloud CDN
  • Cloudflare (multi-cloud)
  • Akamai (enterprise)

10 — CASOS REALES

Arquitecturas E2E y Trade-offs

🏦 Caso: Plataforma Bancaria Digital

Banco necesita reducir costos sin comprometer disponibilidad. Sistema con transacciones, consultas de saldo, y notificaciones.

Decisiones de Arquitectura

📊 Base de Datos

PostgreSQL / Aurora (RDS) para transacciones — ACID obligatorio en finanzas. NoSQL para catálogos de productos y sesiones.

Trade-off: NoSQL más barato a escala, pero sin consistencia fuerte → no apto para transferencias.

⚡ Serverless para Esporádicos

Procesos batch de fin de mes, generación de reportes, notificaciones → AWS Lambda. Reducción de costos significativa vs instancias 24/7.

🔐 Seguridad

OAuth 2.0 + JWT para autenticación. Azure Key Vault / AWS Secrets Manager para credenciales. Zero Trust: mTLS entre microservicios.

📡 NoSQL para Analytics

DynamoDB para historial de transacciones de lectura rápida. BigQuery/Redshift para analytics histórico. Replicación de write DB → read store.

Arquitectura simplificada

Client → CDN → API Gateway → [Auth Service (JWT)]
                              ↓
                    [Microservicios]
                    ├── Account Service → PostgreSQL (ACID)
                    ├── Transaction Service → PostgreSQL + Event → Kafka
                    ├── Notification Service → SQS/SNS → Lambda
                    └── Analytics Service → DynamoDB (read) + Redshift

[Kafka] → Event Store → CQRS Read Store (DynamoDB)
[Circuit Breaker] en cada inter-service call
[Service Mesh (Istio)] para mTLS + observabilidad
[Redis Cache] para sesiones y consultas frecuentes

🛒 Caso: E-Commerce a Gran Escala

📦 Catálogo

NoSQL (DynamoDB/MongoDB) — datos semiestructurados, lectura intensiva, baja latencia.

CDN para imágenes. ElastiCache Redis para productos frecuentes.

🛒 Carrito

Redis (AP: disponibilidad > consistencia fuerte). Aceptable eventual consistency.

💳 Pagos

PostgreSQL con ACID. Saga pattern para coordinar: Inventario → Pago → Envío.

Circuit breaker hacia payment gateway externo.

🔔 Notificaciones

Event-driven: Order Service → Kafka → Notification Service → Email/Push.

Desacoplado, escalable independientemente.

⚖️ Trade-offs Clave para Entrevistas

Decisión Opción A Opción B Cuándo elegir A vs B
Consistencia vs Disponibilidad CP (consistencia fuerte) AP (disponibilidad + eventual consistency) A: finanzas, salud | B: redes sociales, e-commerce
Sync vs Async REST/gRPC síncrono Event-driven asíncrono A: respuesta inmediata requerida | B: desacoplamiento, resilience
Monolito vs Microservicios Monolito modular Microservicios A: equipo pequeño, dominio nuevo | B: múltiples equipos, dominio estable
SQL vs NoSQL PostgreSQL/MySQL DynamoDB/MongoDB A: transacciones ACID, JOINs | B: escala masiva, schema flexible
SSR vs SSG SSR (runtime) SSG (build time) A: datos dinámicos por usuario | B: contenido estático, SEO, perf
Serverless vs Containers Lambda/Functions ECS/EKS/K8s A: workloads esporádicos, eventos | B: workloads continuos, control fino
REST vs GraphQL REST GraphQL A: APIs simples, múltiples consumidores externos | B: UI complejas, múltiples clientes con distintas necesidades

🌐 Sistemas Distribuidos — Conceptos Clave

Tipos de Arquitectura Distribuida

  • Client-Server: nodo server fijo + clientes
  • P2P (Peer-to-Peer): todos los nodos son client/server/ambos

Elasticidad vs Escalabilidad

  • Scalability: capacidad de crecer (escalar hacia arriba)
  • Elasticity: adaptar recursos dinámicamente según demanda actual (up AND down). Requiere scalability como prerequisito.

NTP — Sincronización de Tiempo

Network Time Protocol es la solución real para sincronizar clocks en sistemas distribuidos. Sincroniza con UTC vía jerarquía de servidores de tiempo.

Riesgos de Sistemas Distribuidos

  • ✅ Network failure cascade
  • ✅ Governance/GDPR (datos en múltiples regiones)
  • ✅ Mayor superficie de ataque (seguridad)
  • ❌ Escalabilidad NO es un riesgo — es una ventaja

🗺️ Domain-Driven Design (DDD)

Metodología para modelar software en torno a la complejidad del dominio de negocio. Puente entre expertos de negocio y desarrolladores.

Conceptos Centrales DDD

  • Ubiquitous Language: vocabulario común entre negocio y tech
  • Bounded Context: frontera explícita de un modelo de dominio
  • Aggregate: cluster de objetos de dominio tratados como unidad
  • Domain Event: algo relevante que ocurrió en el dominio
  • Repository: abstracción de persistencia

Qué NO es DDD

  • ❌ No se enfoca en minimizar coupling/cohesión para performance estructural (eso es diseño OO general)
  • ❌ No identifica mecanismos de software a replicar (eso es ADD)
  • ✅ Organiza artefactos de código en torno al problema de negocio
  • ✅ Provee prácticas para resolver problemas complejos

🔄 Agile, Scrum y Gestión de Proyectos

📜 Agile Manifesto — 4 Valores

  1. Individuals & interactions over processes & tools
  2. Working software over comprehensive documentation
  3. Customer collaboration over contract negotiation
  4. Responding to change over following a plan

🏃 Ceremonias Scrum

  • Sprint Planning: planificar trabajo del sprint
  • Daily Standup: sincronización diaria del equipo
  • Sprint Review: demo del incremento a stakeholders
  • Sprint Retrospective: inspeccionar proceso, mejorar
  • Backlog Refinement: afinar items futuros

📊 KPIs — Criterios SMART

Un KPI debe ser: Specific, Measurable, Achievable, Relevant, Time-bound.

✅ "Alcanzar 3,000 ventas en el primer trimestre"

❌ "Vender lo más posible" (no medible)

❌ "100% QA en cada sprint" (no alcanzable)

⚠️ Deuda Técnica — Causas

  • Tecnología desactualizada (legacy)
  • Presión de tiempo (velocidad > calidad)
  • Cambios constantes de scope
  • Falta de tests automáticos
  • Código sin documentar ni refactorizar

🧪 TDD — Test-Driven Development

Ciclo Red → Green → Refactor

  1. 🔴 Red: escribir test que falla (aún no hay código)
  2. 🟢 Green: escribir el mínimo código para que el test pase
  3. 🔵 Refactor: limpiar código manteniendo tests verdes

Ventajas TDD

  • ✅ Codebase más fácil de mantener
  • ✅ 100% de coverage garantizado
  • ✅ Ahorro de costos a largo plazo
  • ✅ Diseño más limpio (testeable = desacoplado)

Lo que TDD NO garantiza

  • ❌ Los tests no necesitan mantenimiento cuando cambia el código → FALSO. Los tests deben actualizarse con cada cambio de comportamiento.

Code Review — Métodos válidos

  • ✅ Pair programming
  • ✅ Pull request comments
  • ✅ Tool-assisted (linters, SonarQube)
  • ❌ Post-mortem analysis (es para incidentes, no code review)
