Arquitectura de Software: patrones, paradigmas y decisiones

Modelos y principios fundamentales#

Teorema CAP#

Un sistema distribuido solo puede garantizar dos de tres propiedades simultáneamente:

Consistency (C)

Todos los nodos ven los mismos datos al mismo tiempo. Una lectura siempre retorna el dato más reciente.

Availability (A)

Todo request recibe una respuesta (no necesariamente el dato más reciente). El sistema sigue respondiendo.

Partition Tolerance (P)

El sistema funciona aunque haya fallas de red entre nodos. En sistemas distribuidos, P es obligatorio.

Elección Garantiza Sacrifica Ejemplos
CP Consistencia + Particiones Disponibilidad (responde error si hay partición) HBase, Zookeeper, etcd, MongoDB (w:majority)
AP Disponibilidad + Particiones Consistencia eventual DynamoDB, Cassandra, CouchDB, Riak
CA Consistencia + Disponibilidad Tolerancia a particiones (imposible en distribuido) PostgreSQL, MySQL (single node)

En sistemas distribuidos reales, las particiones de red son inevitables. Por tanto, la elección real es siempre entre CP o AP. La categoría CA solo aplica en sistemas de un único nodo.

ACID vs BASE#

ACID (Bases de datos tradicionales)

  • Atomicity: Transacción completa o ninguna
  • Consistency: Datos siempre en estado válido
  • Isolation: Transacciones no se interfieren
  • Durability: Datos persisten tras commit
  • Ejemplos: PostgreSQL, MySQL, Oracle
  • Ideal para: banca, e-commerce, inventario

BASE (NoSQL, distribuidos)

  • Basically Available: Siempre responde
  • Soft State: Estado puede cambiar sin input
  • Eventually Consistent: Convergencia eventual
  • Ejemplos: DynamoDB, Cassandra, MongoDB
  • Ideal para: redes sociales, analytics, IoT
  • Prioriza escala sobre consistencia estricta

The Twelve-Factor App#

Metodología para construir aplicaciones cloud-native portables, escalables y mantenibles. Publicada originalmente por Heroku.

I. Codebase

Un repositorio, múltiples despliegues. Sin código compartido entre apps via copy-paste.

II. Dependencies

Declarar y aislar dependencias explícitamente (requirements.txt, package.json, go.mod).

III. Config

Configuración en variables de entorno, nunca en código fuente ni archivos versionados.

IV. Backing Services

Tratar BD, caches, brokers como recursos adjuntos intercambiables via URL/config.

V. Build/Release/Run

Separar estrictamente las etapas de build, release (config) y runtime.

VI. Processes

Ejecutar la app como procesos stateless. Estado en backing services externos.

VII. Port Binding

Exponer servicios via binding de puertos, sin depender de servidores web externos.

VIII. Concurrency

Escalar horizontalmente via procesos, no con threads dentro del mismo proceso.

IX. Disposability

Arranque rápido y apagado graceful. Tolerar fallas repentinas sin corrupción.

X. Dev/Prod Parity

Mantener dev, staging y prod lo más similares posible. Evitar "works on my machine".

XI. Logs

Tratar logs como streams de eventos. La app escribe a stdout, no gestiona archivos.

XII. Admin Processes

Ejecutar tareas administrativas (migraciones, scripts) como procesos one-off.

Domain-Driven Design (DDD)#

Metodología que pone el dominio de negocio en el centro del diseño. El código debe reflejar el lenguaje y los conceptos del dominio, modelados de forma colaborativa con expertos de negocio.

Axiomas y buenas prácticas#

Trade-offs Fundamentales#

La arquitectura de software es el arte de gestionar trade-offs. No existe la arquitectura perfecta, solo la más adecuada para el contexto dado.

Trade-off Opción A vs Opción B Decisión guiada por
Consistencia vs Disponibilidad Fuerte consistencia ↔ Alta disponibilidad Naturaleza del dominio (CAP)
Costo vs Rendimiento Infra optimizada (cara) ↔ Infra genérica (barata) SLA requeridos y presupuesto
Acoplamiento vs Autonomía Llamadas síncronas (bajo lag) ↔ Mensajería async (desacoplado) Tolerancia a latencia
Simplicidad vs Escalabilidad Monolito (simple) ↔ Microservicios (escalable) Tamaño del equipo y carga
Velocidad vs Seguridad Deploy rápido ↔ Revisiones exhaustivas Riesgo del dominio

Axioma del arquitecto: "Optimiza para el cambio, no para la perfección inicial. El código más flexible es aquel que puede ser descartado fácilmente."

Escalabilidad: Horizontal vs Vertical#

⬆ Escalado Vertical (Scale Up)

  • Añadir más CPU/RAM/disco al servidor
  • Simple: sin cambios en la arquitectura
  • Límite físico: hay un máximo de hardware
  • Single point of failure
  • Costo crece no linearmente
  • Ideal para: BBDDs relacionales, legacy apps

↔ Escalado Horizontal (Scale Out)

  • Añadir más instancias/nodos al cluster
  • Requiere stateless apps y load balancer
  • Sin límite teórico de escalabilidad
  • Alta disponibilidad nativa
  • Costo crece linearmente
  • Ideal para: microservicios, contenedores

Observabilidad: Los Tres Pilares#

En sistemas distribuidos, no es suficiente monitorear. Se requiere observabilidad: la capacidad de comprender el estado interno del sistema desde sus salidas externas.

Logs

Registros de eventos discretos con timestamp. Formatos estructurados (JSON). Centralizados en ELK Stack, Splunk, Cloud Logging. Nivel: DEBUG, INFO, WARN, ERROR.

Métricas

Valores numéricos a lo largo del tiempo. Latencia p50/p95/p99, error rate, throughput, saturación. Herramientas: Prometheus + Grafana, Datadog, CloudWatch.

Trazas Distribuidas

Seguimiento de un request a través de múltiples servicios. Trace ID correlaciona logs y spans. OpenTelemetry, Jaeger, Zipkin, AWS X-Ray.

# Instrumentación OpenTelemetry (estándar de facto)
from opentelemetry import trace, metrics
from opentelemetry.sdk.trace import TracerProvider

tracer = trace.get_tracer("orders-service")
meter = metrics.get_meter("orders-service")

# Métrica: contador de órdenes creadas
orders_counter = meter.create_counter(
    "orders.created",
    description="Total de órdenes creadas",
    unit="1"
)

async def create_order(request: CreateOrderRequest):
    # Span: unidad de trabajo en una traza distribuida
    with tracer.start_as_current_span("create_order") as span:
        span.set_attribute("user.id", request.user_id)
        span.set_attribute("order.items_count", len(request.items))

        order = await order_repository.save(Order.from_request(request))

        # Registrar métrica con atributos
        orders_counter.add(1, {"status": "success", "region": "us-east-1"})
        span.set_attribute("order.id", str(order.id))

        return order

Seguridad: Zero Trust y IAM#

El modelo Zero Trust asume que no existe perímetro de red seguro. Cada request, desde dentro o fuera de la red, debe ser autenticado y autorizado explícitamente.

Never Trust, Always Verify

Autenticar y autorizar cada request sin importar el origen. Incluso tráfico interno.

Least Privilege

Dar solo los permisos mínimos necesarios para cada servicio, usuario o rol.

Micro-segmentación

Segmentar la red internamente. Firewall entre zonas, no solo en el perímetro.

mTLS

Mutual TLS entre servicios. Ambos lados se autentican. Istio/Envoy lo implementan.

Secrets Management

Gestión centralizada de secretos: Vault (HashiCorp), AWS Secrets Manager, Azure Key Vault.

Supply Chain Security

SBOM, firma de imágenes de contenedor (Cosign), escaneo de vulnerabilidades en CI/CD.

Tipos de arquitectura según la infraestructura#

On-Premise#

La infraestructura on-premise implica que todos los servidores, almacenamiento y redes se encuentran físicamente en las instalaciones de la organización. La empresa es responsable de adquisición, operación y mantenimiento de cada componente.

Control total Alta inversión inicial (CapEx) Latencia predecible Compliance físico

VENTAJAS

  • Control absoluto sobre hardware y datos
  • Cumplimiento normativo (bancos, gobiernos)
  • Sin latencia de red hacia proveedor externo
  • Sin costos recurrentes de suscripción cloud
  • Personalización total del stack

DESVENTAJAS

  • Alto costo inicial de capital (servidores, datacenter)
  • Escalabilidad lenta y costosa
  • Equipo de operaciones dedicado
  • Riesgo de obsolescencia de hardware
  • Recuperación ante desastres compleja
Cuándo usar
  • Sector financiero con regulaciones estrictas
  • Datos clasificados o de defensa nacional
  • Sistemas legacy que no pueden migrarse
  • Latencia ultra-baja (trading de alta frecuencia)
Cuándo evitar
  • Startups con presupuesto limitado
  • Cargas de trabajo impredecibles o estacionales
  • Necesidad de despliegue global rápido
  • Equipos pequeños sin operaciones dedicadas

Cloud-Native#

Una arquitectura cloud-native no solo usa la nube, sino que está diseñada específicamente para aprovechar sus capacidades: elasticidad, escalabilidad automática y servicios gestionados. Los cuatro pilares de la CNCF (Cloud Native Computing Foundation) son:

Microservicios

Aplicaciones compuestas de servicios pequeños, independientes y desplegables de forma autónoma.

Contenedores

Docker/OCI como unidad de despliegue estándar. Kubernetes como orquestador de facto.

CI/CD

Pipelines automatizados de integración y entrega continua para despliegues frecuentes y seguros.

DevOps & Observabilidad

Cultura de colaboración con métricas, trazas y logs integrados desde el diseño.

Paradigmas de arquitectura de software#

Arquitectura Monolítica#

Una aplicación monolítica es una unidad desplegable única donde todos los componentes (UI, lógica de negocio, acceso a datos) están acoplados en un solo proceso. Es el punto de partida natural de la mayoría de los sistemas.

Cuándo usar
  • Proyectos nuevos o MVPs
  • Equipos pequeños (< 10 desarrolladores)
  • Dominio del problema no bien definido
  • Aplicaciones de baja escala
Cuándo evitar
  • Equipos grandes con ownership distribuido
  • Necesidad de escalar componentes independientemente
  • Ciclos de despliegue frecuentes
  • Alta carga o tráfico variable

// Ejemplo: Microservicio de Orders (Go)
// Cada servicio es un binario independiente con su propio main

package main

import (
    "net/http"
    "encoding/json"
)

type OrderService struct {
    db    OrderRepository
    events EventPublisher   // Comunicación async
}

// Handler HTTP - interfaz de entrada del servicio
func (s *OrderService) CreateOrder(w http.ResponseWriter, r *http.Request) {
    var req CreateOrderRequest
    json.NewDecoder(r.Body).Decode(&req)

    order, err := s.db.Save(Order{
        UserID: req.UserID,
        Items:  req.Items,
        Status: "PENDING",
    })
    if err != nil {
        http.Error(w, err.Error(), 500)
        return
    }

    // Publica evento para otros servicios (pago, notificaciones)
    s.events.Publish("order.created", order)
    json.NewEncoder(w).Encode(order)
}

func main() {
    svc := &OrderService{
        db:     NewPostgresRepository(),
        events: NewKafkaPublisher("kafka:9092"),
    }
    http.HandleFunc("/orders", svc.CreateOrder)
    http.ListenAndServe(":8080", nil)   // Puerto dedicado
}
Cuándo usar
  • Equipos grandes con ownership por dominio
  • Necesidad de escalar componentes independientemente
  • Tecnologías diversas por servicio
  • Alta disponibilidad como requisito crítico
Cuándo evitar
  • Dominio del problema no definido aún
  • Equipos sin experiencia en sistemas distribuidos
  • Cuando la latencia de red importa criticamente
  • Proyectos con presupuesto de operaciones reducido

Serverless (FaaS)#

En una arquitectura serverless, los desarrolladores escriben funciones individuales que el proveedor cloud ejecuta bajo demanda, escalando automáticamente y cobrando solo por el tiempo de ejecución real.

AWS Lambda

Funciones en Node, Python, Go, Java. Hasta 15 minutos de ejecución. Triggers via API GW, S3, DynamoDB, SQS.

Google Cloud Functions

Integración nativa con Firebase, Pub/Sub, BigQuery. Ideal para pipelines de datos y webhooks.

Azure Functions

Deep integration con el ecosistema Microsoft. Durable Functions para workflows complejos. 

# Función AWS Lambda: Procesamiento de imagen tras upload a S3
import boto3
import json
from PIL import Image
import io

def handler(event, context):
    s3 = boto3.client('s3')

    # Trigger automático cuando se sube un archivo a S3
    bucket = event['Records'][0]['s3']['bucket']['name']
    key    = event['Records'][0]['s3']['object']['key']

    # Descargar imagen original
    response = s3.get_object(Bucket=bucket, Key=key)
    image = Image.open(response['Body'])

    # Generar thumbnail
    image.thumbnail((300, 300))
    buffer = io.BytesIO()
    image.save(buffer, format='JPEG', quality=85)

    # Guardar thumbnail en bucket de salida
    s3.put_object(
        Bucket=f"{bucket}-thumbs",
        Key=key,
        Body=buffer.getvalue(),
        ContentType='image/jpeg'
    )

    return {"statusCode": 200, "processed": key}
# BILLING: Solo se cobra por los milisegundos de ejecución real

Cold Start: Las funciones serverless sufren latencia adicional (~100ms–2s) cuando no han sido invocadas recientemente. Para APIs críticas de baja latencia, considerar provisioned concurrency o contenedores.

SOA – Service-Oriented Architecture#

class Order {
  constructor(
    private id: OrderId,
    private items: OrderItem[],
    private status: OrderStatus
  ) {}

  confirm(): void {
    if (this.items.length === 0) throw new Error("Order must have items");
    this.status = OrderStatus.CONFIRMED;
  }

  total(): Money {
    return this.items.reduce((acc, item) => acc.add(item.subtotal()), Money.zero());
  }
}

EVENT-DRIVEN ARCHITECTURE: CUÁNDO ES LA RESPUESTA

La arquitectura event-driven no es un estilo de moda — es la respuesta correcta cuando el negocio genuinamente opera en términos de eventos y necesita desacoplamiento temporal entre productores y consumidores.

Usar EDA cuando
  • Múltiples sistemas deben reaccionar al mismo evento sin coordinación centralizada
  • Los productores no deben esperar a que los consumidores procesen
  • Necesitas auditabilidad completa de lo que ocurrió y cuándo
  • Los consumidores tienen disponibilidades distintas
  • El volumen de eventos supera la capacidad de procesamiento síncrono
No usar EDA cuando
  • Necesitas respuesta síncrona inmediata (checkout de e-commerce simple)
  • El equipo no tiene experiencia con sistemas de mensajería
  • El debugging de flujos asíncronos es prohibitivo con el equipo actual
  • La consistencia transaccional entre servicios es requerida estrictamente
  • El dominio es simple y no justifica la complejidad añadida
CQRS Y EVENT SOURCING: EL PODER Y EL PRECIO

CQRS y Event Sourcing son frecuentemente adoptados juntos, pero son patrones independientes. Cada uno tiene un costo significativo que debe justificarse.

CQRS — Cuándo vale la pena
  • Read/write ratio extremadamente asimétrico (99:1)
  • Los modelos de lectura y escritura son fundamentalmente diferentes
  • Necesitas proyecciones especializadas para reporting
  • Quieres escalar lectura y escritura independientemente
  • Equipo familiarizado con el patrón — curva de aprendizaje real
Event Sourcing — Precio que pagas
  • El esquema de eventos es inmutable — evolucionar es complejo
  • Las proyecciones deben reconstruirse — puede tomar horas
  • No puedes "corregir" datos — solo puedes compensar con nuevos eventos
  • Queries sobre estado actual requieren proyecciones precalculadas
  • El debugging requiere "replay" del historial de eventos

Microservicios: Lo que Nadie te Dice

La taxonomía de servicios importa más que la descomposición

No basta con dividir. Cada servicio necesita un owner claro, un contrato de API versionado, su propio pipeline CI/CD, y un runbook. Sin esto, los microservicios son monolitos distribuidos — lo peor de ambos mundos.

El distributed monolith

Si tus "microservicios" deben desplegarse juntos, comparten base de datos, o una llamada falla en cascada por todos — tienes un monolito distribuido con toda la complejidad de microservicios y ninguna de sus ventajas.

El costo de la red es real

Una llamada in-process: ~microsegundos. Una llamada HTTP entre servicios: 1-10ms. Un flujo de 10 servicios encadenados síncronamente: 10-100ms de overhead adicional solo por la red.

Observabilidad no es opcional

En un monolito, el stack trace te dice exactamente qué falló. En microservicios, sin distributed tracing configurado desde el día uno, debuggear un fallo cross-service puede tomar horas.

Serverless: El Modelo Mental Correcto#

Serverless no es "sin servidores" — es "sin gestión de servidores". El modelo mental correcto es pensar en funciones como unidades de billing y escalado, no como unidades de lógica de negocio.

Serverless ideal para
  • Procesamiento de imágenes/archivos al subir
  • Webhooks de terceros (Stripe, GitHub, Twilio)
  • ETL pipelines con carga variable
  • Scheduled jobs / cron tasks
  • Backends de prototipos y MVPs
  • APIs con tráfico muy esporádico
Serverless problemático cuando
  • Latencia p99 es crítica (cold start 100-2000ms)
  • Workload continuo de alta frecuencia (más caro que VMs)
  • Transacciones de larga duración (>15 min)
  • Estado complejo entre invocaciones
  • Debugging intensivo necesario en producción
  • Necesitas vendor lock-in mínimo

Perspectiva complementariaAnti-patterns de Estilos Arquitectónicos
Distributed Monolith

Microservicios con coupling tan fuerte que deben desplegarse juntos. Lo peor de ambos mundos: complejidad de microservicios sin sus beneficios. Origen: boundaries mal definidos o shared database.

Event-Driven Spaghetti

Sistema event-driven sin documentación de qué eventos existen, quién los produce y quién los consume. El flujo de negocio se vuelve imposible de rastrear. Requiere un event catalog desde el inicio.

CQRS everywhere

Aplicar CQRS a todos los bounded contexts cuando solo uno o dos lo justifican. Añade complejidad de eventual consistency donde no se necesita.

Nano-services

Microservicios tan pequeños que cada función es un servicio. La comunicación entre servicios domina el tiempo de procesamiento real. Señal: servicios que nunca se despliegan solos.

Serverless Monolith

Una función Lambda con 50MB de código que hace todo. Sin beneficios de serverless: cold starts destructivos, timeouts problemáticos, debugging imposible.

Shared Database Antipattern

Múltiples servicios que comparten la misma base de datos y el mismo esquema. El acoplamiento a nivel de datos es más fuerte que el acoplamiento a nivel de API.

Modelos relacionados

La selección de estilo arquitectónico está directamente informada por los Bounded Contexts de DDD (cada BC es un candidato a servicio/módulo), por Conway's Law (el estilo debe mapear a la estructura del equipo), y por los Fallacies of Distributed Computing (que penalizan la sobre-descomposición).

El error más común de los arquitectos junior es elegir un estilo por su popularidad o por lo que usa una empresa de referencia. El SA senior elige el estilo que mejor resuelve las constraints específicas del problema.

Esta sección no es un catálogo de definiciones — es una guía de cuándo cada estilo es la respuesta correcta, cuándo no lo es, y cómo evolucionan los sistemas entre estilos a lo largo del tiempo.

    wait=wait_exponential(multiplier=1, min=1, max=10),  # Backoff exponencial

🧱 Estilos Arquitectónicos Principales#

Un estilo arquitectónico define la organización global del sistema: cómo se dividen los componentes, cómo se comunican y cuáles son los trade-offs de la decisión.

🏛️ Monolítico#

Toda la funcionalidad se despliega como una sola unidad. Sencillo de desarrollar y debuggear inicialmente.

Cuándo usarlo

  • Equipos pequeños (< 10 devs)
  • Dominio poco entendido todavía
  • MVP o prototipo
  • Aplicaciones con bajo tráfico predecible

Desventajas

  • Escalado solo horizontal completo
  • Deploy de todo el sistema por cambio mínimo
  • Acoplamiento tecnológico
Junior

🔬 Microservicios#

El sistema se divide en servicios pequeños, independientes, desplegables de forma autónoma, organizados en torno a capacidades de negocio.

Principios clave

  • Single Responsibility por servicio
  • Comunicación via APIs o mensajes
  • Base de datos por servicio (DB per service)
  • Despliegue independiente
  • Failure isolation

Cuándo NO usarlo

  • Equipo pequeño sin madurez operacional
  • Dominio no bien delimitado (riesgo: nano-servicios)
Senior

⚡ Event-Driven Architecture#

Los componentes se comunican a través de eventos asíncronos. Alta desacoplamiento temporal y espacial.

Patrones internos

  • Event Notification: notifica que algo ocurrió
  • Event-Carried State Transfer: el evento lleva el estado completo
  • Event Sourcing: el estado es la secuencia de eventos
  • CQRS: separación de lectura y escritura

Herramientas

  • Apache Kafka, AWS SNS/SQS, Azure Service Bus, GCP Pub/Sub
Senior

☁️ Serverless#

El proveedor cloud gestiona completamente la infraestructura. El código se ejecuta en respuesta a eventos.

Modelos

  • FaaS: AWS Lambda, Azure Functions, Cloud Run
  • BaaS: Firebase, Auth0, Stripe (lógica backend gestionada)

Trade-offs

  • ✅ No gestión de servidores, pago por uso
  • ❌ Cold starts, límites de ejecución, vendor lock-in
  • ❌ Debugging complejo, stateless by design
Mid

🎯 Principios SOLID#

SOLID es un conjunto de 5 principios para diseño orientado a objetos que guían la creación de software mantenible, extensible y testeable. Como Arquitecto, los aplicas a nivel de módulos y servicios, no solo clases.

Principio Significado Aplicación en Arquitectura Nivel
SRP Single Responsibility — una clase/módulo = una razón para cambiar Microservicio por capacidad de negocio. Clase Square no debe calcular área Y mostrar output. Junior
OCP Open/Closed — abierto a extensión, cerrado a modificación Plugins, strategy pattern, feature flags en arquitectura Mid
LSP Liskov Substitution — subtipos sustituibles sin romper el sistema Contratos de API compatibles entre versiones (v1 → v2) Mid
ISP Interface Segregation — interfaces específicas por cliente APIs granulares; no exponer endpoints innecesarios Mid
DIP Dependency Inversion — depender de abstracciones, no implementaciones Service Mesh, abstracciones de storage, repositorio pattern Senior

📐 CAP Theorem#

En un sistema distribuido, ante una partición de red (Partition Tolerance), debes elegir entre:

CP — Consistency + Partition Tolerance

Prioriza datos consistentes. Puede no estar disponible durante una partición. Ejemplos: HBase, Zookeeper, MongoDB (configuración stricta).

Uso: Sistemas financieros, transacciones bancarias.

AP — Availability + Partition Tolerance

Siempre responde, pero puede dar datos stale. Ejemplos: Cassandra, DynamoDB, CouchDB.

Uso: Redes sociales, catálogos de productos, carritos de compra.

⚠️
En la práctica, la partición de red es inevitable. La verdadera decisión es entre consistencia eventual (AP) vs indisponibilidad temporal (CP). El teorema PACELC extiende CAP para considerar también latencia vs consistencia en condiciones normales.

📋 12-Factor App#

Metodología para construir aplicaciones SaaS modernas, cloud-native, altamente portables y mantenibles.

I. Codebase

Un repo, múltiples deploys (dev, staging, prod).

II. Dependencies

Declaradas explícitamente y aisladas (requirements.txt, package.json).

III. Config

Configuración en variables de entorno, no en código. Nunca hardcodear credenciales.

IV. Backing Services

Bases de datos, queues, APIs externas tratadas como recursos adjuntos intercambiables.

V. Build, Release, Run

Separación estricta de fases. Build → artifact; Release → artifact + config; Run → proceso.

VI. Processes

Stateless, share-nothing. Estado en backing services (DB, cache).

VII. Port Binding

La app es auto-contenida y exporta servicios via puerto. No depende de un servidor externo (Apache, Nginx).

VIII. Concurrency

Escalar horizontalmente via procesos (process model).

IX. Disposability

Inicio rápido, shutdown graceful. Resiliente a fallos repentinos.

X. Dev/Prod Parity

Reducir diferencias entre entornos. Usar mismas versiones de DB/cache en local.

XI. Logs

Logs como streams de eventos. La app no gestiona archivos de log; los agrega el entorno.

XII. Admin Processes

Tareas de administración (migraciones, scripts) como procesos one-off.

🔄 Patrones de Arquitectura Distribuida#

⚡ CQRS#

Command Query Responsibility Segregation. Separa las operaciones de escritura (Commands) de las de lectura (Queries) en modelos y bases de datos distintas.

Ventajas

  • Escalado independiente de lectura y escritura
  • Modelos optimizados para cada operación
  • Ideal con Event Sourcing

Desventaja clave

  • Eventual consistency entre read/write stores

📖 Event Sourcing#

El estado de la aplicación se deriva de una secuencia inmutable de eventos, no de valores actuales en DB.

Ventajas

  • Auditoría completa del historial
  • Reconstrucción de cualquier estado pasado
  • Temporal decoupling

Uso típico

  • Sistemas bancarios, pedidos, auditoría

🔌 Circuit Breaker#

Patrón de resiliencia. Cuando un servicio downstream falla repetidamente, el "breaker" se abre y deja de llamarlo temporalmente, evitando cascade failures.

Estados

  • Closed: operación normal
  • Open: bloqueando llamadas (fallo)
  • Half-Open: probando recuperación

Implementaciones

  • Hystrix, Resilience4j, Polly, Istio

🔀 Saga Pattern#

Gestión de transacciones distribuidas sin 2PC. Cada servicio ejecuta su transacción local y publica un evento; si falla, se ejecutan compensaciones.

Tipos

  • Choreography: cada servicio reacciona a eventos
  • Orchestration: un orquestador dirige el flujo (Temporal, Camunda)

🚪 API Gateway#

Punto de entrada único para clientes. Maneja routing, auth, rate limiting, logging, transformación de requests.

Funciones

  • Autenticación/Autorización centralizada
  • Load balancing
  • SSL termination
  • Caching, rate limiting
  • Request aggregation (BFF pattern)

🕸️ Service Mesh#

Infraestructura dedicada a manejar la comunicación service-to-service. Se implementa como sidecar proxy por servicio o por nodo.

Capacidades

  • mTLS automático entre servicios
  • Observabilidad (traces, metrics)
  • Traffic management (canary, A/B)
  • Circuit breaking, retries

Herramientas

  • Istio, Linkerd, Consul Connect

🏭 Producer-Consumer#

Desacopla productores de mensajes de consumidores vía cola/broker. Ideal para baja acoplamiento en microservicios.

Herramientas

  • RabbitMQ, Apache Kafka, AWS SQS
  • Azure Service Bus, GCP Pub/Sub

vs Pub/Sub

  • Queue: un consumer por mensaje
  • Pub/Sub: múltiples subscribers por mensaje

🗄️ Database per Service#

Cada microservicio es dueño de su propia base de datos. Ningún servicio accede directamente a la DB de otro.

Ventajas

  • Loose coupling real entre servicios
  • Libertad de elegir DB por servicio
  • Escalado independiente

Consecuencia

  • Joins distribuidos → Saga o API composition

💡 SRP en la Práctica — Ejemplo Real#

La clase Square vista en la evaluación viola SRP porque tiene dos responsabilidades: calcular área Y formatear output.

// ❌ MAL: dos responsabilidades en una clase
class Square {
    public $length;
    function __construct($pLength) { $this->length = $pLength; }
    
    public function getArea() { return pow($this->length, 2); }
    
    // ❌ Responsabilidad de presentación mezclada
    public function output() {
        return 'The area of square is: ' . $this->getArea($this->length);
    }
}

// ✅ BIEN: separación de responsabilidades
class Square {
    public $length;
    function __construct($pLength) { $this->length = $pLength; }
    public function getArea() { return pow($this->length, 2); }
}

class SquarePresenter {
    public function output(Square $square) {
        return 'The area of square is: ' . $square->getArea();
    }
}

Casos de uso reales#

NETFLIX

Microservicios + Cloud-Native + Chaos Engineering

Netflix migró de un monolito on-premise a más de 1,000 microservicios en AWS entre 2008 y 2016. Inventaron el Chaos Monkey para probar resiliencia deliberadamente. Usan Cassandra como base de datos distribuida para streaming, y Kafka para analytics en tiempo real.

AWS Microservicios Chaos Engineering Cassandra Kafka Zuul API Gateway

Lección: A gran escala, la resiliencia se debe probar activamente, no asumir. El "Netflix OSS" (Hystrix, Zuul, Eureka) inspiró patrones adoptados en toda la industria.

AMAZON

SOA → Microservicios + Two-Pizza Teams

Amazon fue pionero en la transformación a microservicios. La famosa directiva de Jeff Bezos (2002) mandó que todos los equipos debían exponer sus datos y funcionalidades a través de interfaces de servicio sin excepciones. AWS fue el resultado natural de tener que operar esta infraestructura a escala.

AWS Multi-Service DynamoDB (AP) SQS/SNS Two-Pizza Teams

Lección: La organización del equipo (Conway's Law) debe alinearse con la arquitectura. Equipos pequeños y autónomos producen servicios pequeños y autónomos.

UBER

Monolito → Microservicios → Domain-Oriented Microservices

Uber pasó por tres fases: monolito inicial, explosión de microservicios (>2000 servicios), y finalmente DOMA (Domain-Oriented Microservice Architecture) para reducir la complejidad. DOMA agrupa servicios en "layers" y "domains" con propiedad clara.

DOMA Go / Python Kafka (real-time) Cadence (workflows)

Lección: Más microservicios no siempre es mejor. La excesiva granularidad introduce complejidad organizacional. Agrupar por dominios de negocio mejora la mantenibilidad.

SHOPIFY

Monolito Modular (Modular Monolith)

Shopify eligió no descomponer su monolito Ruby on Rails en microservicios. En cambio, introdujeron boundaries estrictos entre módulos usando su framework "Packwerk". Esto les permitió escalar a millones de tiendas con un equipo productivo sin la complejidad operativa de los microservicios.

Rails Monolith Packwerk MySQL (Vitess) Kafka

Lección: El monolito modular es una alternativa válida y frecuentemente mejor que los microservicios para muchas organizaciones. La clave es los boundaries, no el despliegue.

AIRBNB

Microservicios + SOA + Data Platform

Airbnb construyó su infraestructura con servicios orientados a dominios (Listing, Booking, Payments, Trust). Su arquitectura de datos usa Airflow para pipelines, Druid y Presto para analytics, y Kafka como backbone de eventos en tiempo real para sincronizar servicios.

Microservicios Airflow Kafka GraphQL (Unified API)

Lección: Para plataformas de marketplace, separar el dominio de datos del dominio de aplicación permite escalar analytics e inteligencia de negocio de forma independiente.

Contexto Arquitectura recomendada Razón
